## 0. 调查结论（先看这个，决定了后面所有设计）

### 0.1 立绘图片在哪里？——答案是「图床 URL」

你让我看的状态栏脚本证实了这一点。酒馆助手脚本-状态栏.json 的正文里有一张内嵌的 base64 HTML，解码后是一份**硬编码的角色图库**，形如：

```js
{ name: "潮听澜",
  defaultImg:  "https://pub-...r2.dev/潮听澜头像.png",
  portraitImg: "https://pub-...r2.dev/道友录潮听澜.png" },
{ name: "沈慕微",
  defaultImg:  "https://i.postimg.cc/Nf4V2XhJ/1_2_artist_shion(mirudakemann)_....png",
  portraitImg: "https://i.postimg.cc/7YHrrRJx/....png" },
```

即：**立绘不是内嵌在角色卡里的二进制，而是图床直链**。
所以「提取图片元数据」 = 脚本按 URL 把 PNG 拉下来，解析 PNG 的 tEXt 块。

### 0.2 元数据到底是什么？——NovelAI V4.5 格式（已实测一张真图确认）

我下载了 道友录潮听澜.png 并解析，PNG 块结构为：

```
IHDR, tEXt(Title:"NovelAI generated image"), tEXt(Description:...),
tEXt(Software:"NovelAI"), tEXt(Source:"NovelAI Diffusion V4.5 C02D4F98"),
tEXt(Generation time), tEXt(Comment:{...JSON...}), pHYs, IDAT*..., IEND
```

**关键在 Comment 块**，它是一个 JSON，字段实测如下：

| 字段 | 内容 |
|---|---|
| `prompt` | 完整正向提示词，含 NovelAI 权重语法 `1.2::artist:xxx::` |
| `uc` | 负向提示词（长串质量词） |
| `v4_prompt.caption.base_caption` | 场景/画风部分 |
| `v4_prompt.caption.char_captions[0].char_caption` | **角色 DNA！只含角色外观，不含场景** |
| `v4_negative_prompt.caption.base_caption` | 结构化负向 |
| `width/height/steps/scale/seed/sampler` | 生图参数 |

实测 char_caption 内容（潮听澜）：

```
girl, solo, sharp eyes, straight nose, small fang when smiling, short dark blue hair,
low ponytail, dark cyan short garment, silver-white light armor,
tide seal and short sword and waterproof sea chart at waist
```

**这行就是我们要喂给 LLM 去转成角色预设格式的核心原料。** 它天然是「角色外观 DNA」，比从世界书文字硬推要准确得多。

> 注意：这张图是「场景立绘」而非「角色立绘」，所以 prompt 里混了大量洞穴/冰海场景词，
> 而 char_caption 里恰好只有角色。**所以解析器必须优先取 char_captions，prompt 作为兜底/补充。**

### 0.3 两个绘图插件的格式——实测字段差异

**智绘姬 (st-chatu8)** —— 文件 st-chatu8-角色-全部 (1).json，实测结构：

```json
{ "characters": {
    "[苍玄界]潮听澜": {
      "nameCN": "朝听澜", "nameEN": "chao tinglan",
      "characterTraits": "brave, adventurous, sharp",
      "facialFeatures": "short dark blue hair, low ponytail, sharp eyes, ...",
      "facialFeaturesBack": "...", "upperBodySFW": "...", "upperBodySFWBack": "...",
      "upperBodyNSFW": "...", "upperBodyNSFWBack": "...",
      "fullBodySFW": "...", "fullBodySFWBack": "...", "fullBodyNSFW": "...",
      "outfits": ["[苍玄界]海潮轻甲短打套装"],
      "generationContext": "", "generationVariables": {}, "generationWorldBook": "",
      "mediaSchemaVersion": 2, "negative": "" }
  },
  "outfits": {
    "[苍玄界]海潮轻甲短打套装": {
      "nameCN": "海潮轻甲短打套装", "nameEN": "tide light armor and short garment suit",
      "owner": "chao tinglan",
      "upperBody": "...", "upperBodyBack": "...", "fullBody": "...", "fullBodyBack": "..." }}
}
```

→ **特点：角色 × 身体部位 分片（正/背面 × SFW/NSFW 六份），服装单独建表按 owner 关联。**

**小白x** —— 文件 小白x全角 创意工坊角色提示词（直接导入）-3.json，实测结构：

```json
{ "type": "novel-draw-characters", "version": 3,
  "characters": [{
      "id": "char-1787476551005-72vm", "name": "沈慕微", "aliases": [],
      "type": "mature woman",
      "appearance": "flat chest, slender waist, tall curvy figure, long narrow phoenix eyes, ...",
      "negativeTags": "bare chest, forehead mark, bun, ...",
      "danbooruTag": "",
      "outfits": [ { "name": "常服", "tags": "blue and white gradient robe, wrapped tightly, wide sleeves," } ]
  }] }
```

→ **特点：角色单条扁平，appearance 一段搞定全部（不按部位拆分），服装是内联数组，需要 id（格式 char-<时间戳>-<随机>）。**

**这就是为什么必须两套 LLM 预设** —— 两边的字段语义和颗粒度完全不同：

| 维度 | 智绘姬 | 小白x |
|---|---|---|
| 角色粒度 | 按部位切 6 片 | 单字段 appearance 全包 |
| 服装 | 独立表 + owner 关联 | 内联数组 |
| 负向 | 角色级 negative | 角色级 negativeTags |
| 身份 | nameCN + nameEN（要罗马音） | name + aliases + type |
| ID | 无（用 [苍玄界]名 做键） | 必填 char-... |

### 0.4 世界书源数据——实测

我的苍玄界，才不会这么跌宕起伏！世界书.json：**219 个条目**，结构：

- **条目 6-28：====角色设定==== 区块** — 江念、沈慕微、欧阳诚…雪照宁、USER档案（22 个核心角色），每个是 <npc_xxx> YAML 风格块，含：基础信息/外貌特征/与XX的关系/性格调色盘/语料。**这些是「完整角色」源。**
- **条目 172-173：苍玄界势力概览 / 苍玄界区域概览** — 势力树（上三门/下四宗/魔道六门…），每行格式：`  - 天剑宗: 西境断剑山脉剑道圣地 | 核心: ... | 地点: ... | 人物: 欧阳诚,沈慕微,江念`。**这是「势力」选择的天然主键来源。**
- **条目 174：全角色蓝灯精简** — **这就是你截图里那种格式的现成范例**，16966 字，约 104 个角色，每行 `**名字**｜一句话身份。性别，年龄，修为，宗门。性格…`。**它证明了你说的「用户预设决定填什么」，脚本只需提供框架。**
- 条目 30-129：地标 + 常驻人物（每个角色约 1300 字）
- 条目 175-218：追加角色（uid 是大的随机数）

**已确认关键点：势力概览里的人物名 → 能在角色条目里找到对应条目。这条链路可行。**

### 0.5 一个必须提前说的技术风险

**CORS**：实测两个图床的响应头：

| 图床 | Access-Control-Allow-Origin |
|---|---|
| i.postimg.cc | 有（*）|
| pub-....r2.dev | **无** |

浏览器里 fetch() 直接读跨域 PNG 会被 CORS 拦。所以解析链路必须设计成：

1. **优先** fetch(url, {mode:'cors'}) → ArrayBuffer → 解 PNG 块（postimg 这类可以直接跑通）
2. **CORS 失败时**降级到 no-cors + <img>（拿得到像素但**拿不到元数据**）→ 此时提示用户：
   - 手动上传该 PNG 到脚本界面（拖拽/选择文件），本地解析（**一定能拿到元数据**）
   - 或走「代理 URL 前缀」设置（用户自填自己的图床/CF Worker 代理）

→ 所以**「手动导入 PNG」不是可选项，是必要兜底**。这一点我会在界面里做成主路径之一，而不是等失败了才提示。

**形态**：src/苍玄界立绘工坊/ —— **前端界面项目**（index.ts + index.html + Vue 组件），按你选的「可视化操作面板」形态，遵循 .cursor/rules/前端界面.mdc。

## 2. 总体架构

```
① 数据采集层
   ├─ 图库来源适配器：状态栏硬编码图库 / 创意工坊自定义角色 / 用户手动粘贴 URL
   └─ 手动导入：拖拽 PNG/ZIP → FileReader → ArrayBuffer（绕过 CORS，最可靠）

② 元数据解析层  (pure ts, 可单测)
   ├─ png_meta.ts   ：PNG tEXt/iTXt/zTXt 块解析器（手写，不依赖库）
   ├─ nai_parser.ts ：NovelAI Comment JSON → NaiMeta{prompt,uc,charCaptions,...}
   └─ a1111_parser.ts：A1111 parameters 兜底解析

③ LLM 打包层
   ├─ 预设管理：ILlmPreset[]（可增删改查，持久化到脚本变量）
   │             内置两套默认预设：智绘姬 / 小白x
   ├─ 引擎：generateRaw({ ordered_prompts, json_schema, user_input })
   └─ 分批 + 断点续跑 + 重试 + JSON 修复

④ 导出层
   ├─ 智绘姬：合并进 characters/outfits 表 → 下载 JSON
   └─ 小白x：合并进 characters 数组 → 下载 JSON

⑤ 世界书生成（功能二，独立 Tab）
   源选择器(世界书条目树 + 势力树) → 抽取 → LLM 按预设模板生成 → createWorldbook
```

## 3. 功能一：立绘提示词 → 角色预设

### 3.1 界面流程（4 步）

**Step 1｜选图源**
- 自动扫描：读状态栏脚本里的硬编码图库（可从脚本内容正则提取），得到 角色名 → URL 列表
- 也支持：创意工坊自定义角色（cx_workshop_custom_roles_v1 本地存储 / cx_workshop_custom_roles_prompt_v1 聊天变量）
- 也支持：手动粘贴 URL 列表，或拖入 PNG 文件

**Step 2｜解析元数据 → 预览表格**

| 勾选 | 角色名 | 来源图 | 解析状态 | char_caption 预览 | 操作 |
|---|---|---|---|---|---|
| 有 | 潮听澜 | 道友录潮听澜.png | 成功 NAI V4.5 | girl, solo, sharp eyes, small fang... | 查看全量 / 手动编辑 |
| 有 | 沈慕微 | 1_2_artist_shion....png | 成功 NAI V4.5 | ... | ... |
| 无 | 红 | 道友录红.png | CORS 拦截 | — | 手动上传 |

- 解析状态要**明确区分**：解析成功 / 无元数据（二次压缩过的图）/ CORS 被拦 / 待处理
- 每行可展开看完整 prompt / uc / char_captions / 生图参数

**Step 3｜选预设 → 打包**
- 下拉选择 LLM 预设（智绘姬 / 小白x / 用户自建）
- 显示该预设的目标格式说明 + 一条 JSON Schema
- 「开始打包」→ 进度条 + 每个角色的状态 + 实时日志
- **支持断点续跑**：中断后重新打开，已完成的不重跑

**Step 4｜预览 & 导出**
- 左右 Diff：左边 LLM 产出 JSON，右边合并进现有文件的最终结果
- 冲突处理：同名角色已存在 → 选择 覆盖 / 跳过 / 保留双方(改名)
- 「导出 JSON」下载 / 「写入工坊」直接调本地存储 + 触发已有的头像绑定同步

### 3.2 LLM 预设的数据模型

这是「支持添加修改 LLM 预设」的核心。预设存**脚本变量**：getVariables({type:'script', script_id: getScriptId()}) 的 llm_presets 字段。

```ts
const LlmPreset = z.object({
  id: z.string(),                       // 'zhihatsuki' | 'xiaobaix' | uuid
  name: z.string(),                     // 显示名，如「智绘姬 · 立绘→角色预设」
  builtin: z.boolean().default(false),  // 内置预设不可删，但可「另存为」副本后改
  target: z.enum(['zhihatsuki', 'xiaobaix', 'custom']),

  // —— 提示词部分 ——
  system_prompt: z.string(),            // 角色设定
  instruction: z.string(),              // 核心转换指令
  few_shot: z.string().default(''),     // 可选示例（输入→输出 对照）
  output_schema: z.string(),            // 要求 LLM 输出的 JSON schema 文本（人可读）

  // —— 生成参数 ——
  temperature: z.number().default(0.3),
  batch_size: z.number().default(4),    // 一次喂几个角色（长 prompt 时调小）
  max_retries: z.number().default(2),

  // —— 后处理 ——
  json_fix: z.boolean().default(true),  // 是否自动修复 LLM 输出的 JSON
  merge_strategy: z.enum(['merge', 'replace']).default('merge'),
});
```

**预设编辑器 UI**：左侧预设列表（+ 新建 / 复制 / 删除 / 导入 / 导出），右侧表单（提示词多行编辑、参数、格式说明），底部「预览效果」用 1 个角色试跑。

> **关键设计**：预设里的 output_schema 会同时用于 (a) 拼进 LLM 的 user_input，(b) 传给 generateRaw({ json_schema }) 做**强制结构化输出**。这样即使 LLM 不听话，也能拿到合法 JSON。对 170+ 个角色的批量任务，这一点极其重要。

### 3.3 内置两套预设的提示词骨架（你后续可直接改）

**智绘姬预设 · 转换指令骨架**：

```
你是「立绘 → 智绘姬角色预设」的转换器。

输入：一张 NovelAI V4.5 立绘的元数据，其中 char_caption 是角色 DNA（不含场景），
      prompt 是完整提示词（含场景与画风，仅作参考，不要把场景写进角色）。
      uc 是负向提示词。

要求：
1. 提取角色外观 DNA，去掉场景、构图、光影、画风、artist 标签。
2. 按身体部位拆分，输出六个字段：
   facialFeatures / facialFeaturesBack / upperBodySFW / upperBodySFWBack /
   fullBodySFW / fullBodySFWBack
   （背面字段无法从正面图得知时，基于已知特征合理推断，不要留空）
3. characterTraits 输出 2-5 个英文逗号分隔的标签（如 mature woman, expressionless）。
4. nameCN 用中文名；nameEN 用**全小写空格分隔的拼音**（如 潮听澜 → chao tinglan）。
5. outfits 数组填服装键名，键名格式 "[苍玄界]<中文服装名>"；
   服装条目单独输出到 outfits 表，含 upperBody/upperBodyBack/fullBody/fullBodyBack，
   owner 填 nameEN。
6. 保留原始 NovelAI 权重语法（如 1.6::xxx::），不要转成其他语法。
7. 负向：从 uc 中剔除通用质量词（blurry, lowres, worst quality...），
   只保留角色特征相关的负向词。

输出：严格 JSON，结构如下 { ... }
```

**小白x 预设 · 转换指令骨架**：

```
你是「立绘 → 小白x (novel-draw-characters v3) 角色预设」的转换器。

输入：同上的 NovelAI V4.5 元数据。

要求：
1. 提取角色外观 DNA，去掉场景/构图/光影/画风/artist 标签。
2. 全部外观合并进单个 appearance 字段（不要按部位拆分），
   保留 NovelAI 权重语法，末尾以逗号结尾（与原格式一致）。
3. type 输出一个核心身份标签（如 girl / mature woman / 1boy）。
4. aliases 输出该角色的别名数组，无则 []。
5. danbooruTag 若非同名已有角色，留空字符串。
6. negativeTags：从 uc 剔除通用质量词，只留角色特征负向。
7. outfits：内联数组，每项 { name, tags }；name 用中文服装名（如 常服）。
8. id 固定输出空字符串，由脚本生成 char-<时间戳>-<随机>。

输出：严格 JSON，结构如下 { ... }
```

### 3.4 关键实现细节

- **解析器不用第三方库**：PNG 块解析只是读 length(4) + type(4) + data + crc(4)，手写约 60 行，比引入 png-chunks-extract 更可控（而且项目禁止 nodejs 库）。
- **iTXt / zTXt 也要支持**（ComfyUI 可能写在这里，需要 inflate；浏览器有 DecompressionStream('deflate') 可用）。
- **禁止用 prompt 直接当角色 DNA**：实测证明它混了大量场景词（"floating immortal cave dwelling, suspended above a frozen inland sea..."），**必须优先 char_captions**。
- **并发控制**：图片下载并发 4，LLM 调用**串行**（避免酒馆生成队列打架）。
- **token 预算**：单个角色元数据实测约 2-6KB，4 个/批 + 预设本体，控制在合理范围。

## 4. 功能二：世界书生成

### 4.1 界面流程（3 步）

**Step 1｜选源**
- **模式 A · 按世界书条目树**：列出源世界书的条目，按 ====区块==== 自动分组（核心规则 / 角色设定 / 世界观 / 地标势力与常驻人物 / 特殊规则设定 / CG系统 / 变量设定）→ 勾选要纳入的条目（默认只勾「角色设定」区块）
- **模式 B · 按势力**：读 `苍玄界势力概览` 条目，解析成树：

```
上三门
  天剑宗   核心:剑道专修  地点:剑临城,小寒山·月微居,祖师祠堂  人物:欧阳诚,沈慕微,江念,冷小凝
  玄清宗   ...
下四宗 / 魔道六门 / 非宗门势力 / 边地 / 秘境
```

勾势力 → **自动带出其人物列表** → 再去角色条目里取内容（链路已验证可行）

- 两个模式可叠加，最终汇成一个「待处理角色清单」

**Step 2｜选预设 → 生成**
- 预设决定：**世界书名称**、条目拆分方式、每个条目填什么内容
- 预设模型：

```ts
const WorldbookPreset = z.object({
  id: z.string(),
  name: z.string(),
  builtin: z.boolean().default(false),

  worldbook_name_template: z.string(),   // 如 "{源名} · 全角色蓝灯精简"
  entry_mode: z.enum(['single', 'grouped', 'auto']),
                    // single: 所有角色塞进 1 个条目（对应"全角色蓝灯精简"那种）
                    // grouped: 按势力/区块拆成多个条目
                    // auto: 由 LLM 决定
  entry_name_template: z.string(),       // 如 "全角色蓝灯精简" 或 "{势力名}精简"

  system_prompt: z.string(),
  instruction: z.string(),               // 核心：告诉 LLM 每个角色要压缩成什么格式
  field_spec: z.string(),                // 字段/行格式规范
  few_shot: z.string().default(''),      // 可内置「全角色蓝灯精简」的真实样例
  temperature: z.number().default(0.4),
  batch_size: z.number().default(6),

  entry_defaults: z.object({
    strategy: z.enum(['constant', 'selective']).default('constant'),
    keys: z.array(z.string()).default([]),
    position_type: z.string().default('before_character_definition'),
    order: z.number().default(100),
    depth: z.number().default(4),
  }),
});
```

**Step 3｜预览 → 写入**
- 预览：条目名 / 条目数 / 每个条目的内容 / 总字数 / 预计 token
- 与源数据对照，可**单条目手动编辑**后再写入
- 「创建世界书」→ createWorldbook(name, entries)
- 若重名 → 提示 覆盖 / 新建带后缀 / 取消
- 写入后可选 **「绑定到当前角色卡」**（rebindCharWorldbooks）

### 4.2 内置默认预设：全角色蓝灯精简

你给的现成范例我已读到原文，会作为该预设的 few_shot 基准。实测格式为：

```
**诗疏影**｜上古云梦蝶仙分身，常作读书文修。女，未知（外貌十八九），真仙，无宗门。温柔优雅、好奇浪漫，爱好书与故事，亦藏腹黑爱推波助澜。待人先听后说，极少争执。……

**今长乐**｜天剑宗护宗祥瑞仙兽兼风雪堂采药童子。女，24岁（外表十六出头），筑基五层，天剑宗/风雪堂。慵懒随性、务实理性，极度眷恋烟火气。……

```

即：**`**名字**｜身份一句话。性别，年龄（修为），境界，势力。性格与行为模式 2-4 句。`**
外层包 <npc_list> 标签，条目为**蓝灯（constant）**，16966 字 / 104 人 ≈ **每人 163 字**。

预设里我会把这条格式规范写死为默认值，用户可以整段替换。

### 4.3 分批策略（对 170+ 角色是刚需）

- 按 batch_size 切片（默认 6 人/批），每批独立调用
- 每批产出**直接追加**到一个累积缓冲区，失败只重跑该批
- **进度持久化**：processed: string[]、failed: string[]、partial_output: string 存脚本变量 → 关掉界面再打开可继续
- 全部完成后做一次**二次 LLM 调用**（可选，预设开关）：「以下是分批生成的内容，请检查格式一致性、去重、统一标点，不要增删角色」
