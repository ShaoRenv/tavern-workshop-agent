## 0. 前置边界声明（重要）

### 本脚本**不碰** Cloudflare Worker，不发任何网络请求给作者的云服务

**我上一条回复说得含糊了，这里明确澄清：**

你说的完全对。工坊的流程本来就是「**把图片链接保存在本地**」，状态栏再从本地读。
我设计里要读的**只有 localStorage，不是 Worker**。

| 环节 | 数据来源 | 本脚本是否使用 |
|---|---|---|
| 创意工坊**添加/同步**角色 | 走 Cloudflare Worker API | **不用** —— 那是工坊自己做的事 |
| 工坊**已存到本地**的角色 | `localStorage['cx_workshop_custom_roles_v1']` | **只读这个** |
| 状态栏自建角色 | `localStorage['cx_status_custom_roles_v1']` | **只读这个** |
| 内置图库 | 状态栏脚本正文（base64 HTML） | 本地文本正则抠取 |
| 立绘图片本身 | **图床直链**（postimg / r2.dev） | 下载图片**只为读元数据**，这是图片本身的地址，与 Worker 无关 |

**明确不做的三件事：**

1. **不调用工坊的 Worker API** —— 不读不写作者的云服务
2. **不读取/不索取管理员密钥** —— 那些只存在 Worker Secret 里，我们不涉及
3. **不改动工坊的任何数据** —— localStorage 只读，不写入、不覆盖、不删除

> 换句话说：**脚本只做「读本地已有数据」+「下载图片读元数据」。**
> 工坊怎么同步、Worker 里有什么，完全不关我们的事。
> 这也是为什么方案里「导出」走**下载 JSON 文件让你手动导入插件**，而不是反向写回工坊。

## 0. 修正：图源到底是从哪来的？

### 0.1 你问对了 —— v1 的假设是错的

我实测验证了你的三个判断：

| 你的判断 | 实测结果 |
|---|---|
| 创意工坊添加的角色**不会**写进状态栏脚本 | **[已实测] 正确**。在状态栏脚本里搜 `紫不语`，结果 `-1`（不存在）。全脚本搜 `cx_workshop_custom_roles` 也是 `-1` |

### 0.2 真实的数据流（这就是脚本该走的路）

```
┌────────────────────────────────────────────────────────────────┐
│ 状态栏脚本正文 = 一段 base64 编码的 HTML（内嵌 UI）              │
│   解码后里面才是真正的角色图库代码                              │
└────────────────────────────────────────────────────────────────┘
                             │
                             ▼
  localStorage['cx_workshop_custom_roles_v1']   ← 创意工坊写入     
  localStorage['cx_status_custom_roles_v1']     ← 状态栏手动添加   
                             │                                    
                             ▼                                    
   getAllCustomRoles() = loadWorkshopRoles() ∪ loadCustomRoles()   
                             │                                    
                             ▼                                    
   getMergedNpcList()  = [ 内置 npcList 20人 ] ∪ getAllCustomRoles()│
                             │                                    
                             ▼                                    
   { name, defaultImg, portraitImg, sect, profile, source }        
```

**关键代码（实测原文）**：

```js
const CUSTOM_ROLE_STORAGE_KEY  = 'cx_status_custom_roles_v1';
const WORKSHOP_ROLE_STORAGE_KEY = 'cx_workshop_custom_roles_v1';

function loadWorkshopRoles() {
  const parsed = JSON.parse(localStorage.getItem(WORKSHOP_ROLE_STORAGE_KEY) || '[]');
  return parsed.map(normalizeWorkshopRole).filter(Boolean);
}
function loadCustomRoles() {
  const parsed = JSON.parse(localStorage.getItem(CUSTOM_ROLE_STORAGE_KEY) || '[]');
  return parsed.map(normalizeCustomRole).filter(Boolean);
}
function getAllCustomRoles() {
  const roleMap = new Map();
  loadWorkshopRoles().forEach(role => roleMap.set(role.name, role));
  loadCustomRoles().forEach(role => roleMap.set(role.name, role));
  return [...roleMap.values()];
}
```

**归一化后的角色对象**（实测）：

```js

  defaultImg,    // 'https://...'  ← 头像
  portraitImg,   // 'https://...'  ← 立绘（我们要的）

  profile,       // 角色设定文本（最长 12000）
  custom: true,
  source         // 'workshop' | 'statusbar_manual'
}
```

**另有一份内置图库**（实测 20 人），硬编码在状态栏 HTML 里，形如：

```js

    portraitImg: "https://i.postimg.cc/7YHrrRJx/....png" },
```

> **结论**：脚本不该「读状态栏脚本里的固定角色」，而应该
> **① 直接读那两个 localStorage key**（拿最新、最全的工坊角色）
> **② 再从状态栏脚本正文里正则抠出内置 npcList**（作为基础图库）
> **③ 两者按 name 合并去重**（与状态栏 getMergedNpcList 行为一致）
> **④ 用户可再手动粘贴 URL / 拖入 PNG 补充**

这样就能做到你说的「**根据图库批量选择角色**」。

**提取规则做成可配置**（你说「用 \"JSON\"{json内容} 提取」，但也要支持别的写法）：

```ts
const ExtractRule = z.object({
  label: z.string().default('JSON'),   // 标记名
  // 内置几种模式，用户可选或自定义正则
  mode: z.enum(['fenced', 'labeled_brace', 'regex', 'whole']).default('fenced'),
  // fenced       → ```json ... ```
  // labeled_brace→ "JSON"{ ... }   ← 你提到的写法
  // regex        → 用户自填正则 + 捕获组
  // whole        → 整个回复就是 JSON
  custom_regex: z.string().default(''),
  json_path: z.string().default(''),   // 可选：只取 JSON 里的某个路径
});
```

**图片元数据提取内容也可自定义**（你说「提取内容可以自定义标签，但内置默认 char_captions 与 prompt」）：

```ts
const MetaExtractRule = z.object({
  id: z.string(),
  name: z.string(),
  builtin: z.boolean().default(false),
  // 从图片元数据里取哪些字段
  fields: z.array(z.object({
    label: z.string(),          // '角色DNA'
    source: z.enum(['tEXt_key', 'json_path', 'regex']),
    key: z.string(),            // 'Comment' 或 'v4_prompt.caption.char_captions[0].char_caption'
    fallback: z.string().default(''),  // 取不到时的备用路径
  })),
  // 把取到的内容渲染成给 LLM 的文本块
  render_template: z.string(),  // '【{{label}}】\n{{value}}'
});
```

**内置默认规则**（就是你说的）：

### 2.3 容错说明默认内容（你说的「会写一些容错」）

预设内置这段，用户可改：

```
【容错规则】
1. 若某个角色在世界书中查不到完整设定，只写名称与已知信息，不要编造。
2. 若同一角色出现多个名称写法（如 朝听澜/潮听澜），以世界书条目名为准，
   在输出中只保留一个，另一个放入 aliases 字段（若模板有该字段）。

   [缺失] 角色名（势力名）
4. 若输入为空或无法解析，输出 {\"error\": \"原因\"}，不要输出空内容。
```

## 3. 功能一的完整界面流程

**Step 1｜图库**
- 自动加载三个来源并合并去重，表格展示：角色名 / 势力 / 来源 / 立绘 URL / 头像 URL
- 支持全选 / 按势力筛选 / 搜索 / 只看有立绘的
- 也可粘贴 URL、拖入 PNG 补充

**Step 2｜解析**
- 勾选后点「解析元数据」→ 并发 4 拉图 + 解析
- 表格实时显示状态：`成功 NAI V4.5` / `成功 A1111` / `成功 无 char_caption（已降级）` / `CORS 拦截` / `无元数据`
- 点行展开看完整字段；可**手动编辑**某个角色的元数据（覆盖解析结果）

**Step 3｜打包**
- 选 LLM 预设（智绘姬 / 小白x / 自建）+ 选 JSON 模板
- 「开始打包」→ 分批调 LLM → 按 `extract_rule` 抽 JSON → 校验 → 合并
- 进度条 + 逐角色状态 + 实时日志 + **断点续跑**

**Step 4｜导出**
- Diff 预览（LLM 原始产出 vs 合并后最终结果）
- 同名冲突：覆盖 / 跳过 / 改名
- 下载 JSON（可选：写回 localStorage）
