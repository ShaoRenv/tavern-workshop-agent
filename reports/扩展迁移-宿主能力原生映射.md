## 二、三个必须知道的「降级/差异」点

1. **`getScriptTrees`（core/portrait.ts:18）没有原生对应。**
   这是读「酒馆助手脚本树」的接口——**本来就是酒馆助手独有的概念**。portrait.ts 用它找状态栏脚本正文。扩展形态下若还需要这个能力，只能：① 继续要求酒馆助手存在（声明为可选依赖）；② 或改成读 ST 原生扩展目录。**这是唯一一个没有原生替代的接口。**

2. **`registerMacroLike` 的正统替换是 `macros.register()`。**
   ST 已经把 `MacrosParser.registerMacro` 标为 **@deprecated**，指向 `macros.register(name, {handler, description})`（st-context.js:180-181、:112）。我们用扩展形态应当走**新的 `macros` API**，而不是继续用旧 registerMacro——顺带解决「宏注册端到端未证实」的历史遗留。

3. **宏拼写差异：ST 是 `substituteParams`，酒馆助手是 `substitudeMacros`**（少一个 t、名字不同）。写适配层时**不要**按名字直接映射。

## 三、对架构的直接影响

**原计划顾虑的「扩展里拿不到宿主接口」——不成立。** 真实情况反过来：

- 酒馆助手（JS-Slash-Runner）的那层 API，**很大程度就是 ST 原生能力的再包装**；
- 扩展形态下我们**直接对接 ST 原生**，少一层中间商，也**不再依赖第三方插件**；
- 用户的核心诉求「能力取决于插件」由此**真正成立**：底座自带原生适配层，插件声明需要什么能力。

**桥的设计因此确定为（provider chain）：**
```
resolve(name) →
  1. 注入的假实现（测试 / 覆盖）
  2. 原生适配器：SillyTavern.getContext() 里的对应导出   ← 新增，主路径
  3. globalThis.TavernHelper[name]                      ← 兼容装了酒馆助手的环境
  4. globalThis[name]                                    ← 兼容旧行为
```
