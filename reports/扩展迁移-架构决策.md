## 决策 0：**迁。** 风险已证伪，收益确凿

原以为「扩展里拿不到酒馆助手接口」是致命风险 —— **实测证伪**。JSR（酒馆助手）本身只是 ST 原生的薄封装，底座 17 个宿主依赖**全部**能在 `SillyTavern.getContext()`（145 个 key）找到对应。

**真正需要自建的只有 3 块**（不是「复刻整个 JSR」）：
1. 脚本树（`getScriptTrees` 等）—— ST 无「脚本」抽象
2. global 初始化协议（`global_X_initialized`）—— 可基于 `eventSource` 自定
3. 变量作用域适配层 —— JSR 六作用域 vs ST local/global

## 决策 1：宿主桥 —— 单条 provider chain，**晚绑定**

消灭审计发现的**三条**平行解析链，合成一条：

```
resolve(name):
  1. 注入的假实现（测试 / 覆盖）            ← 保留 hostFn 第(1)层，可测性的根
  2. 注册的**原生适配器**（扩展自带）        ← 新增：ST.getContext() / STscript / 后端 API
  3. globalThis.TavernHelper[name]          ← 兼容装了 JSR 的环境
  4. globalThis[name]                        ← 兼容旧行为
```

**硬约束（全部来自审计的实证判定）**：
- ✅ **必须晚绑定**：不 `.bind` 固定函数引用，每次调用重新解引用。理由：`hostFn` 闭包是晚绑定，`globalFunction` 的 `.bind` 是早绑定；**扩展热重载时宿主接口会被替换**，晚绑定才拿到新实现。
- ✅ **删除 `globalFunction()`**（`agent/transport.ts:166-183`）**并同时删掉 `deps.substituteMacrosImpl` / `deps.generateRawImpl` 两个后门**。只删前者不删后者，二义性没根除（会变成「链 + 后门」）。
- ✅ **收编第三条链**：`core/macros.ts:55-58` 的 `applyStMacros` 裸取 `globalThis.substitudeMacros`，与 `agent/transport.ts:450` 走 `globalFunction` —— **同一接口两条链**，最坏形态，必须统一。
- ✅ `fetch` 也纳入（`transport.ts:494`、`image/nai.ts:328` 裸取 `globalThis.fetch`）。

## 决策 2：能力表（Capability）—— 从个案提升为框架机制

现状：能力可得性是**逐插件硬编码的个案**（`image/manifest.ts` 的 `status()`），缺接口时各处自己 try/catch 静默降级（`portrait.ts:19-26` 返回 `[]`、`storage.ts:495` `console.warn`）。

**改为**：
```ts
interface Capability { name: string; provider: string; required: boolean; degrade?: () => void; label: string; }
```
- 底座启动时探一遍，得出**能力表**；
- 插件在 `contributes` 里声明**需要哪些能力**；
- 能力缺失 → **该插件不注册**，并给出可读原因（而非运行时炸在半路）；
- 设置页直接显示「立绘图库：不可用（缺 getScriptTrees）」。

**明确标为不可用能力**：`getScriptTrees`（ST 无对应）。图库数据源改走 ST 原生 —— `assets.ts:80-83` 已经在用 `/api/images/list`。

## 决策 3：存储 —— 抽 `StoragePort`，**RootData 零改动**

```ts
interface StoragePort { read(): unknown; write(data: unknown): void | Promise<void>; }
createStoragePort(backend: 'extensionSettings' | 'scriptVars' | 'memory'): StoragePort
```

- ✅ **删除** `VariableScope{type:'script'}` / `resolveScriptId()` / `__CX_SCRIPT_ID__`（纯删除，无下游依赖）
- ✅ **新增 v6 迁移**：脚本变量 → 扩展存储（放进既有 `migrateRootData` 版本链，模板见 `storage.ts` 的 v4→v5）
- ⚠️ **不要把全部状态塞 `extensionSettings`**：实测落盘在 `data/default-user/settings.json`（**已 50MB**，每次保存**全量重写**）。多会话 + 事件日志宜**分片**或走 `accountStorage` / `chatMetadata`。
- ✅ **最大好消息**：`RootData` + zod schema + v1→v5 迁移函数**100% 可复用**（审计实测确认）。阻塞的只是**存储后端**，不是数据模型。

## 决策 4：UI —— **面板是常驻 DOM，不是 iframe**（本轮结案）

**事实**（Lead 实测）：`public/index.html:5777` 是 `<div id="extensions_settings2" class="flex1 wide50p">` —— **普通 DOM 节点**。官方模板就 `$app.appendTo('#extensions_settings2')`。探针也实测挂载成功。

**因此必须修正这 4 处「iframe 自适应高度」假设**（审计 §9 的未决项现已解除）：

| # | 位置 | 现状 | 扩展版 |
|---|---|---|---|
| 1 | `global.css:8` | 「不用 vh、不给整页锁高度、不做滚动容器」 | **补滚动容器 + 高度约束** |
| 2 | `components/AppShell.vue:36-37` | 「不要在这外面再套一层滚动容器」 | 同上，要重估 |
| 3 | `components/Sheet.vue:21-28` | 用文档流 + `scrollIntoView` 而非 fixed 居中（为迁就 iframe） | 常驻 DOM 下 **fixed 居中反而更正确** |
| 4 | `core/portrait.ts:1117-1139` | `hostStorage()` 三级兜底穿透 `parent/top.localStorage` | **扩展本就同源**，这条变简单；但仍要显式化，别静默返回 `[]` |

**挂载时机**：`getContext()` 在模块求值时**已就绪**（145 key），但 `APP_READY` **不稳定**（实测 24050ms vs 556ms）→ **顶层只注册，UI 挂载放 `activate` hook 或 `APP_READY` 之后**。

## 决策 5：宏 —— 换 ST 新 API，并**从类型上根治**历史积病

| | 旧 | 新 |
|---|---|---|
| 注册 | `registerMacroLike`（JSR 私有） | `getContext().macros.register(name, {handler, unnamedArgs})` |
| 注销 | `unregisterMacroLike` | `macros.registry.unregisterMacro(name)` |

**历史未证实项已结案（根因是参数名写错）**：传 `minArgs`/`maxArgs`/`unnamedArgDefs` → **注册「成功」但永不替换、且不报错**。真名是 `unnamedArgs`（`MacroRegistry.js:66`）；`minArgs` 是**产物**字段（:137）。默认 `strictArgs=true`（:68）→ 静默失败。
> **不变量**：ST 宏注册**静默失败**。底座必须**注册后自检**一次。

**两条硬约束**：
1. **handler 必须同步**（官方 :916「can never return a Promise」）。我们的 `PluginMacro.render` 契约**本来就是同步返回 string**，天然兼容 —— **但要固化**：类型不放宽 + 运行时守卫（返回 Promise 则拒绝注册）+ 测试断言。
2. **命名空间**：ST 内置宏实测 **131 个**，底座宏名要带前缀/中文，避免冲突。

**从类型上根治 `plugin_state` 误传**（审计的核心建议，我采纳）：
- `PluginStateHost.plugin_state` 改**必填** + 引入**不透明** `PluginState` 值对象 → `{plugin_state: undefined}` **编译不过**；
- `rememberMacroValues(data, state)` **补必填 state 参数**（它现在根本没有 state 参数，这才是根因）；
- `lastMacroValues` **关闭时清空**，并按会话分区；
- 补回归测试「插件关闭时其宏名不得进缓存」。
> 依据：`rememberMacroValues` 缺陷与阶段 3 的 **F-A'** 是**同一个坑**（`agent/registry.ts:164` 还留着当时的注释）。两次都栽在「`plugin_state` 的传递语义」→ 这不是巧合，是**接口设计缺陷**。

## 决策 6：单例 → 实例容器

宏注册表（`macros.ts:123/140`）+ `registeredTavernMacros`（`host.ts:65`）是**模块级单例**，注释明写「后注册覆盖前者」—— 单实例成立，**多实例/热重载直接变 bug**。

**改为** `createCore({host, storage, macros})` 实例容器，并**给 `unwirePluginMacros` 接上真实 `dispose()`**（审计实测它现在是**死代码**：src 与 tests 各 0 处调用，而 `App.vue:300` 的 `onUnmounted` 只摘了 `visibilitychange`，没拆宏接线）。

## 决策 7：构建 —— **沿用 webpack**，但撤销单文件妥协

现有工程已是 webpack5 + TS + Vue3 + pinia + zod，**迁移成本最低**。官方 webpack 模板（`docs/Extension-WebpackTemplate/`）与我们的栈一致。

**撤销清单（纯收益）**：
| 妥协 | 位置 | 扩展版 |
|---|---|---|
| `splitChunks: false` | `webpack.config.ts` | **撤销**，实测分包可用 |
| `String.fromCharCode(123,123)` 拼花括号 | `plugins/host.ts:112` | **撤销**，直接写字面量 |
| 插件页必须**静态 import** | `App.vue:93`/`types.ts:30`/`Page.vue:99` | **撤销**，改 `component: () => import()` —— **顺带补上「插件=自包含目录」在 UI 层的破洞** |
| 宏残留闸（禁字面量） | `tests/bundle_artifact` | **放宽/删除** |

**manifest.json**（照官方模板）：
```json
{
  "display_name": "…", "loading_order": 120,
  "js": "dist/index.js", "css": "dist/index.css",
  "author": "…", "version": "0.1.0", "homePage": "…", "auto_update": true,
  "hooks": { "activate": "onActivate", "install": "onInstall", "update": "onUpdate",
             "enable": "onEnable", "disable": "onDisable", "delete": "onDelete" }
}
```
> ⚠️ `activate` **5 秒超时**且模块是**单例**（点「启用」不重跑顶层代码）→ 初始化逻辑必须写成**可重复调用的 `init()`**，别依赖顶层副作用。
> ⚠️ 动态 chunk 用 **hash 文件名**，更新后旧 chunk 404 → **发布必须原子**（index.js 与 chunk 同批上线）。

## 决策 8：分层 —— 保持并**加 lint 门禁**

审计实测**100% 合规**：`plugins/**` 零 import `components/`/`views/`/`stores/`/`App.vue`；插件间零互 import。

**改进**：把这条规矩做成 `no-restricted-imports` **lint 门禁**，而不是靠人工自觉。同理把「禁止向 `PluginStateHost` 传字面量 `undefined`」也做成门禁 —— **两者本质都是「把口头约定变成编译器能拦的约束」**。
