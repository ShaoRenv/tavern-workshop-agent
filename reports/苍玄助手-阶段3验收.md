## 3. F-V1 严重项：根因、复现、修复确认

**第一轮现象**（复现：关掉苍玄助手 → 刷新 → 看「插宏」或跑 `render()`）：
```
cangxuan OFF | {{图片提示词}} => "[]"          ✅
cangxuan OFF | {{角色列表}}   => "[ROLE_A]"    ❌ 泄漏真实内容
cangxuan OFF | {{图片元数据}} => "[PROMPT_X]"  ❌ 泄漏真实内容
```

**根因（我定位到行）**：`core/macros.ts` 的 `render() = applyPluginMacros(applyOwnMacros(applyStMacros(text)))`，而 `applyOwnMacros` 硬编码了
```ts
// core/macros.ts:86-89（修复前）
角色列表: d.characters,
图片元数据: d.portrait_meta,
```
它**先于且无条件**执行 → 等 `applyPluginMacros` 想按「插件关了回空串」处理时，占位符早被换成真值。`图片提示词` 正确，恰恰因为它**不在**那张表里。

**为什么测试没拦住**：task-7 的断言只覆盖 `图片提示词`，于是「关掉即消失」看起来成立 —— 正是任务书预警的「只在一层成立」。

**修复确认（本轮复跑）**：三者在 OFF 时均为 `[]`，ON 时均正常出值，NEVER 场景保持占位符。**该严重项闭环。**

## 4. F-V2 中等项：芯片列表 —— 真酒馆开关实测通过

**第一轮**：`MSG_MACROS` 是写死数组，ON/OFF 都是同样 12 个芯片（多给两个插件宏、漏掉 `{{图片提示词}}`）。

**我定位的两处根因（Lead 已采纳）**：
1. `plugins/host.ts:48` 用 `allMacros()`（全插件，不管开关）注册名字清单 —— 对**渲染**是对的（停用名字也得在，才能把占位符换成空串），但当**界面数据源**是错的；
2. `core/macros.ts:135` 的 `pluginMacroNames()` 返回**模块级普通变量，非响应式** → `computed` 收集不到依赖，开关变了不重算。

**修复确认（我用真酒馆开关实测，非推理）**：

| cangxuan | 芯片数 | 三个插件宏 | 落盘状态 |
|---|---|---|---|
| **ON** | **12** | 三个都在 | `{cangxuan:{enabled:true}}` |
| **OFF**（点真开关） | **9** | `hasPrompt=false / hasRole=false / hasMeta=false` | `{cangxuan:{enabled:false}}` |

```
ON  chips = [用户需求 世界书 已选条目 角色名 产物 未完成 轮数 截图 当前时间 图片提示词 角色列表 图片元数据]
OFF chips = [用户需求 世界书 已选条目 角色名 产物 未完成 轮数 截图 当前时间]
```
（注：UI 开关写入有 2500ms debounce，我等待 3.2s 后读 `getVariables` 复核落盘值才判定，避免假阴性。）
**该中等项闭环。**

## 6. 如实标注：两条「未证实」+ 一条宿主限制

### 6.1 `scopes: ['tavern']` 端到端 —— **未证实**
`plugins/host.ts` 现传的确实是 **RegExp**（符合 `@types/function/macro_like.d.ts` 的 `registerMacroLike(regex: RegExp, ...)` 签名），且 `__CX_HOST_API__.registerMacroLike` **是 function**（桥通了）。
但我**找不到有效判据**：`TavernHelper.substitudeMacros` 与 `ST.getContext().substituteParams` 对 `{{user}}`/`{{char}}` 正常，对**我自己刚注册的探针宏同样不替换** → 这两个 API 不在酒馆助手宏的替换路径上，**不能作为判据**。Lead 复核后确认：该宏由 JSR 的**消息渲染路径**应用。
**结论：未证实**（不是「已实现」，也不是「坏了」）。建议改用「真角色卡里写 `{{图片提示词}}` 再发一条消息」验证 —— 我没做，那会往用户聊天里插内容，越了只读验收的分寸。

### 6.2 生图自检回路 —— **未证实（仅静态核查）**
- 能确认：`gen_image` 说明里加了「画完自己看一眼」的指引（源码可见）；`loop.ts` 把 `record.images` 回灌成 user 消息的**机制本来就在**（阶段 2 已有）。
- **未能确认**：模型是否因此真的改变行为 —— 需真实多模态回合 + `api.send_images` 开启 + 费用，属行为性断言。
- **证据强度：未证实。不应写成「已实现」。**

### 6.3 宿主限制：未开聊天时 `getChatWorldbookName('current')` 会抛
真酒馆实测：无聊天时抛 `未打开任何聊天, 不可获取聊天世界书`。`scopes()` 用 try/catch 兜住（我验了：抛错时整表退化为全「未启用」，**不崩**）—— 容错设计正确。但**未开聊天时「当前聊天」这一态永远判不出来**，属宿主限制。

## 7. 新增功能 1：`wb_list` 标绑定范围 —— ✅ 四态 + 优先级 + 容错全验

```
G-book    => global / 全局
C-primary => character / 当前角色卡     ← primary
C-extra   => character / 当前角色卡     ← additional 也认
CH-book   => chat / 当前聊天

PRECEDENCE：同一本同时挂 全局+角色卡+聊天 => 只报「全局」  ✅ 与注释口径一致
```
真酒馆 API 形状核对：`getCharWorldbookNames('current')` 实测返回 `{primary:null, additional:[]}` —— 与实现里的 `.primary` / `.additional` 解析**吻合**。抛错容错见 §6.3。
