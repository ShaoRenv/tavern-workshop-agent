# 苍玄助手 · 底座与插件（设计理念转向）

> 起因：用户提出「我想主要做一个 agent 底座，其他如苍玄界专用的立绘功能、还有其他都做成插件」。
> 本文回答三件事：**边界怎么划**、**插件能贡献什么**、**界面长什么样**，最后给可验收的迁移步骤。

## 0. 一句话

底座只回答一个问题：**选预设 → 跑一轮 → 看结果**。其余一切都是插件（页面 / 工具 / 提示词块 / 设置）。

## 1. 什么该进底座：三句判据

1. **没有它，agent 还跑不跑得起来一轮？** 跑不起来 → 底座
2. **它是某个内容 / 场景专有的吗？**（立绘＝苍玄界、生图＝某个画图服务）是 → 插件
3. **关掉它，用户还有没有「助手」？** 没了 → 底座；只是少个功能 → 插件

用它过一遍现有功能：

| 现有东西 | 归属 | 说明 |
|---|---|---|
| 对话循环 / 工具调用 / 停止 / 轮次 | 底座 | 没有它没有 agent |
| 运行状态（● 运行中 · 第 N 轮） | 底座 | 「看得见在跑」是底座的承诺 |
| 模型接口（自填接口 / 酒馆）、多模态、超时 | 底座 | 没有它发不出请求 |
| 预设（items + 特殊层）/ 技能 / 轮数预算 | 底座 | 没有它不知道发什么 |
| 会话、事件日志、记录页 | 底座 | agent 自己的运行史 |
| 存储（脚本变量）/ 导入导出 / 版本迁移 | 底座 | 数据在「助手」里 |
| 插件注册表 + 页签注册表 + 装载 | 底座 | 底座的定义之一 |
| 世界书页面 + 6 个世界书工具 | 内置插件（默认开） | ST 最大众用例，但可关 |
| 立绘功能（`{{图片提示词}}` 宏 + 3 个图片工具）+ 智绘姬预设模板 | 内置插件**「苍玄助手」**（默认开，无页面） | 苍玄界专有 |
| 生图 gen_image + NovelAI 设置 | 内置插件（默认关） | 第三方服务专有，按张收费 |
| 技能库 / 插件管理 | 底座的管理面 | 挂进「设置」 |

**不进底座的东西**（即使它很常用）：立绘、世界书、生图、翻译、联网搜索、TTS……常用不等于核心；
判断只看「关掉之后 agent 还成不成立」。

## 2. 插件能贡献什么（活的 / 入口 两类，最小可用）

```ts
interface PluginManifest {
  id: string;            // 'cangxuan' / 'worldbook' / 'image' / 'mcp'（页面 id 仍是老的 portraits / worldbook → 零迁移）
  name: string;          // 界面上显示的名字
  version: string;
  apiVersion: 1;         // 底座只保证同大版本兼容
  desc: string;          // 一句话（插件列表行上用）
  builtin?: boolean;     // 内置插件：可关不可卸；外部插件：可卸
  defaultEnabled: boolean;
  contributes: {
    pages?: PluginPage[];      // 页面：{ id, title, order, inTabbar } → 变成顶栏一格；**可以一个都不要**
    tools?: string[];          // 工具：阶段 1 写工具名（实现仍在 agent/registry.ts）；阶段 3 起换成 ToolDef
    macros?: MacroDef[];       // 宏：{ key, scopes: ('tavern'|'preset')[], resolve(ctx) }，注册 / 注销由底座做
    skills?: Skill[];          // 自带知识：随插件开关
    presets?: PresetTemplate[];// 预设**模板**：入口贡献，导入即归用户，关插件不回收
    settings?: SettingsField[];// 声明式设置表单：插件声明字段，**宿主渲染**
  };
  status?(config): { label; kind };   // 插件自己算状态（未启用 / 出错 / 缺配置 / 已启用）
}
```

**贡献分两类**（这条以后每个贡献点都按它判）：

- **活的**：页面 / 工具 / 技能 —— 关掉插件即消失；
- **入口**：预设模板 —— 点一下导入成用户数据，导入后归用户，**关插件不回收**（否则用户数据会无声消失）。

`contributes.prompts`（提示词块）**本版删掉**：没有消费者，跟钩子总线一起进二期。

两条硬规矩：

1. **插件只拿得到 `host`**（底座给的能力），插件之间**不许互相 import**。这样任何一个插件都能单独关掉/拿掉。
2. `contributes` 里的东西必须能「关掉即消失」：关掉世界书 → 顶栏没有世界书页；关掉苍玄助手 → 模型拿不到它的 3 个工具、`{{图片提示词}}` 这些宏也一起失效。

## 3. 底座给插件的能力（host 接口，唯一外部依赖）

| host 能力 | 内容 | 现状 |
|---|---|---|
| `host.worldbook` | 列世界书 / 列条目 / 读 / 写（写只落草稿）/ 草稿落地 | 已有 core/worldbook.ts |
| `host.variables` | 脚本变量读写（插件自己那一段） | 已有（storage.scope） |
| `host.storage` | 插件自己的持久化分区 `plugins.<id>` | 已有雏形 |
| `host.config` | 读 / 写**自己那一段**设置（get / set / subscribe，只认调用方插件的 id） | 新增；插件内容页只拿这个，**不许 import store** |
| `host.llm` | 调模型（无工具的一次生成，给页面流程用） | 部分（transport） |
| `host.image` | 生图（由生图插件实现后注入） | 已有 ctx.genImage |
| `host.http` | 带超时/错误翻译的 fetch | 新增 |
| `host.ui` | 通知 / 确认 / 表单弹窗 / 长任务进度 | 部分（App.vue 的 notify/Sheet） |

## 4. 界面：顶栏只放「你在用的页面」

```
顶栏：  对话 │ 世界书 │ 设置        ← 记录收在对话页右上角 ⋯ 里（不是页面、不占格子）；苍玄助手不贡献页面（它给宏和工具）；世界书是插件贡献的页面
设置：  接口 │ 预设 │ 能力（工具 · 技能 · 插件）│ 数据   ← 管理面（宏不单独占段：来源在插件管理页）
插件管理页：插件列表（纯列表）→ 点进某个插件 → 它自己的设置
```

- **顶栏 = 页面（你在哪）**，不是功能清单。插件贡献页面，页面才上顶栏。
- **少用的东西不占页面**：记录 → 对话页右上角 `⋯` 里的一张 Sheet；能力 / 技能 / 插件 → 设置。
- **管理面在「设置 · 能力」**：工具（标注来自哪个插件）/ 技能库 / 插件列表。
- **插件列表只有列表**：一行一个插件 = 图标 · 名字 · 状态 · 它加了什么 · 开关 · `>`。
- **插件管理页** = 这个插件的设置；它贡献的页面 / 工具只放**可点跳转行**，不写解释段落。
- **插件内容页** = 插件贡献的页面（例：世界书页）。两个词别混用：「插件页」这种说法本版起不用了。

## 5. 数据与兼容

```
RootData = { ...现有底层字段（api / presets / skills / sessions / drafts / artifacts）,
             plugins: { <id>: <这个插件的设置> },        // 已有（plugins.image → 现在还有 plugins.cangxuan）
             plugin_state: { <id>: { enabled: boolean } } }  // 新增：插件开关（内置插件也在这；installed_at 二期才加）
```

- **页签 id**：世界书仍是 `worldbook`、对话 / 设置不动；立绘页（`portraits`）在阶段 3 取消（功能变成宏 + 工具），老数据 `active_tab = portraits` 自动回落到对话页 → **老数据零迁移**。
- 插件关掉时，它的设置留在数据里（重新打开还在），只是不生效。
- `plugins.cangxuan`：图库来源 / 元数据读取规则 / **手动元数据 manual_meta**（现在的传图结果只在内存里，刷新就没 → 顺手修掉）。

## 6. 迁移步骤（每步都能单独验收）

| 步 | 内容 | 验收标准 |
|---|---|---|
| 1 | 插件契约（含宏）+ 四张注册表 + **页面注册表驱动**；苍玄助手（原立绘）/ 世界书先「标记」成插件页，功能一动不动 | 界面与现在完全一样（6 格、老顺序、名称都不变） |
| 2 | 「能力」并进「设置 · 能力」（工具/技能/插件三段）+ **记录收进对话页右上角 `⋯`**；工具行标「来自谁」 | 顶栏 4 格（对话 / 苍玄助手 / 世界书 / 设置）；`⋯ → 记录` 能开能关 |
| 3 | 搬家：`plugins/builtin/cangxuan`（**去页面**，改贡献宏 + 3 个图片工具）/ `worldbook` / `image` | 顶栏 3 格（对话 / 世界书 / 设置）；关掉苍玄助手 → 它的宏与工具一起消失；删掉任一插件目录只影响它自己 |
| 4 | 声明式设置表单（插件声明字段 → 宿主渲染） | 生图插件的管理页不再自己画表单 |
| 5 | **MCP 插件**（HTTP / SSE；远端工具走**运行时注册**） | 连上服务器 → 工具出现在「能力 · 工具」且能被真调用；断开即消失；CORS 被挡时给可操作提示 |
| 6 | 外部插件装载（URL / 粘贴）+ apiVersion 校验 + 失败隔离 | 按之前冻结的节奏，等前五步稳了再做 |

## 7. 实话：代价与风险

- 这是**底座化重构**：现有 6 页里 4 页要动（立绘页删、记录页收进 `⋯`、能力并进设置、世界书搬家），测试里大量 import 路径要跟着动；所以分 5 步、每步验收。
- **插件 API 对外**（给别人用）意味着 apiVersion 兼容承诺 + 文档 + 示例插件，是长期成本；只自己用就轻很多。这件事要你定。
- 同源限制不变：插件代码跟主程序同权，浏览器给不了进程级隔离；「禁网」只能靠隔离 iframe 那一档。
- 全权装载、不做权限门禁这条不变（开源项目，出事不怪底座）。

## 4.1 前端要做的适配（对着现有代码逐条列的）

结论：**适配集中在 5 个文件（+ 1 个新文件 core/pages.ts），持久化数据不用改**。插件内容页能上顶栏这件事，本质是把「写死的 6 个页签」换成「注册表渲染」。

| 位置 | 现在的写法 | 要改成 |
|---|---|---|
| `core/types.ts` | `TAB_IDS` 常量数组 + `TabId` 联合类型 + `active_tab: z.enum(TAB_IDS)` | 页签集合变成**运行时注册表**（核心页 + 已启用插件页按 `order` 合并）；**`TAB_IDS` / `TabId` 删掉**（页面 id 只在注册表与核心页定义里各一份）；`active_tab` 放宽成 `z.string()` + `migrateTabId` 兜底 + 「当前可用页面」校验。**老数据 `portraits`/`worldbook` 不变 → 零迁移** |
| `components/ui_types.ts` | `TAB_LABELS: Record<TabId, string>` 手写表 | 删掉；标题跟着页面定义走（`PluginPage.title`） |
| `components/AppShell.vue` | `v-for="id in TAB_IDS"` + `TAB_LABELS[id]` | 从注册表渲染：核心页常驻 + 插件内容页（`inTabbar` 且插件已启用）按 `order` 填；**超出容量进「更多」→ 推迟到阶段 3** |
| `App.vue` | 6 个 `v-if / v-else-if` 硬编码视图；`tab = computed(() => store.data.active_tab)` | `<component :is="page.component" v-bind="pageProps(page)" />` 动态渲染；跨页跳转从 `@goto-capability` 这种一次性事件换成统一的 `ui.goto(pageId)`。**`RecordsView` 收进对话页右上角 `⋯` 的 Sheet，`PortraitsView` 直接删掉**（活交给苍玄助手插件） |
| `stores/app.ts` | `setTab(id: TabId)` | `setTab(id: string)` + 「这个页面现在存在吗」校验；**关掉插件时若当前页是它的页，自动回落到第一个可用页** |

另外三条硬要求（不然会变成新的技术债）：

1. **一个脚本 = 一个文件**：苍玄助手在酒馆里是**一整段 JS**（现在 540 KB 的单脚本），`import()` 拆出的 chunk **没有任何人能加载**（webpack 的 `publicPath` 是空串，请求会打到酒馆页面 URL 上 404）→ 页面一律**静态 import**，阶段 3 加 `limitChunkCount = 1`，验收看「构建产物里不出现 chunk」。懒加载留给二期外部插件（那时才有独立 URL 可加载）。
2. **插件内容页的取数契约**：页面只拿得到 `host`（世界书/变量/存储/LLM/生图/HTTP/UI/**config**）+ 自己插件的 `plugins.<id>` 数据，**不许直接 import store**。跟「插件之间不许互相 import」是同一条规矩，否则页面也拆不掉。
3. **运行状态归宿主**：`● 运行中 · 第 N 轮`、底部 composer、通知条由 AppShell/宿主统一画；插件内容页不各画一份。

### 必须现在定的规则：顶栏容量

**现在只有 3 格**（对话 / 世界书 / 设置），容量问题暂时不存在；规则先留档，等真有第 3 个插件页再实现。

手机上药丸栏实际最多放 5 个。所以页面分两类：

- `inTabbar: true`（默认）：想上顶栏的页面（现在只有世界书）
- `inTabbar: false`：不占顶栏，从「设置 · 能力 · 插件 → 这个插件 → 它加了什么 → 页面」进（相册、语料库这类低频页）

超容量时的兜底顺序：核心页（对话 / 设置）永远常驻 → 插件页按 `order` 抢占剩余位 → 抢不到的收进 `⋯`（= 「所有页面」Sheet）。

**这两条（抢占 + ⋯）等真有第 3 个插件页再做**：现在实现是为假想需求写代码。
## 9. MCP 是什么：**「工具来源」的一种协议，本身就是一个插件**

底座里只有「工具」这一个概念。MCP 工具 = **远端声明的工具**：名字 / 说明 / 参数 schema 从 MCP server 的 `tools/list` 拿，调用转发到 `tools/call`。
所以底座**不需要为 MCP 增加任何概念**——这正是分层的价值。

MCP 插件（内置、默认关）负责：

- **连接管理**：服务器地址 / 请求头 / 鉴权 / 断线重连 / 超时
- **拉清单**：`initialize` + `tools/list` → 每个远端工具注册成底座 `ToolDef`，来源标 `MCP · <服务器名>`
- **转发调用**：`tools/call` + 结果/错误翻译成人话
- **页面**：服务器列表（一行一个：名字 / 地址 / 状态 / 开关 / `›`）→ 服务器页 = 它的工具清单
- **注册通道**：`manifest.tools` 是**静态**贡献；MCP 的工具是**运行时注册**（`registerRuntimeTools`，断开即撤销、失败只影响自己）。所以底座完全不知道「MCP」这个词 —— 这才是分层的价值。
- **停用**：只能在**来源**处停 —— 关服务器、或在服务器页逐条勾掉（存 `plugins.mcp.servers[].disabled_tools`）。「设置 · 能力 · 工具」段是只读视图，被停用的行标「已停用」。

MCP 三件套的映射（只做前两件，第三件二期）：

| MCP 概念 | 落在底座哪 | 第一期 |
|---|---|---|
| tools | 工具注册表 | 做 |
| resources | 先当只读工具（`read_resource`）暴露；以后可提成 host 数据源 | 做（只读） |
| prompts | 提示词块（`contributes.prompts`） | 不做 |

**分期与顺序（重要）**：

- 第一期内置只做 **HTTP / SSE**（浏览器能直连；CORS 挡了就填反代，跟生图插件同一个套路）。
- **stdio 需要本地小桥**（本机小进程或酒馆服务端）→ 二期，或者干脆不做；浏览器里生不出进程，这点要说实话。
- **MCP 应该排在「外部插件装载（URL / 粘贴 JS）」之前做**：MCP 让用户扩展能力，但**不加载别人的代码**，风险小一个数量级。先把「能扩展」用 MCP 打通，外部代码装载再慢慢来。

**风险（实话）**：远端工具的描述会进提示词（提示词注入面），调用会真的执行。全权装载、不做权限门禁这条不变，但要在界面上标清「来自远端」+ 能逐条停用，出问题用户能立刻关。

## 10. 技能：**留在底座**（跟工具是一对原语），但要做两件事

先按判据走一遍：没有技能，agent 照样跑得起来一轮 → 机械上讲它**可以**做插件。但**不建议**，原因是「原语 vs 内容」：

- 工具 = **可执行动作**；技能 = **按需加载的知识**。两者都是「模型能请求的东西」，是底座的一对原语。
  把它们都插件化，底座就只剩「发请求」，「模型能请求什么」这个抽象就没了。
- **工具的实现天然来自插件**（工具就是插件代码）；**技能的内容通常是用户自己的知识**，不属于任何插件 → 库必须留在底座。
- 技能插件化还有个副作用：跨插件的知识贡献没有统一入口，每个插件都要自己造一套「知识」概念。

所以：

1. 技能库 + `skill()` / `read_skill_file` 两个工具 → **底座**；
2. 技能库的**管理页**从独立页签挪进「设置 · 能力 · 技能」（跟「能力」并进设置是同一刀）；
3. 新增 `contributes.skills?: Skill[]`：插件可以**自带技能条目**（例如苍玄助手带「智绘姬输出格式」），跟插件一起开关。

| 页面注册表 | 底座 | 插件（`inTabbar` / `order`） |
| 提示词块 | **二期** | 插件（`contributes.prompts`）—— 本版删掉，跟钩子总线一起做 |
| 宏注册表 | 底座 | 插件（`contributes.macros`）；**注册 / 注销由底座做**，没有独立管理段 |
| 声明式设置表单 | 底座 | 插件（声明字段，宿主渲染） |
| 运行时工具注册 | 底座 | MCP 插件（`registerRuntimeTools`，断开即撤销） |
| 勾子总线 | 底座（二期） | 插件订阅 |
| 预设 | 底座 | 用户 + 插件提供的**模板**（入口贡献：导入即归用户，关插件不回收） |
| **MCP** | **插件** | — |

一句话：**底座有四张注册表（工具 / 技能 / 页面 / 宏）+ 一把设置；插件 = 往这几张表里贡献 + 声明自己的设置。MCP 是「用远端工具填工具表」的那一个插件。**
