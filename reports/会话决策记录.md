## 2. 立绘工具的确切形状（D6 + 用户 C4 回答）

用户原话：「c4 返回提示词，不要元数据，多个，我给过你提示词的 JSON 键」

### 工具形状

```
portrait_list              → 列出角色（名字 + 有没有图 + 来源）
portrait_prompt(names[])   → 批量读原生图提示词（支持一次多个名字）
```

- `portrait_meta` **删掉**（用户明确说「不要元数据」）
- `names[]` **支持多个**（批量提取）
- 只返回**提示词**，不返回元数据

### 「固定格式人物预设提示词」的 JSON 键（用户指的就是这个）

来源：`src/苍玄助手/presets/builtin.ts` 的 `ZHI_SKELETON`（智绘姬预设骨架）。
链路：`portrait_prompt` 读出 `char_caption`（角色DNA）+ `prompt`（完整提示词）
→ **LLM 转换**成下面这套键 → `write_file` 落盘。

```json
{
  "characters": {
    "[苍玄界]<中文名>": {
      "nameCN": "<中文名>",
      "nameEN": "<全小写拼音，空格分隔>",
      "characterTraits": "<2-5 个英文标签>",
      "facialFeatures": "<面部与发型>",
      "facialFeaturesBack": "<背面发型>",
      "upperBodySFW": "<上身>",
      "upperBodySFWBack": "<背面>",
      "fullBodySFW": "<下身>",
      "fullBodySFWBack": "<背面>",
      "upperBodyNSFW": "",
      "upperBodyNSFWBack": "",
      "fullBodyNSFW": "",
      "fullBodyNSFWBack": "",
      "outfits": ["[苍玄界]<服装名>"],
      "negative": "<角色负向词>",
      "generationContext": "",
      "generationVariables": {},
      "generationWorldBook": "",
      "mediaSchemaVersion": 2
    }
  },
  "outfits": {
    "[苍玄界]<服装名>": {
      "nameCN": "<服装名>",
      "nameEN": "<服装英文>",
      "owner": "<该角色的 nameEN>",
      "upperBody": "",
      "upperBodyBack": "",
      "fullBody": "",
      "fullBodyBack": ""
    }
  }
}
```

### 转换规则（智绘姬预设里已有的 `ZHI_RULES`，原文）

- 角色按身体部位拆成六个字段：facialFeatures / facialFeaturesBack / upperBodySFW / upperBodySFWBack / fullBodySFW / fullBodySFWBack。
- 背面字段若无法从正面立绘得知，可依据已有特征合理推断，不要留空。
- nameEN 必须是小写、以单个空格分隔的拼音；它同时是 outfits 中 owner 的取值。
- outfits 数组填服装键名，键名必须是 [苍玄界]<中文服装名>；服装条目另起一张表。
- 保留原始 NovelAI 权重语法（如 1.6::xxx::），不要转换成其他语法。
- 无法从 SFW 立绘推断的 NSFW 字段留空字符串，禁止编造。

### 智绘姬系统提示词（原文，`ZHI_SYSTEM`）

```
你要把一张立绘的元数据转换成「智绘姬」角色预设。

输入里的「角色DNA（char_caption）」是该角色最可靠的外观描述，请以它为准；
「完整提示词（prompt）」里的场景、构图、光影、画风词**不属于角色本身**，不要写进角色字段。

请逐个角色转换，严格遵守下面的 JSON 结构，只输出 JSON，不要输出任何解释性文字。
```

## 8. 存储形式（实测，不是读代码推的）

| 项 | 值 |
|---|---|
| 载体 | 酒馆助手**脚本变量**（`TavernHelper.getVariables` / `insertOrAssignVariables`） |

### ⚠️ 量级风险（真实，未排期）

| 块 | 现在 | 将来 |
|---|---|---|
| `presets` | 5.2 KB | 用户调预设 → 涨；多几个预设 → 线性涨 |
| `skills` | 1.5 KB | **`世界书工程` skill 正文 + 2 个参考文件 → 可能涨到 10-20 KB** |

**解法方向**：大块（`wb_backups`）换载体 → ST 真文件 `/api/files/`（阶段 7 已用过这条路）。

## 9. 「多余设计」自查（用户问：改动这么大，会不会有很多多余的设计）

| 块 | 判断 | 理由 |
|---|---|---|
| `sessions` + `session` | ⚠️ **可疑·双写** | `session` 是 v1 遗留（兼容读老数据），现在两处都写，容易不同步 |
| `turns` + `events` | ⚠️ **可疑·双写** | 注释说「turns 是读路径，events 是权威流」—— 同一份数据存两遍 |
| `artifacts` | ⚠️ **疑似死块** | 现在是空的；`makeArtifact` 的产物**存进这里但没消费** |
| `drafts` | ✅ 必要 | 草稿机制是核心 |
| `tool_overrides` | ✅ 必要 | 用户改提示词的落点 |
| `presets` / `skills` | ✅ 必要 | — |
| `wb_backups` | ⚠️ **量级不对** | 世界书整本塞进变量 |

**结论：确实存在多余设计**，集中在**双写**和**大块塞进小容器**两类。
