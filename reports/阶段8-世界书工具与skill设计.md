# 世界书工具与 Skill 设计（待评审）

> 目标：让一个**没读过手册的模型**也能正确写世界书。
> 现状问题：工具把世界书当「可读写的 JSON 文本」，而它是**关键词驱动的条件注入引擎** ——
> 模型写进去的条目常常**永远进不了 prompt**，而它自己不知道。

## 0. 真机实测（本文档的事实基础）

用一次性世界书 + ST 真实引擎（`checkWorldInfo(..., isDryRun=true)`）验的，**不是读文档推的**：

| 验证项 | 结果 |
|---|---|
| **order 方向** | ✅ 已证：`order=1` 的内容排在 `order=999` **前面** → 数值大的更靠近最新消息 |
| **死条目**（非常亮 + 无关键词） | ✅ 已证：5 条里只有它**任何消息都不激活**（`c5` 从未出现） |
| **有 key 就够，`selective` 无关** | ✅ 已证：`selective=true/false` 都激活；区别只在**有没有**次关键词 |
| **次关键词是硬门槛** | ✅ 已证：`key2=['副词']` 时，只说「触发词」**不激活**，说「触发词 副词」才激活 |
| `matchWholeWords` 默认 | ✅ 实测 `false`（A3 手册说默认开、对中文有害 —— **该说法在 v1.18 不成立**） |
| 当前环境 `world_info_depth` | 实测 **2**（不是手册说的 4；4 是 `DEFAULT_DEPTH`，即 position=4 时的默认深度） |

⚠️ **一个会咬人的实现细节**：`worldInfoCache` 会缓存整本书。改完磁盘上的书再试算，**必须 `worldInfoCache.delete(书名)`**，
否则读到的是旧版本 —— 我第一轮就因此得出「关键词条目不激活」的错误结论，差点写进设计里。
这条对 `wb_preview` 的实现是硬要求：**它必须先清缓存再试算**，否则 agent 自检会看到过期结果。

## 1. 设计原则（四条）

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **工具描述只讲「怎么用」，不讲「世界书是什么」** | 后者归 skill。工具描述压到 1–2 句，省下的 token 给 skill 用 |
| 2 | **读/搜结果必须带激活信息** | 模型看见「常亮 / 有关键词 / order=900」，才知道这条会不会生效；只给正文等于让它瞎猜 |
| 3 | **写工具默认产出「活」条目** | 既非常亮又无关键词 = 死条目。这种情况工具直接拒绝，而不是写完让用户发现没用 |
| 4 | **修改走一条路** | 现在改正文要 `entry_edit`、改属性要 `entry_meta`（还默认关着）。合成一个 |

## 2. 工具改动总表

| 现在 | 改后 | 变化 |
|---|---|---|
| `wb_list` | `wb_list` | 描述精简 |
| `wb_search` | `wb_search` | 命中结果带**激活状态** |
| `wb_read` | `wb_read` | 渲染时带**激活字段**，不只正文 |
| `entry_create` | `entry_create` | 全字段可选；**死条目拦截** |

| `entry_delete` | `entry_delete` | 描述精简 |
| — | **`wb_preview`** | **新增**：真引擎试算，这条到底会不会进 prompt |

净结果：7 → 7 个工具，但覆盖面从「能改正文」扩到「能改全部激活字段 + 能自检」。

## 3. 工具提示词全文（改后）

> 下面每条里的「模型描述」就是会进系统提示词的那段原文。

### 3.1 `wb_list` —— 列世界书

**模型描述**：

```
列出世界书，标出每本的生效范围（全局 / 角色卡 / 当前聊天 / 未启用）和条目数。
用户说「改世界书」但没指明哪本时，先用它确认 —— 动全局书会影响所有聊天。
```

**参数**：`in_scope_only`（只列本次可读写范围内的，默认 false）

### 3.2 `wb_search` —— 搜条目

**模型描述**：

```
按关键词找条目，返回 uid + 标题 + 命中处 + 激活状态（常亮 / 有关键词 / 已停用），不含全文。
定位到 uid 后用 wb_read 读全文。
```

**参数**：`keyword`（必填）、`worlds`、`limit`（默认 20）

**改动**：命中行从「uid + 标题 + 摘要」变成「uid + 标题 + 激活状态 + 摘要」。模型一眼能看出这条是死是活。

### 3.3 `wb_read` —— 读条目

**模型描述**：

```
读条目全文。给 uids 读指定几条；不给就分页读整本。
返回里带激活字段（常亮/关键词/order/position/depth）—— 它们决定这条会不会进 prompt，改之前先看。
```

**参数**：`world`、`uids`、`offset`、`limit`、`max_content`

### 3.4 `entry_create` —— 新建条目

**模型描述**：

```
新建条目。必须二选一让它能激活：给 keys（关键词触发）或 constant=true（常亮）——
两者都不给就是死条目，工具会拒绝。其余字段可选，不填用默认值。
```

**参数**（全部可选，除 name / content）：
`world` `name` `content` `constant` `keys` `keys_secondary` `order` `position` `depth` `scan_depth` `probability` `group` `group_weight` `match_whole_words` `enabled`

（**不含 `selective`**：实测它不影响激活判定，暴露给模型只会诱导它乱设。）

**改动**：原来允许建死条目；现在拦。

### 3.5 `entry_update` —— 改条目（新，合并 `entry_edit` + `entry_meta`）

**模型描述**：

```
改一条条目：world + uid 必填，其余字段填了才改、不填原样不动。
改正文两种方式：old_string + new_string 精确替换（推荐，改动小不易误伤）；或直接给 content 整条替换。
```

**参数**：

| 参数 | 说明（会进 schema） |
|---|---|
| `world` | 世界书名；不填 = 本轮只选中一本时用那本 |
| `uid` | **必填**。要改的条目 uid |
| `old_string` + `new_string` | 精确替换正文里的一段 |
| `content` | 整条替换正文（和上面二选一） |
| `name` | 新标题 |
| `enabled` | 启用 / 停用 |
| `constant` | true=常亮；false=改为关键词触发 |
| `keys` | 触发关键词（整组替换） |
| `keys_secondary` | 次关键词 { logic, keys } |
| `order` | 顺序。**越大越靠近最新消息** |
| `position` | 插入位置 0–7 |
| `depth` | 仅 position=4 有意义 |
| `scan_depth` | 扫描深度，或 same_as_global |
| `probability` | 命中后插入概率 0–100 |
| `group` / `group_weight` | 互斥分组：同组只插一条 |
| `match_whole_words` | 全词匹配。**中文保持关闭** |

### 3.6 `entry_delete` —— 删条目

**模型描述**：

```
删一条条目。uid 必填；expect_name 填了就要求实际标题一致，防删错。
```

### 3.7 `wb_preview` —— 试算激活（新增）

**模型描述**：

```
拿真实引擎试算一次：给几条试探消息，返回这一轮真正会进 prompt 的条目、各自从哪个位置进、
以及哪些没进来。写完条目用它自检 —— 界面显示「已保存」不等于它会生效。
```

**参数**：`world`（不填=范围内全部）、`messages`（试探文本数组）、`budget`（上下文预算，默认当前设置）

**实现**：调 ST 的 `checkWorldInfo(chat, maxCtx, isDryRun=true)` —— 已在真机验证可行，不改聊天状态。

### 4.1 元信息

|---|---|

| name | 世界书工程 |

### 4.2 正文（`body`）

```markdown
# 世界书工程

## 一句话心智模型

世界书不是文档，是**条件注入引擎**：每轮生成前，酒馆扫描最近的聊天记录，按关键词/常亮/滤镜挑出条目，
按 position + order 插进 prompt，最后受 token budget 裁切。
**它只保证内容进上下文，不保证模型会照做。**

## 一、决定「能不能进 prompt」的字段

| 字段 | 作用 | 默认 |
|---|---|---|
| 激活方式 | 常亮（无需关键词）/ 关键词 / 向量化 | 关键词 |
| keys | 触发词，逗号分隔，支持 /正则/ | 空 |
| keys_secondary + logic | 次关键词**硬门槛**：设了就要求同时命中，否则本条不激活 | 无 |
| enabled | 关掉 = 完全不参与 | true |
| position | 0 角色定义前 / 1 角色定义后 / 2 AN顶 / 3 AN底 / 4 指定深度 / 5-6 示例消息前后 / 7 命名插槽 | 1 |
| depth | 仅 position=4 有意义：插在倒数第几条消息 | 4 |
| order | 同位置内的先后。**越大越靠近最新消息** | 100 |
| probability | 命中后有多少概率真的插入 | 100 |
| scan_depth | 只扫最近多少条消息 | 跟随全局 |

**最常见的死条目**：既不是常亮，又没写 keys —— 它永远不进 prompt。写完必查这一条。

（顺带一个已实测的坑：`selective` 这个旧字段**不影响**激活与否 —— 有 key 就会匹配，`true`/`false` 都一样。
但**次关键词是硬门槛**：一旦填了 `keysecondary`，主键和次键**都**命中才会激活。不确定就别填。）

## 二、三个反直觉的点（错了会白写）

1. **order 越大越靠近最新消息。**
   酒馆按 order 降序排完再往数组头部插，所以 order 大的离当前对话更近、影响更强。
   「重要规则要放前面」在这里对应的是 **order 小**。

2. **常亮条目先吃 token budget。**
   budget 默认占上下文窗口的 25%。耗尽了，后面关键词命中也**不再插入**。
   一堆常亮条目会把预算吃光，让所有关键词条目一起失效。

3. **中文条目不要开「全词匹配」。**
   它按 \W 划词边界，对没有词间空格的中文不可预期。默认是关的，别去开。

## 三、工具怎么配合用

| 要做什么 | 用哪个 |
|---|---|
| 不知道改哪本 | `wb_list` —— 看生效范围 |
| 有关键词、找 uid | `wb_search` |
| 读全文 / 看激活字段 | `wb_read` |
| 加新条目 | `entry_create` |
| 改已有条目（正文或属性） | `entry_update` |
| 删条目 | `entry_delete` |
| **确认它真的会进 prompt** | `wb_preview` |

## 四、什么时候用哪种激活方式

| 内容类型 | 激活方式 |
|---|---|
| 世界基本设定（地理、势力、核心规则） | **常亮** —— 每轮都要在 |
| 具体人物 / 地点 / 道具的详细设定 | **关键词** —— 提到才需要 |
| 随机事件、天气、偶遇 | **关键词 + probability < 100** |
| 一次性状态（受伤、下雨） | **关键词 + sticky / cooldown** —— 持续 N 条消息后自动退场 |
| 同一槽位的互斥内容（今天下雨 / 今天晴天） | **关键词 + 同组 group** —— 同组只插一条 |

## 五、写完必做的自检

1. 这条能激活吗？常亮 or 有关键词，二者必居其一。
2. 关键词是用户/角色**真会说到**的词吗？写「天剑宗」比写「剑」好。
3. 想让它更靠近当前对话（影响更强）→ 调大 order。
4. 如果加的是常亮条目，想想会不会把 budget 吃紧。
5. 用 `wb_preview` 试一句含关键词的话，确认它真的进来了。
```

### 4.4 参考文件 2：`范式模板.md`

```markdown
# 五个可直接套用的范式

## 1. 随机事件

常亮会让事件每轮都出现；用关键词 + 低概率：

- keys: 探索, 前进, 出发
- probability: 15
- content: 一段「投骰子」描述，让模型从几种结果里挑

## 2. 互斥回退序列

同一个槽位（比如「今天的天气」）准备几条，同组只插一条：

- 三条都设 group: weather
- 想要确定性顺序就设 groupOverride + 不同 order
- 想要加权随机就设 groupWeight（相对权重，100 vs 300 = 75% 概率）

## 3. 状态机（一次性状态）

「受伤」这类状态：激活后持续几轮再自动退场。

- keys: 受伤, 中箭, 吐血
- sticky: 3 —— 激活后强制持续 3 条消息
- cooldown: 10 —— 退场后 10 条内不再激活

注意：单位是**消息数**不是回合数；手动改条目会清掉正在计时的效果。

## 4. 递归链

A 的正文里提到 B 的关键词 → B 被激活 → B 的正文里提到 C → C 被激活。

- 需要全局开启递归
- 用 Max Recursion Steps 或 Min Activations 控制深度（两者互斥）
- 不想让某条参与：preventRecursion（不被别人触发）/ excludeRecursion（不触发别人）

## 5. 条件组合（次关键词）

「只有同时提到天剑宗和掌门时才触发」：

- key: 天剑宗
- keysecondary: 掌门, 首座
- selectiveLogic: 0 (AND_ANY) —— 主键命中 + 次键命中任一

**主键命中是所有模式的共同前提**，次关键词只能再收紧、不能单独触发。
```

## 6. 需要你拍板的三点

### ① `entry_edit` + `entry_meta` 是合并还是保留？

- **方案 A（我推荐）**：合并成 `entry_update`。工具少一个，模型不用先判断「我要改的是正文还是属性」。
- **方案 B**：`entry_update` 只做属性，`entry_edit` 保留做正文精确替换。
  好处是精确替换的**安全约束**（禁止整条重写）保持独立；坏处是模型要二选一。

你说的「添加一个修改工具，给 uid、所有内容可选」我按 **A** 理解的。

### ② `entry_update` 允许整条替换正文吗？

- 允许（按你的要求「所有内容可选」）—— 但 `content` 和 `old_string/new_string` 二选一，且草稿里照常出 diff。
- 风险：模型可能偷懒整条重写，把没注意到的细节改掉。
- 缓解：描述里写「推荐精确替换」；草稿 diff 会显示全貌，用户点保存前看得见。

### ③ 高级字段（probability / group / sticky / cooldown / match_whole_words）要不要全进 schema？

- **全进**：模型有能力做复杂设计，但 schema 变长（约 +300 token）。
- **只进常用的**（probability / group）：其余写进 skill，需要时……但**模型没法用工具设置它们**。
- 我倾向**全进**：这几个字段正是「设计世界书」和「改文本」的分界线。
