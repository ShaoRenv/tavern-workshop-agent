## 1. 世界书是什么

**一句话**：世界书是一本**按关键词查表**的设定字典。平时不占 prompt，只有当聊天里出现某个词，对应那条设定才被塞进 AI 的上下文。

**它为什么被发明**：角色卡上的 `description` 是**永远在场**的 —— 写多少就每轮都花多少 token。但一张卡的世界观、几十个角色、几十个地点、几百条规则，全塞进 description 会撑爆上下文。

世界书把「设定」变成**按需加载**：

| | 角色卡 description | 世界书 |
|---|---|---|
| 在场时机 | 每轮都在 | 命中关键词才在 |
| 容量 | 有限，写多了每轮都贵 | 理论上无限 |
| 适合 | 主角人设、开场、核心语气 | 世界观、配角、地点、规则、表格 |

> 出处：手册 §1「World Info 是动态字典，仅当关键词出现在扫描缓冲区时才将对应条目内容插入 prompt」
> 置信度：high `[文档·多源]`

**它保证什么、不保证什么**：只保证内容**进入了**上下文，**不保证模型一定照着写**。
> 出处：手册 §1「仅保证内容进入 context，不保证模型遵循」

## 2. 人拿世界书干什么（从真实数据反推）

我扫了 14 本书 1788 条，按**用途**归类，这是真实存在的用法：

| 用途 | 真实例子 | 典型配置 |
|---|---|---|
| **世界观/设定总览** | 「世界观总览」902 字 | 蓝灯，pos=0（角色定义前） |
| **角色档案** | 「江念」1601 字 keys=`["江念","无情道弟子"]` | 绿灯，按角色名触发 |
| **地点档案** | 「剑临城」402 字 keys=`["剑临城","坊市","东城"]` | 绿灯 |
| **规则/系统** | 「战力体系规则」2679 字、「经济体系规则」2026 字 | 蓝灯 |
| **变量更新规则** | 「[mvu_update]变量更新规则」4766 字 | 蓝灯，pos=4（贴近最新消息） |
| **CG/插画触发** | 「[mvu_plot]沈慕微CG触发」921 字 keys=`["沈慕微"]` | 绿灯，pos=4 |
| **宏注入（极短）** | 「线上微信历史」**17 字**，内容就是 `{{PHONE_HISTORY}}` | 蓝灯 |
| **生图 tag 表** | 「明日方舟」1631 字 角色↔tag 对照 | 蓝灯，pos=4 depth=1 |

**关键观察**：世界书早就不只是「设定库」了。真实用户拿它当**宏的挂载点**、**状态栏的模板**、**数据库的表头**、**生图 tag 的索引**。它是**往 prompt 任意位置注入任意文本的通用管道**。

## 3. 最重要的发现：人类用「命名约定」给扁平列表分区

世界书编辑器是**一个扁平列表**（219 条排在一起）。真实制卡人自己发明了分区办法：

```
====核心规则====_开始          ← 蓝灯，7 字，无关键词
世界观总览                      ← 蓝灯
世界引擎                        ← 蓝灯 pos=4
故事基调                        ← 蓝灯
对话格式硬性规则                ← 蓝灯
====核心规则====_结束          ← 蓝灯，9 字
====角色设定====_开始          ← 蓝灯，7 字
江念                            ← 绿灯 keys=["江念","无情道弟子"]
沈慕微                          ← 绿灯 keys=["沈慕微","无情道首座"]
…
====角色设定====_结束          ← 蓝灯，9 字
```

「苍玄界」这张卡里有 **18 个这样的分节标记**。还有**语义前缀约定**：

| 前缀 | 含义 | 实例 |
|---|---|---|
| `[mvu_update]` | 变量更新相关 | `[mvu_update]变量更新规则` |
| `[mvu_plot]` | 剧情/CG 触发 | `[mvu_plot]沈慕微CG触发` |
| `====xxx====_开始/_结束` | 分节标记 | — |

**这对工具设计的含义（重要）**：
- ❌ 我上一版设计「分页读整本」——**对 219 条的书毫无意义**，人不需要第 1-20 条
- ✅ 人需要的是**看清结构**：有哪些节、每节多少条、哪些条目是骨架、哪些是内容
- ✅ 工具必须**理解并尊重**这些命名约定，不能把它们当普通条目

## 4. 两套字段名 —— 我上一版设计的根本性错误

**同一个概念，两套完全不同的字段名。**

### 独立世界书文件（`data/default-user/worlds/*.json`）

```json
{ "uid": 1, "comment": "世界观总览", "key": [], "keysecondary": [],
  "constant": true, "selective": false, "selectiveLogic": 0,
  "order": 1, "position": 0, "depth": 4, "role": 0,
  "disable": false, "displayIndex": 1, "probability": 100, … }
```
**43 个字段**（我实测统计）。

### 卡内世界书（V2 spec `character_book`）

```json
{ "id": 1, "comment": "世界观总览", "keys": [], "secondary_keys": [],
  "constant": true, "selective": false,
  "insertion_order": 1, "position": "before_char", "enabled": true,
  "use_regex": true,
  "extensions": { "position": 0, "depth": 4, "role": 0,
                  "probability": 100, "selectiveLogic": 0,
                  "exclude_recursion": true, "display_index": 1, … } }
```
**12 个顶层字段 + 32 个 extensions 子字段**，命名是 **snake_case**。

### 对照表

| 概念 | 独立文件 | 卡内 V2 |
|---|---|---|
| 唯一标识 | `uid` | `id` |
| 标题 | `comment` | `comment` ✅同 |
| 主关键词 | `key` | `keys` |
| 次关键词 | `keysecondary` | `secondary_keys` |
| 启用 | `disable`（**反义**） | `enabled` |
| 顺序 | `order` | `insertion_order` |
| 插入位置 | `position: 0-7`（数字） | `position: "before_char"`（字符串）+ `extensions.position: 0`（数字） |
| 其余字段 | 顶层平铺 | 塞进 `extensions`，snake_case |

**结论**：**我们插件现在只支持独立文件那一套**（`core/native.ts` 走 `loadWorldInfo`/`saveWorldInfo`）。
如果用户让 agent 改「卡里自带的世界书」，现有设计**会写坏数据**。这是一个**待你定的范围问题**（见设计稿 Q1）。

## 5. 真实字段使用统计（1788 条实测）

| 字段 | 出现次数 | 真实取值样本 |
|---|---|---|
| `comment` / `content` / `constant` / `key` / `keysecondary` / `order` / `position` / `selective` / `uid` | 1788（全部） | — |
| `depth` | 1788 | 4(1399) 2(167) 0(88) 1(77) **10000(26)** 999(17) |
| `disable` | 1788 | false / true |
| `addMemo` `caseSensitive` `cooldown` `delay` `delayUntilRecursion` `displayIndex` `excludeRecursion` `group` `groupOverride` `groupWeight` `match*` `preventRecursion` `probability` `role` `scanDepth` `selectiveLogic` `sticky` `useGroupScoring` `useProbability` `vectorized` | 1784 | 见下 |
| `ignoreBudget` `outletName` `triggers` | 997 | 部分书有 |

**⚠️ `extra` 字段是真实的**：45 条条目带 `extra`，来自第三方工具（`module_id`/`source` = 模块导入；`cw_*` = 创意工坊）。**如果我们的写入丢了这个字段，就等于毁掉用户的导入溯源信息。**

## 6. 「死条目」—— 真实存在，但要区分故意和失误

**定义**：非常亮 + 无关键词 + 非向量 = **任何消息都不会激活它**。

实测只找到 **4 条**：

| 书 | 标题 | 判断 |
|---|---|---|
| 苍玄界 (3) | `====CG系统====_开始 [mvu_plot]` | ✅ **故意** —— 分节标记 |
| 苍玄界 (3) | `====CG系统====_结束 [mvu_plot]` | ✅ **故意** —— 分节标记 |
| 苍玄界 | `USER档案` | 已 `disable=true`，无害 |
| 苍玄界 (3) | `[mvu_plot]红CG触发` | ❌ **真 bug** —— 其他 15 条 CG 触发都有 keys，只有它丢了 |

**所以「死条目检测」有真实价值**，但工具必须能区分「故意的骨架」和「忘填关键词」。

## 8. 已经实测确认的机制（真机验过，不是读文档）

| 结论 | 状态 |
|---|---|
| `order` 越大越靠近最新消息 | ✅ 真机验过（order=1 排在 order=999 前） |
| 死条目（非常亮+无关键词）任何消息都不激活 | ✅ 真机验过 |
| `selective` 字段**不影响**激活判定 | ✅ 真机验过 |
| **次关键词是硬门槛** | ✅ 真机验过 |
| `matchWholeWords` 默认 **false** | ✅ 真机验过（TavernWeave 手册说默认开 = **错的**） |
| 当前环境 `world_info_depth` = **2** | ✅ 真机验过（4 是 `DEFAULT_DEPTH`，不是当前值） |
| ⚠️ `worldInfoCache` 缓存整本书，改完磁盘必须 `worldInfoCache.delete(书名)` | ✅ 踩过坑 |

**人类手册自己承认的悬案（§21，U1-U11）**—— 哪些影响我们做 agent：

| 悬案 | 对我们的影响 |
|---|---|
| **U1** AND_ALL 激活门槛（getScore 返回非 0，与文档矛盾） | 🔴 直接影响 —— 我们判断「这条会不会触发」可能判错 |
| **U2** NOT_ANY/NOT_ALL 实现位置未定 | 🔴 直接影响 —— 同上 |
| **U4** 分组竞争后被 probability 淘汰是否补位 | 🟡 间接（真实数据没人用 group） |
| **U5/U6** 同 depth 多 role 顺序 / depth 超长行为 | 🟡 影响我们解释「注入到哪」 |
| U3/U7/U8/U9/U10/U11 | 🟢 影响小 |

## 9. 我现在对「好世界书 / 坏世界书」的理解

**好**：
- 骨架清晰（分节、命名一致）
- 蓝灯只放真正必须常驻的（世界观、核心规则、变量规则）
- 绿灯按「实体名」触发（角色名、地名），关键词**专指**
- 单条聚焦一个实体，长度可控（实测主流是 200-1000 字）
- 内容自洽：光看这一条，模型能懂

**坏**：
- 扁平一坨，没有分区
- 蓝灯泛滥（274/296）→ 预算被吃光，绿灯挤不进来
- 关键词用单字（「历」「红」）→ 到处误触发
- 同一条塞进多个实体 → 触发一个带出一堆
- 忘填关键词（死条目）→ 写了等于没写
