**位置**

- `src/苍玄界立绘工坊/core/llm_extract.ts:160-163`（`{}` 本身就是合法 JSON，直接 `ok: true`）
- `src/苍玄界立绘工坊/llm/engine.ts:153-166`（`consume`：`outcome` 非 null 即算成功）
- `src/苍玄界立绘工坊/core/merge.ts:124-130`（`{}` 的 `Object.entries` 迭代 0 次，**连一条 warning 都不产生**）

### M-1 `runPortraitBatches` 在"最后一批被中止"时返回 `aborted: false`，界面会把取消显示成"完成"

**位置**：`src/苍玄界立绘工坊/llm/engine.ts:168-227`

**最小复现**

```ts

const res = await runPortraitBatches({
  roles: [{ name: 'A', metaText: 'x', imageUrl: '' }],
  preset: { ...presetWithBatch1Retries2, batch_size: 2, max_retries: 2 },

  generate: async () => { signal.aborted = true; throw new Error('user cancel'); },

console.log(signal.aborted, res.aborted);   // 实际：true false   期望：true true
```

实测输出：`E5 signal.aborted => true` / `E6 result.aborted => false` / `E7 failures => [{"name":"A","error":"user cancel"}]`

影响：`stores/workshop.ts:394` 因此走 `'完成：...'` 分支而不是 `'已中止。'`；用户在"停止"之后看到的是任务完成。现有测试 `engine.test.ts:169-188` 只覆盖了"4 批、第 1 批后中止"（此时还有下一轮循环兜住），所以没有暴露。

**建议修法**：把中止判定收敛成一个 `const isAborted = () => signal?.aborted === true`，在批次重试循环、降级循环每一轮前都检查，并在每次跳出批次循环后立即补 `if (signal?.aborted) aborted = true`（或在批次循环结束后统一补 `aborted = signal?.aborted ?? false`）。

### M-6 降级路径把重试预算乘了一轮：同一批最坏 `(batch_size + 1) × (max_retries + 1)` 次调用

**位置**：`src/苍玄界立绘工坊/llm/engine.ts:185`（整批 `max_retries+1` 次）与 `:198-221`（逐角色，每个角色再来 `max_retries+1` 次）

**实测调用次数**（用计数型假 generator）

```ts
// batch_size=2, max_retries=2, 4 个角色（2 批）→ 实测 E1 => 18 次（每批 3 + 2×3 = 9 次）
// batch_size=4, max_retries=2, 4 个角色（1 批）→ 实测 E4 => 15 次 = (4+1)×(2+1)
```

结论：单批最坏调用 = `(batch_size+1) × (max_retries+1)`。内置预设 `batch_size`：智绘姬 4、小白x 6，`max_retries` 默认 2 → 失败时单批分别 15 / 21 次；若选中 100 个角色（小白x，17 批）全部走最坏路径 ≈ **357 次生成**。当模型侧持续失败（额度用尽/超时），这会成倍放大等待时间与 token 消耗，而用户看到的只是"多次重试后仍失败"。

**建议修法**：降级到逐角色时把重试预算降级（例如 `min(max_retries, 1)` 或 0，因为单角色请求本身已经是最小单位）；或给整次任务加一个总调用预算 `max_total_calls`，超预算即中止并明确报告"已触发调用预算保护"。UI 上把"本批已调用 N 次"透出。

## 已验证无问题（同样是审查产出）

1. **`findBalancedJson` 对英文撇号（ISO JSON）是正确的**——这是任务点名的重点。
   `findBalancedJson('{"a": "it\'s fine"}', 0)` → 实测返回整段 `{"a": "it's fine"}`。
   理由：撇号只在 `inString === false` 时才被当作开引号；处在双引号字符串内部时（`llm_extract.ts:43-53`）直接被忽略，不会提前闭合。并且**扫描起点永远是 `{` / `[`**（`findFirstBalanced:125-128`、标签定位），所以正文里的撇号不在扫描区间内，也不影响配平。经 `extractJson` 端到端实测：`labeled_brace` 模式下 `JSON{"name": "O'Brien", "x": 1}` → 正确解出；`fenced` 模式、`whole` 模式同样正确。
   风险只存在于单引号分隔的 JSON（见 L-1），而那是非标准 JSON，且当前"返回 null 报错"比"被 jsonrepair 改坏"更安全。
2. **A1111 的 `Model hash: abc, Model: x` 切分正确**：实测 `{"model_hash":"abc123","model":"xyz"}`，键归一化（小写+空格转下划线）也对。问题只在"值内含逗号"（M-2）。
3. **`merge` 的 `overwrite` 保留小白x 原 id 是有意设计，与"换角色"不冲突**：匹配依据是 `name`（`:231`），保留 id 是为了不破坏插件按 id 建立的引用，`merge.test.ts:127-137` 已作为契约断言；`rename` 会生成新 id（实测 `char-1-bbbb`）并追加新条目，语义分工清楚。真正需要修的是 M-3/M-4，不是保留 id 本身。
4. **`getByPath` 的常用路径全部正确**（probe1 实测）：
   `a[0].b → 1`；`a[*].b → [1,2]`（`toDisplayText` → `"1, 2"`）；`v4_prompt.caption.char_captions[*].char_caption → "A, B"`；`[*]` 作用在非数组上返回 `undefined` 而不抛异常（与 `extractFields` 的"未命中→记入 missing"配合正确）；单元素通配返回标量、`resolveTokens` 过滤空串，都是无害的展示层差异。越界词法见 L-14（是限制，不是回归）。
5. **`png_meta` 的块遍历与三种文本块解析正确**（probe11 用**合成 PNG** 覆盖了真实 fixture 覆盖不到的分支）：
   坏 CRC 被忽略（按设计不校验）；`tEXt` 正常；`zTXt`（keyword + NUL + 方法字节 + deflate）实测解出 `"NovelAI"`；`iTXt` 压缩（flag=1）与未压缩两条路径分别解出 `"压缩中文提示词"` / `"纯文本标题"`；keyword 无 NUL 的块被跳过；`offset = dataEnd + 4`（跳过 4 字节 CRC）算术正确；长度字段被改大 → 返回空数组不抛异常；截断 5 字节 → 仍解出前 4 块；非 PNG → 空数组。全部 100 个测试通过，`parseTextChunk` 的 `catch {}`（`:86`）是"单块失败不影响其他块"的设计意图，判断为**必要**。
6. **`chunkRoles` 的非法批大小处理正确**：`batch_size = 0 / NaN` 实测都退化为逐个（`Math.max(1, Math.floor(batchSize) || 1)`），与 `engine.test.ts:51` 一致。
7. **`nextAvailableKey` 有 1000 次上限**（`merge.ts:60-64`），不会死循环；用满后回落到时间戳后缀，行为安全（与 L-11 的 `while` 形成对照）。
8. **引擎正常路径的计数逻辑正确**：`completed` 只在 `consume` 成功时推进、失败降级后不推进；`emit` 快照 `failures/logs` 不共享引用；`skipNames` 续跑只发未跳过的角色（`engine.test.ts:148-167` 通过）；整批路径重试次数 = `max_retries + 1`（实测 `max_retries=0`→1 次，`=2`→3 次）。
9. **世界书引擎的文本/JSON 两种产出正确**：`output_json_path` 命中时取到字符串、`initialText` 续跑保留既有产出、失败批次按角色记录——仅在路径失配时错误信息不可读（L-9）。
10. **`catch {}` 清单的总体判断**（任务第 6 点）：`json_util.ts:6/87`、`png_meta.ts:86`、`statusbar_scrape.ts:41`、`gallery_source.ts:52/57/62/143`、`workshop.ts:88/413/422` 均为**必要**的容错（不可信输入 / 跨域探测 / 非关键清理），不影响正确性；**不必要或不足**的是 `llm_extract.ts:91`（掩盖用户正则错误）、`engine.ts:235`（静默禁用 JSON Schema）、`gallery_source.ts:80`（静默空图库）、`workshop.ts:91-92` 组合（静默丢用户数据，见 M-5）。
