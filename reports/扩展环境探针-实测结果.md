# 扩展环境探针 · 实测结果

> 真机环境：SillyTavern 1.18.0（C:\SillyTavern-1.18.0，http://127.0.0.1:8000，pageId 2）
> 探针扩展：data/default-user/extensions/cx-probe/（manifest.json + index.js + style.css，最小实现）
> 已装扩展：**JS-Slash-Runner（= 酒馆助手本体）**、ST-Prompt-Template、yuzuki-phone

## 0. 方法说明（决定结论可信度，务必先读）

本机**装有 JS-Slash-Runner（JSR，即「酒馆助手」）**，它会在页面加载时执行 `globalThis.TavernHelper = getTavernHelper()`。
因此所有 P-bridge 结论都分两层给出：

- **【A 层】当前环境的真实可得性** —— 本机装有 JSR。回答「在装了酒馆助手的酒馆里，我们的扩展能不能跑」。
- **【B 层】剥离酒馆助手后的裸扩展能力** ← **决定迁不迁的关键**。用两种独立方法交叉验证：
  1. **静态溯源**：直接读 JSR 的 TypeScript 源码（本机带完整 src/），看每个接口是**包装 ST 原生**还是**JSR 自造**。
  2. **运行时遮蔽**：在页面上把 `window.TavernHelper` 临时置为 `undefined`，重测各接口，测完立即还原（已确认还原成功）。**未卸载/未禁用 JSR**，用户环境无破坏。


**关键：`window.getVariables / generateRaw / triggerSlash` 从来就不在 window 上**（A 层同样是 `undefined`）。
它们**只在 `window.TavernHelper` 这一个对象里**，而该对象 100% 由 JSR 组装（见 `src/function/index.ts:447`）。

## P-bridge：21 个酒馆助手接口的可得性

### 【结论】A 层 —— 装了酒馆助手时

21 个接口**全部可得**（`typeof === 'function'`）。探针返回：

| 接口 | TavernHelper.X | window.X | getContext().X |
|---|---|---|---|
| getVariables / replaceVariables | function | undefined | undefined |
| getWorldbook / createWorldbook | function | undefined | undefined |
| getScriptTrees | function | undefined | undefined |
| generateRaw / generate | function | undefined | **function** |
| registerMacroLike | function | undefined | undefined |
| substitudeMacros | function | undefined | undefined |
| triggerSlash | function | undefined | undefined |
| getModelList | function | undefined | undefined |
| getChatMessages / setChatMessages | function | undefined | undefined |
| getCurrentCharPrimaryLorebook / getLorebooks | function | undefined | undefined |
| getScriptId | **undefined** | undefined | undefined |
| insertOrAssignVariables 等 | function | undefined | undefined |

> 注意 `getScriptId` 在**主页面**为 `undefined`——它被设计为**只能在脚本 iframe 内**取用（src/function/util.ts:97-103 明确 throw 非 TH-script-- 前缀）。这不是安装缺失，是设计如此。扩展形态下该接口**语义无对应物**。

【证据】evaluate_script on pageId 2，返回上方表格；且 `typeof window.TavernHelper === 'object'`。

【对底座设计的影响】A 层说明：**底座今天能跑，完全是因为玩家装了 JSR**。扩展形态若沿用「直接调 TavernHelper」，等于把 JSR 变成硬依赖——这跟「迁到原生扩展」的初衷矛盾。

### 【结论】B 层 —— 裸扩展（无酒馆助手）→ **这是决定性的**

**静态溯源结论：21 个接口中，没有任何一个由 SillyTavern 原生提供。全部是 JSR 在自己进程里组装的。**

决定性证据 1 —— 接口清单完全是 JSR 手写对象（JS-Slash-Runner/src/function/index.ts:195-449）：

```ts
function getTavernHelper() {           // ← 手工枚举 200+ 个字段
  return { getChatMessages, setChatMessages, generateRaw, generate, triggerSlash, ... };
}
export function initTavernHelperObject() {
  globalThis.TavernHelper = getTavernHelper();   // ← 只此一处注入
}
```

决定性证据 2 —— 逐个溯源，**JSR 接口的底层全部落在 ST 原生 API 上**，即：JSR 是**薄封装层**，不是黑魔法。

| 底座接口 | JSR 底层实现 | 底层是 ST 原生吗 | 裸扩展能否自己拿到 |
|---|---|---|---|
| triggerSlash | executeSlashCommandsWithOptions（src/function/slash.ts:1-8，整个函数体只有 8 行） | ✅ 是 | **能**，1:1 直取 |
| substitudeMacros | substituteParamsExtended（src/function/util.ts:9-11，3 行） | ✅ 是 | **能**，1:1 直取 |
| registerMacroLike | ST 的 MacrosParser.registerMacro（src/macro.ts）+ getContext().registerMacro | ✅ 是 | **能**，用 getContext().registerMacro |
| generateRaw | 自己重写整套 prompt 组装（src/function/generate/generateRaw.ts **19KB**），但依赖 ST 原生 ChatCompletion/oai_settings/PromptManager；且 ST **原生就有** getContext().generateRaw | ⚠️ **ST 有同名原生函数**（实测 typeof ct.generateRaw === 'function'） | **能（同/近语义）**，直接用 ct.generateRaw 或 /genraw |
| generate | 同上 | ✅ ST 原生 getContext().generate 存在 | **能** |
| getChatMessages / setChatMessages | 直接读写 chat 数组、chat_metadata | ✅ 是，getContext().chat（MUTABLE） | **能**，但需自己写楼层存取逻辑 |
| getVariables / replaceVariables | 分 message/chat/character/preset/global 五种作用域，读 chat[i].variables 与 extension_settings（src/function/variables.ts，10KB） | ⚠️ ST **有** getContext().variables，但语义/作用域与 JSR 的**不完全一致** | **部分能**，需自己补作用域逻辑 |
| getWorldbook / createWorldbook | 封装 ST 世界书 | ✅ ST 原生有 loadWorldInfo/saveWorldInfo/getWorldInfoNames/updateWorldInfoList | **能**（见 P-worldbook） |
| getModelList | 读 ST API 配置 | ⚠️ 未逐一溯源 | 未证实 |
| getScriptTrees / getScriptId | **JSR 自己的「脚本」概念**（脚本树、脚本 iframe） | ❌ **ST 完全没有这个概念** | **不可得**，扩展形态无对应物 |
| errorCatched / getLastMessageId | JSR 自造（依赖 toastr） | ⚠️ 自造但易复刻 | 可自实现 |

【证据】
- 静态：src/function/index.ts:195-449（getTavernHelper 全量字段清单）、src/function/slash.ts、src/function/util.ts:9-11、src/function/generate/generateRaw.ts 文件大小 19373 字节。
- 运行时：B 层遮蔽测试返回 TavernHelper: "undefined" 而 SillyTavern: "object"；同时 bare_ctx_keys_present 列出 **22 个**候选函数全部仍在。

【对底座设计的影响 —— 这是本次探针最重要的结论】
1. **不存在「ST 原生提供 TavernHelper.xxx」这件事。** TavernHelper 是 JSR 的**私有命名空间**。任何直接 TavernHelper.xxx 的调用，在裸扩展里**一律 undefined → TypeError**。
2. **但风险比预想低得多**：JSR 自己也不是从零实现的——它是 ST 原生 API 的薄封装。底座改走 SillyTavern.getContext() 后，**大部分能力可以 1:1 或近 1:1 直取**，无需复刻 JSR 的 19KB generateRaw 逻辑。
3. **真正在裸扩展里「拿不到」的是两类**：
   - **(a) 概念性缺失**：getScriptTrees / getScriptId / replaceScriptTrees —— ST 没有「脚本树」概念，这是 JSR 独有的脚本管理模型。**底座若依赖脚本树做多脚本编排，扩展形态必须自建。**
   - **(b) 语义不完全对齐**：getVariables 的五作用域变量模型（message/chat/character/preset/global）——ST 有 variables 对象但模型不同，需自建一层适配。
4. **迁移成本分层**：triggerSlash/substitudeMacros/registerMacroLike/generateRaw 这类近乎**零成本**（改一行调用目标）；getChatMessages/setChatMessages/getWorldbook 中等成本（需自写存取）；脚本树/变量作用域是**主要工程量**。

## P-context：SillyTavern.getContext() 能拿到什么

### 【结论】可得，且极其丰富——**145 个 key，其中 95 个是函数**

【证据】evaluate_script 实测返回 ctxKeyCount: 145。函数类代表性清单：

```

registerMacro, unregisterMacro, substituteParams, substituteParamsExtended, messageFormatting,

```

关键**数据属性**（非函数）：chat(object, MUTABLE)、characters(object)、characterId(undefined——当前无角色)、chatId、chatMetadata、groups、groupId、extensionSettings、extensionPrompts、variables={"local":{},"global":{}}、macros、powerUserSettings、accountStorage、constants、streamingProcessor、swipe、tokenizers、mainApi="openai"、maxContext(number)、menuType、onlineStatus。

## P-worldbook：ST 原生世界书能否替代 getWorldbook

### 【结论】**结构上存在，功能上可用**——ST 原生完备，可替代

【证据】实测调用链（真实数据，非推测）：
```
await ct.getWorldInfoNames()  → 返回 14 个真实世界书名：
  ["5.16更新「柚月小手机变量」","道友先上我断后 (2)","道友先上我断后","道渊开局创建人物","道源DLC-1",
   "命定之诗与黄昏之歌v4.2","同人tag表","我的苍玄界，才不会这么跌宕起伏！ (3)", ...]
await ct.loadWorldInfo(names[0]) → 返回对象，keys=["entries"]，entries 条目数 = 6
```
**注意**：getContext().world_info 与 getContext().worldInfo **均为 undefined** —— 世界书**不在 context 上暴露为模块对象**，必须走上述函数式 API。

【对底座设计的影响】getWorldbook 系列**可以低成本替代**：读用 loadWorldInfo、写用 saveWorldInfo、枚举用 getWorldInfoNames。但要注意两点差异：(1) 返回结构是 ST 的 {entries:{...}} 格式，与 JSR getWorldbook 的返回形状可能不同，需适配层；(2) JSR 额外提供 getGlobalWorldbookNames/rebindCharWorldbooks 等**绑定关系**概念，ST 原生绑定信息需从 characters[].data.extensions.world / chat_metadata 自己取——**未逐一实测**，列为未证实。

## P-slash：triggerSlash / STscript 在扩展里可不可用

### 【结论】**可用，且这是替代 generateRaw 的关键路径**

【证据】
1. 静态：src/function/slash.ts 全文仅 9 行，整个函数体就是调 ST 的 executeSlashCommandsWithOptions(command)。**triggerSlash 是 ST 原生的纯别名。**
2. 运行时（A 层）：await ct.executeSlashCommandsWithOptions('/help') → isError: false，调用成功。
3. 运行时（探针扩展内，真实调用）：await ct.executeSlashCommandsWithOptions('/echo cx-probe-slash-ok') → {isError:false, pipe:"cx-probe-slash-ok"}，**返回值正确回传**。
4. 遮蔽 TavernHelper 后 executeSlashCommandsWithOptions **仍为 function**。
5. 文档佐证：docs/.../st-script.md:651-672 定义 /gen 与 /genraw，/genraw 支持 lock=/stop=/instruct= 参数——即 **STscript 原生具备生成能力**。

【对底座设计的影响】**这是最省力的一条迁移路径**。底座里 triggerSlash 与 generateRaw 两大能力，在裸扩展下可分别用 ct.executeSlashCommandsWithOptions() 和 /genraw（或直接 ct.generateRaw）覆盖，**几乎零成本**。建议扩展版优先走这条，避免复刻 JSR 的 19KB prompt 组装。

## P-store：扩展持久化

### 【结论】**结构上存在，功能上可用，跨刷新验证通过，且确实落盘**

【证据】探针扩展写入 → 刷新页面 → 再读：
```
写入(第1次运行): extensionSettings['cx_probe'] = {stamp:"set-at-1789980001017", runs:1}
刷新页面后读取:   {stamp:"set-at-1789980033746", runs:2}     ← runs 递增，数据存活
磁盘验证: Select-String settings.json → 命中 "cx_probe": {
```
可用持久化面（均实测 typeof 正常）：extensionSettings(object)、saveSettingsDebounced(function)、accountStorage(object)、writeExtensionField(function)、saveMetadata/saveMetadataDebounced(function)、localforage(object, SillyTavern.libs.localforage)、localStorage(object)。

**能否写文件**：**未证实**（前端扩展无 Node fs 权限；本次未验证 /api/ 后端写文件端点）。可确定的是**写服务器端 settings.json 是通的**（cx_probe 已落盘），这已满足持久化需求。

【对底座设计的影响】extensionSettings + saveSettingsDebounced() 是标准且够用的持久化方案，**跨刷新与跨会话均可靠**。底座状态可直接放这里，无需引入额外存储层。

## P-panel：扩展往 UI 挂东西的正确方式

### 【结论】**可用**——探针实测挂载成功，DOM 挂载点与官方范式均已确证

【证据】探针真实挂载：
```js
$('<div id="cx_probe_panel" class="inline-drawer">...').appendTo('#extensions_settings2');
// 实测返回: panelAttached: true, panelParent: "extensions_settings2"
```
挂载点存在性实测：extensions_settings=true、extensions_settings2=true、extensionsMenu=true、rm_print_characters_block=true、left-nav-panel=true、ai-config-button=true、send_form=true、movingDivs=true；chat_history=false。
#extensions_settings 真实子元素共 18 个，含各内置扩展容器（expressions_container、sd_container、tts_container…）与 **tavern_helper**（JSR 自己的面板，实测 tavern_helper_el: true）。

【对底座设计的影响】
- 官方推荐路径（Writing-Extensions.md:227-245）：用 renderExtensionTemplateAsync('third-party/<name>','settings',data) 渲染 Handlebars 模板，再 $('#extensions_settings2').append(settingsHtml)，**返回 HTML 自动过 DOMPurify 且支持 data-i18n 本地化**。
- JSR 的做法是把 Vue app mount 到 #extensions_settings 下自建的 <div id="tavern_helper">（src/index.ts:45-46），启动时机是 jQuery 的 $(() => {...})。
- 底座扩展版建议：**挂 #extensions_settings2，用官方模板函数**，避免与 JSR 的 #tavern_helper 冲突。

## P-events：eventSource / event_types 在扩展里的用法

### 【结论】**结构上存在，功能上可用**——实测注册成功

【证据】
- ct.eventSource = object，其**原型**上共 8 个方法：on, once, emit, emitAndWait, makeFirst, makeLast, removeListener, constructor。
- ct.eventSource.on(ct.eventTypes.CHAT_CHANGED, handler) → **注册成功**（event_on_ok: true）。
- ct.eventTypes 与 ct.event_types **是同一个对象**（same: true），共 **104 个**事件类型。
- ct.eventTypes.CHAT_CHANGED 的实际值 = "chat_id_changed"（**不是枚举名本身**，是事件字符串）。
- 遮蔽 TavernHelper 后 eventSource/eventTypes 仍在 context 里（但 window.eventSource/window.event_types 为 undefined）。
- 探针扩展本身就是在 APP_READY 事件里跑完全部测试并成功的。
- **重要偏差**：ct.eventSource.off() **不存在** → TypeError: ct.eventSource.off is not a function；正确反注册是 removeListener。

【对底座设计的影响】事件系统是**纯 ST 原生**，扩展形态可完整沿用。适配层必须把「off」改写成「removeListener」。推荐按官方 APP_INITIALIZED / APP_READY 分层初始化（Writing-Extensions.md:144-148）。

## P-build：ES module 动态 import 是否可用

### 【结论】**可用**——三种 import 全部实测成功，懒加载完全可行

【证据】探针扩展内 await import(...) 实测：
```
import('/script.js')               → ok:true, type:"object", 导出 keys = 249
import('/scripts/extensions.js')   → ok:true, keys 含 ["EMPTY_AUTHOR","ModuleWorkerWrapper","cancelDebouncedMetadataSave",
                                      "deleteExtension","disableExtension","doDailyExtensionUpdatesCheck","doExtrasFetch",
                                      "enableExtension","extensionNames","extensionTypes","extension_settings","findExtension",
                                      "getApiUrl","getAuthorFromUrl"]
import('/lib.js')                  → ok:true, keys 含 ["Bowser","DOMPurify","DiffMatchPatch","Fuse","Handlebars","Popper",
                                      "Readability","SVGInject","chalk","chevrotain"]
```
补充：探针 index.js 本身**未用 type="module"** 声明，仍可正常执行并被 ST 加载；说明扩展入口是经典脚本但**动态 import 语法可用**。
另外 import.meta 在 evaluate 的经典脚本上下文**报错** Cannot use 'import.meta' outside a module——但这只反映 evaluate_script 的执行上下文，**不代表扩展里不可用**，故列为未证实。

【对底座设计的影响】**懒加载可行**。底座可以做成极小的 index.js 引导层，按需 await import() 拉取重量级模块（ST 自身 249 个导出也能按需取）。这对「扩展形态要轻量」的目标非常有利。

## P-update：扩展一键更新机制

### 【结论】**机制在文档中存在，auto_update 字段可确认；端到端更新流程未实测**

【证据】
- manifest.json 支持 "auto_update": true，文档 Writing-Extensions.md:116 明确：set to true if the extension should auto-update **when the version of the ST package changes**。
- 官方提供生命周期钩子（Writing-Extensions.md:98-105）：install / update / delete / enable / disable / activate；其中 update 在 Writing-Extensions.md:682 描述为 After a successful extension update (before the reload toast)。
- 本机已装扩展中，**JS-Slash-Runner 自己的 manifest 就是 "auto_update": true**（实测读取其 manifest.json:11），且其源码含 src/panel/info/update.ts（4836 字节）与 updateTavernHelper 接口——证明该机制真实可用。
- 本机运行日志确认 ST 会扫描本地扩展：Extensions available for default-user [{type:'local',name:'third-party/JS-Slash-Runner'}, ...]。
- 相关 context API 实测存在：getExtensionManifest(function)、openThirdPartyExtensionMenu(function)、importFromExternalUrl(function)。

**未证实**：本次**未实际执行**一次「版本变更 → 自动更新」的端到端流程（会改动安装态，超出了只读探针范围）。

【对底座设计的影响】更新机制**有官方支持且字段简单**（auto_update + version + homePage + update 钩子）。但注意 auto_update 的触发条件是「**ST 包版本变化**」而非扩展版本变化，若要按扩展自身版本更新，需走 hooks.update 自行实现。建议扩展版发布时同时提供 hooks.update。

| P-update | ✅ 文档+字段 | ⚠️ 端到端未实测 | ✅ 原生 | 低 |
| **P-bridge（21 接口本体）** | ❌ **裸扩展全无** | — | ❌ **不可得** | **见下** |

### 最关键的一句话

**TavernHelper 的 21 个接口在裸扩展环境下「结构上全部不存在」，但这不等于「能力拿不到」——因为 JSR 自己也只是 ST 原生 API 的薄封装。**

- **真正不可得（ST 无对应概念）**：getScriptTrees / getScriptId / replaceScriptTrees 等**脚本树模型**。ST 没有「脚本」这一层抽象，这是 JSR 独有。**底座若依赖脚本树做多脚本编排，扩展形态必须自建。**
- **语义需适配（ST 有但模型不同）**：getVariables/replaceVariables 的五作用域变量模型（message/chat/character/preset/global）——ST 有 variables 但作用域模型不同。
- **近乎零成本替代（ST 原生同名或同名函数）**：triggerSlash→executeSlashCommandsWithOptions、substitudeMacros→substituteParamsExtended、generateRaw/generate→getContext().generateRaw/generate 或 /genraw、registerMacroLike→registerMacro、getWorldbook→loadWorldInfo/saveWorldInfo。

**结论：可以迁。核心工作量集中在「脚本树 + 变量作用域」两块自建，其余接口基本是改调用目标。**

## Q2. `macros.register()` 端到端（本项目历史未证实项）

### 【结论】**完全可用——已打通，并定位出历史上一直失败的确切原因**

【证据·成功的完整配方】探针在真实扩展里注册并在多种路径下替换成功：

```js
const ct = SillyTavern.getContext();
ct.macros.register('cxProbeMacro', {
  unnamedArgs: 1,                                    // ← 关键参数（见下）
  handler: (ctx) => 'CX_PROBE_MACRO(' + ctx.unnamedArgs[0] + ')'
});
```

实测替换结果：
```json
{
  "oneArg_dblcolon":    "CX_PROBE_MACRO(abc)",       // {{cxProbeMacro::abc}}
  "multiline":          "a CX_PROBE_MACRO(x) b",     // {{cxProbeMacro::x}}
  "messageFormatting":  "<p>CX_PROBE_MACRO(mf)</p>"  // 走 messageFormatting 渲染路径
}
```
注意 **`messageFormatting()` 返回 `<p>...</p>` 且宏已替换** —— 说明宏在**角色卡消息渲染路径**上同样生效，不只是 `substituteParams`。

### 历史失败的根因（这是本项目最有价值的发现）

**旧写法 `ct.macros.register(name, 函数)` 或 `{ handler, minArgs }` 会「注册成功但永不替换」，静默失败、不报错。**

实测对照矩阵（同一次运行，全部 `inRegistry: true`）：

| 注册参数 | `minArgs` | 替换 `{{名::x}}` | 结果 |
|---|---|---|---|
| `{ handler }` | 0 | ✗ 原样返回 | 失败 |
| `{ handler, minArgs:1 }` | **0** | ✗ 原样返回 | 失败（minArgs 被忽略） |
| `{ handler, maxArgs:1 }` | **0** | ✗ 原样返回 | 失败（maxArgs 被忽略） |
| `{ handler, unnamedArgDefs:[{}] }` | **0** | ✗ 原样返回 | 失败 |
| `{ handler, unnamedArgs:1 }` | **1** | ✅ `OK ["hello"]` | **成功** |
| `{ handler, unnamedArgs:2 }` | 2 | ✅ `OK ["a","b"]` | **成功** |
| `{ handler, unnamedArgs:[{name:"v"}] }` | 1 | ✅ `OK ["x"]` | **成功** |

**根因（源码钉死）**：`public/scripts/macros/engine/MacroRegistry.js:63-75` 的 `MacroDefinitionOptions` typedef 里**根本没有 `minArgs`/`maxArgs`/`unnamedArgDefs` 这三个入参**——真正的入参是 `unnamedArgs`（`:66`，可为数字或定义数组）。
`minArgs`/`maxArgs` 是**产物** `MacroDefinition`（`:137-138`）的只读字段，不是注册选项。传错名字不会报错，因为没有校验未知字段，结果宏被建成 `minArgs:0`。
然后 `strictArgs` 默认 `true`（`:68`），带参数的调用 `{{宏::x}}` 与 `minArgs:0` 不匹配 → **静默不替换**。

### 另一条重要澄清
- 旧 API `ct.registerMacro(name, fn)`（`st-context.js:179`，标注 @deprecated，绑定 `MacrosParser`）**仍然可用**：实测 `{{cxOldApi}}` → `OLD_VAL`，且能在新 registry 里被 `getMacro` 查到。**所以「旧 API 坏了」这个假设不成立**——历史失败是**参数名写错**，与新旧 API 无关。
- `{{roll::1d20}}` → `12`、`{{reverse::I am Lana}}` → `anaL ma I`，**内置带参宏工作正常**，证明宏引擎本身没问题。
- 参数语法三种都支持（前提是声明了 `unnamedArgs`）：`{{m::x}}`、`{{m:x}}`、`{{m x}}` 均可。官方推荐 `::`（见内置宏 `exampleUsage` 如 `{{roll::1d20}}`）。

【对底座设计的影响】
- **历史遗留的「宏注册不生效」问题可以关闭了**，配方就是：`macros.register(name, { unnamedArgs: N, handler })` + 调用用 `{{name::arg}}`。
- 底座若要给脚本暴露自定义宏（替代 JSR 的 `registerMacroLike`），**走 `ct.macros.register` 即可，ST 原生完整支持**。
- ⚠️ **务必在扩展内部用中文/带前缀的宏名做命名空间**，避免与内置 131 个宏冲突（实测内置宏数量 131）。
- ⚠️ 陷阱：传错选项名**不报错**，只是静默不替换。建议底座封装一层并在注册后自检一次 `substituteParams`。

## Q4. manifest `hooks` 与 `activate` 执行时机

### 【结论】**`activate` 确实被调用，且在模块首次求值之后**；5 秒超时已在源码确认

【证据】manifest 声明 6 个 hook（`activate/enable/install/update/delete/disable`），只观测到 activate（其余需要用户操作触发）：
```json
"HOOKS": { "activate_called": "2026-09-21T08:50:58.805Z", "readyState": "complete", "ctxKeys": 145 }
```
对比同次运行的 `EARLY.t0` 时刻，activate 在**模块顶层代码执行完毕后**被调用；且此时 `getContext()` 已有 145 个 key、`document.readyState` 已是 `complete`。

【源码佐证】`public/scripts/extensions.js:628-642`：`addExtensionScript()`（注入 `<script type=module>`）resolve **之后**才 `activeExtensions.add(name)` 并 `callExtensionHook(name,'activate')`。
`callExtensionHook`（`:406-466`）实现为：`await import(url)` → 取 `module[hookFunctionName]` → **必须是导出函数**，否则 `console.warn(... is not an exported function)`（`:440-442`）→ 调用并 `Promise.race` 与 **`HOOK_TIMEOUT = 5000`**（`:447`）竞争，超时仅告警（`:458-459`）。

⚠️ **重要机制**：`callExtensionHook` 用 `await import(url)` 拿的是 **ES module 单例**。若该扩展 JS 已作为 `<script type=module src>` 加载过，`import` 命中缓存，**模块顶层代码不会重跑**，只执行被导出的 hook 函数。**在扩展管理界面点「启用」不会重新执行你的顶层初始化代码。**

【对底座设计的影响】
- **`activate` 可用且时机安全**（此时 context 已完整），适合做同步初始化。
- 但由于上面的单例语义：**hook 函数体内的逻辑不能依赖「模块顶层已跑过」之外的东西重跑**。底座做初始化的正确写法是：顶层只做「注册 + 定义函数」，真正的初始化逻辑放在一个可重复调用的 `init()` 里，`activate` 调用它。
- **5 秒超时是硬约束**：`activate` 里不要做长耗时迁移（如大量世界书写入），超时只告警但会**继续往下走**，你的初始化可能只完成一半。长任务应丢给后台异步（APP_READY 之后）。
- `enable`/`disable`/`install`/`update`/`delete` 会在对应操作时被调用（`extensions.js:474/491/1389/1568/1771`），可用于数据迁移/清理。

## Q5. 动态 import 分包 chunk 懒加载

### 【结论】**完全可行**——相对路径、嵌套目录、绝对 URL 三种 chunk 全部加载成功；缺失 chunk 给出明确 404 类错误

【证据】探针实测四条路径：
```json
{
  "relative_chunk": { "ok": true, "keys": ["PROBE_CHUNK_VALUE"], "value": "CHUNK_LOADED_OK" },
  "nested_chunk":   { "ok": true, "value": "NESTED_CHUNK_OK" },       // ./subdir/chunk-probe2.js
```

**相对路径能正确解析**，因为 ST 用 `script.src = url` 注入模块（`extensions.js:824-827`），模块的 base URL 即 `/scripts/extensions/<name>/`，所以 bundler 生成的 `import('./x.chunk.js')` 天然可用。

【对底座设计的影响】
- **懒加载方案成立**：底座可以做极小的 `index.js` 引导层，按需 `import('./<chunk>.chunk.js')` 拉取重量级模块。官方 webpack/vite 模板的 `chunkFileNames: '[name].[hash].chunk.js'` 正是为此设计，**与实测行为一致**。
- 失败模式清晰：chunk 缺失抛 `TypeError: Failed to fetch dynamically imported module`（含完整 URL），**易于定位**，建议底座在懒加载处 catch 后降级并提示。
- ⚠️ 注意 hash 文件名：更新后旧 hash chunk 会 404，**必须保证发布是原子的**（新 index.js 与它引用的 chunk 同批上线），否则用户会加载失败。

## 追加：B 层补充 —— JSR 注入清单里「ST 原生没有的」

按 Lead 指示，B 层静态溯源只补「JSR 自造、ST 原生无对应」的部分。基于 `src/function/index.ts:195-449` 的全量清单比对 `getContext()` 145 个 key：

### ST 原生**没有**对应物的（JSR 独有概念）—— 共 3 类

| JSR 接口 | 为什么 ST 没有 | 扩展形态后果 |
|---|---|---|
| `getScriptTrees` / `replaceScriptTrees` / `updateScriptTreesWith` / `getAllEnabledScriptButtons` | ST **没有「脚本」这层抽象**，这是 JSR 自建的脚本管理模型（脚本树 + 每脚本 iframe 运行时，见 `src/store/scripts.ts`、`src/store/iframe_runtimes/`） | **必须自建**。这是最大的一块工程量 |

| `initializeGlobal` / `waitGlobalInitialized` / `_initializeGlobal` / `_waitGlobalInitialized` | JSR 自造的「全局变量就绪」事件协议（`eventSource.emit('global_X_initialized')`，`src/function/global.ts`） | 可自实现（基于 ST eventSource），但**协议要自己定** |

### ST 原生**有**对应物的（JSR 只是再包装）—— 供对照

| JSR 接口 | ST 原生对应 |
|---|---|
| `generateRaw` / `generate` / `generateQuietPrompt` | `getContext().generateRaw` / `.generate` / `.generateQuietPrompt`（**同名**） |
| `substitudeMacros` | `getContext().substituteParams` / `.substituteParamsExtended` |
| `triggerSlash` | `getContext().executeSlashCommandsWithOptions` |

### 【结论】B 层最终判定

**JSR 注入的 200+ 个字段中，ST 原生无对应物的只有「脚本树 / iframe 脚本运行时 / global 初始化协议」这一小块（约 3 类）。** 其余全部是 ST 原生能力的包装——与 Lead 的静态结论一致，并被本次真机实测逐条佐证。

**迁移的真正工程量 = 自建脚本树 + 自建 global 初始化协议 + 变量作用域适配层**，而非「复刻整个 JSR」。
