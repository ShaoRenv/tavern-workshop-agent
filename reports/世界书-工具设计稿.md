## 1. 设计原则（这次先定原则，再定工具）

**P1 · 工具服务动作，不服务 API**
一个工具 = 一个人真的会做的动作。不做就不给工具。

**P2 · 提示词只写三件事**
干什么 · 什么时候用 · 返回什么。**领域知识进 skill，不进工具描述。**

**P3 · 必填最少，其余走默认**
真实数据里 1788 条，绝大多数只用 `comment`/`content`/`key`/`constant`。高级字段按需出现。

**P4 · 尊重人类的命名约定**
`====xxx====_开始/_结束`、`[mvu_update]`、`[mvu_plot]` 这些前缀要**识别**，不能当噪音。

**P5 · 绝不丢字段**
真实数据有 `extra`（45 条）、`characterFilter`（913 条）、`ignoreBudget`（997 条）。读-改-写必须**原样保留所有没碰的字段**。

**P6 · 只读工具要便宜、可并行**
看结构、搜条目这种，不产生正文，可以默认开。

## 3. 候选工具集（请你砍）

### 3.1 我建议的 5 个工具

```
wb_list      列世界书
wb_outline   看一本书的结构（★替代原来的分页读）
wb_read      读条目（★必须返回判定所需的全部字段）
wb_search    搜条目
wb_write     新建 / 改 / 删（★合并）
```

**提示词（全部按 P2 写，一句话）**：

| 工具 | 提示词（草） | 返回 |
|---|---|---|
| `wb_list` | 列出酒馆里的世界书。不确定用户指哪本时先调它。 | 名字 + 生效范围 + 条目数 |
| `wb_outline` | 看一本书的结构：分节、每节条目、每条的状态。改之前先看它。 | 树状目录 |
| `wb_read` | 读条目。改之前一定要读。 | 正文 + 判定所需字段 |
| `wb_search` | 按关键词找条目。 | uid + 标题 + 摘要 |
| `wb_write` | 新建、修改或删除世界书条目。改完要回读确认。 | 变更结果 |

### 3.1.1 为什么删掉了 `wb_check`（用户指正）

**用户原话**：「能不能触发只需要了解世界书是否开启、蓝绿灯、key 就可以判断出来，只需要世界书的信息就可以判断了」

**我原来的错**：把「判断能不能触发」当成一个需要工具去算的问题。
实际上判定依据**全是条目自己的字段**：

| 判断依据 | 来自哪个字段 |
|---|---|
| 开没开 | `disable`（或卡内 `enabled`） |
| 蓝灯还是绿灯 | `constant` |
| 会不会命中 | `key` |
| 次级门槛 | `keysecondary` + `selectiveLogic` |
| 命中概率 | `probability` |
| 扫多深 | `scanDepth` vs 全局 `world_info_depth` |
| 常亮能否保命 | `sticky`/`cooldown`/`delay` |

**所以正确做法**：
- **工具负责把字段摆全**（`wb_read` / `wb_outline` 返回）
- **skill 负责教判定规则**（`世界书工程` skill 正文）

多一个工具 = 多一次调用 + 多一份提示词开销 + 多一层黑盒。
**这和上一版「把领域知识塞进工具描述」是同一个错的镜像**：那次是不肯把知识给 skill，这次是不肯把判断给 skill。

### 3.2 `wb_outline` 长什么样（关键设计）

**输入**：世界书名
**输出**（真实书试算）：

```
《我的苍玄界，才不会这么跌宕起伏！》 219 条
├─ ====核心规则==== (6 条 · 蓝灯)
│   世界观总览              902字  蓝 pos0
│   世界引擎               2586字  蓝 pos4
│   故事基调               1496字  蓝 pos0
│   ...
├─ ====角色设定==== (23 条 · 21 绿灯)
│   江念          1601字  绿 keys=["江念","无情道弟子"]
│   沈慕微        2156字  绿 keys=["沈慕微","无情道首座"]
│   ...
└─ ====世界观==== (…)
```

**为什么这样设计**：
- 直接复现**人类自己的分节**（`====xxx====_开始/_结束` 配对）
- 一眼看出**蓝灯比例**（蓝灯泛滥是真实病）
- **不是分页** —— 219 条一屏看完结构，不需要翻页

**⚠️ 已收敛：不做「异常标记」**（用户指正后的修正）

我原来想在 outline 里标「死条目 / 单字关键词 / 重名」。**这越界了** —— 那是**判断**，不是**数据**。
工具只忠实显示字段，判断交给模型 + skill：

```
江念         绿  keys=["江念","无情道弟子"]  1601字  pos0
历           绿  keys=["历"]                2332字  pos0   ← 模型自己看出单字有问题
红CG触发     绿  keys=[]                     621字  pos4   ← 模型自己看出是死条目
USER档案     停用                             345字  pos0
```

skill 里教：「看到 `绿 + keys 空` 就是死条目」。

### 3.3 `wb_write` 的参数（按 P3 收窄）

```
必填：world, action(create|update|delete)
create 时必填：content
update 时必填：uid
delete 时必填：uid

可选（只填要改的）：
  name         标题
  content      正文
  keys         主关键词
  constant     是否常亮
  depth        深度（pos=4 时）
  position     插入位置
  order        顺序
  enabled      是否启用
```

**对比上一版**：13 个参数 → **8 个**，且 `group`/`sticky`/`cooldown`/`probability`/`role`/`scan_depth` 全部下沉到 skill 讲解 + 需要时手动加。

**⚠️ 待你定**：高级字段（group/sticky/cooldown/probability/vectorized…）要不要留一个「逃生口」？我倾向：**保留，但不出现在工具提示词里**，模型读了 skill 才知道有它们。

### 3.4 `wb_read` 必须返回的字段（这是新设计的核心）

删掉 `wb_check` 之后，**判定所需的全部信息必须由 `wb_read` / `wb_outline` 摆出来**：

```
uid=1  「江念」
正文: <1601 字全文>
────────────────────────
启用:      是
类型:      绿灯（关键词触发）
主关键词:  ["江念", "无情道弟子"]
次关键词:  无
扫描深度:  跟随全局（当前 2 楼）
概率:      100%
位置:      角色定义之前 (pos=0)
顺序:      100
────────────────────────
[高级字段] 递归: 禁止（exclude_recursion）
[其他字段] 本条目还有 12 个扩展字段，已原样保留
```

**最后两行是关键** —— 这就是原来想让 `wb_check` 干的活：**把判定所需信息摆全**，判断交给模型。

**⚠️ 诚实说明**：受人类手册 §21 悬案 U1/U2 影响（AND_ALL 激活门槛、NOT_ANY/NOT_ALL 实现位置未定），
「次关键词组合逻辑」的判定规则我会在 skill 里**如实标注不确定**，不假装准确。
真实数据里 1769/1784 用的是 AND_ANY（最简单那种），影响面小。
