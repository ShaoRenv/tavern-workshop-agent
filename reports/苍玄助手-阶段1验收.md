## ④ 隐患（按严重度排序）

- **H1（阶段 3 会踩，建议现在就记进计划 §7）inTabbar:false 的页面永远打不开。** stores/app.ts:320-325 的 `setTab` 用 `availablePages`（= tabbarPages，过滤掉 inTabbar:false）判定合法性；PluginDetail 的「页面 →」走的也是 setTab。我往 PLUGIN_MANIFESTS 临时塞了一个 `inTabbar:false` 的假插件页验证：allPages 有它、availablePages 没有、`setTab('mcp-page')` 回落到 portraits。计划 §7 要求 MCP 内容页默认 inTabbar:false、从插件管理页进 —— 那条路现在不通。修法：合法性判定用 `allPages`，顶栏只画 `availablePages`（可达性与上不上顶栏是两件事）。
- **H2 App.vue 的视图分发仍是 6 条硬编码 v-if，最后一条是 `<SettingsView v-else>`**（App.vue:3-73）。任何新页面 id（阶段 3 的插件页）会静默渲染成设置页而不是报错。配合 H1，插件页在阶段 3 之前没有落点；阶段 3 要按计划换成「id → 组件静态表」+ 页面级错误边界。
- **H3 plugins 是一个整块，一个插件设置坏掉会连累兄弟插件。** recoverBlock 对 z.object 不做逐键恢复，只有 z.record 才逐条兜底（storage.ts:396-437）。实测 `{plugins:{image:'坏值', cangxuan:{manual_meta:{…}}}}` → plugins 整块回默认、**cangxuan.manual_meta 一起没了**（console：「存储块 plugins 校验失败，已用默认值恢复」）。阶段 3 把「传图结果」搬进 `plugins.cangxuan.manual_meta`（A13）后，这就是用户数据丢失面。建议 plugins 块改成逐 id 恢复。
- **H4 plugin_state 里 enabled 不是 boolean 时那一项被整条丢掉 → 静默回落 defaultEnabled。** 实测 `{image:true, cangxuan:{enabled:'yes'}}` → plugin_state 变 `{}`（image 掉回 false、cangxuan 掉回 true）。对 defaultEnabled=false 的插件等于「坏数据把用户开着的插件关掉」——与 Lead 刚修的 bug 同一方向。建议 parse 前把 enabled 归一成 boolean（或 z.coerce）。
- **H5 migratePluginSwitch 用 `config.enabled === true` 判定**（types.ts:169）：v4 里 enabled 若写成 1 / 'true'（手改数据）会被搬成 false。低概率，与 H4 同类。
- **H6 mergePages 同 order 时按 id 字典序**（core/pages.ts:29）：阶段 2/3 给插件页排 order 时要避免与核心页撞号；撞了不崩，但顺序由 id 而不是声明顺序决定，容易出现「顺序跟想的不一样」。
