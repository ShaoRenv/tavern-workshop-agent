## 二、积病 #1：两条宿主解析链（必须统一）

`hostFn()`（core/storage.ts:76）查找顺序：注入假实现 → `globalThis.TavernHelper[name]` → `globalThis[name]`。
`globalFunction()`（agent/transport.ts:166）查找顺序：`globalThis.TavernHelper[name]`（`.bind(helper)`）→ `globalThis[name]`（`.bind(globalThis)`）→ `globalThis.window[name]`（`.bind(win)`）。

**三处实质差异：**
1. `globalFunction` **不查注入的假实现** —— 所以 transport 的 3 个接口在测试里无法用 `setHostBridge` 假造，只能另外造 `deps.xxxImpl` 后门。这就是 `substituteMacrosImpl` / `generateRawImpl` 存在的原因：**是绕开积病的补丁，不是设计**。
2. `globalFunction` 多了 `window[name]` 兜底；`hostFn` 没有。（`globalThis === window` 在页面里成立，这条兜底多半是无效代码。）
3. `.bind` vs 闭包调用：对 `helper[name]` 而言两者等价；但 `globalThis[name]` 那支 `globalFunction` 绑的是 `globalThis`，`hostFn` 用箭头函数——在本页环境下同样等价。**结论：差异 1 是真实语义差，2/3 是无害差异。**

**改进：扩展版只保留一条链，且升级为「多源、可注册」的解析器**（见下节）。`deps.substituteMacrosImpl` / `generateRawImpl` 两个后门应当**删除**，改用统一桥的假实现注入。

## 三、积病 #2：桥把「酒馆助手」当成了唯一宿主

`hostFn` 硬编码查 `globalThis.TavernHelper`。在扩展形态下这等于**把底座绑死在另一个第三方插件上**（JS-Slash-Runner 不是 ST 官方）。

实测确认：本机 ST 的扩展目录里装的就是 `JS-Slash-Runner`、`ST-Prompt-Template`、`yuzuki-phone`。也就是说「能跑」其实是「玩家恰好装了酒馆助手」。

**改进：宿主解析改成有序的「提供者链」（provider chain）：**

```
resolve(name) →
  1. 注入的假实现（测试 / 覆盖）
  2. 注册进来的原生适配器（扩展版自带：ST.getContext() / STscript / 后端 API）
  3. globalThis.TavernHelper[name]        （沿用酒馆助手，兼容老环境）
  4. globalThis[name]                      （沿用旧行为）
```

第 2 层是**新增的关键一层**：扩展版自己实现拿不到的接口，注册进链里。插件只看「有没有能力」，不看「能力从哪来」。

**这条同时解决了用户的核心诉求**：底座不再是「酒馆助手的壳」，而是「能自己长能力的底座」——正是「能力取决于插件」的架构前提。

## 四、积病 #3：能力可得性是隐式的

现状：拿不到接口时各处自己 `throw new Error('酒馆助手缺少 xxx 接口')`（如 core/worldbook.ts:349）。UI 上 `hasHostFn()` 只是个布尔，没有「哪些能力可用、降级到什么程度」的表达。

**改进：扩展版引入 `Capability` 描述符**，每个宿主接口声明：
```ts
{ name, provider, required: boolean, degrade?: () => void, label }
```
→ 底座启动时探一遍，得出一张**能力表**：
- 插件 `contributes` 里声明「我需要哪些能力」；
- 能力缺失时该插件**不注册**并给出可读原因，而不是运行时炸在半路；
- 设置页能直接显示「世界书插件：不可用（缺 getWorldbook）」。
这把 `plugins/builtin/image/manifest.ts` 已有的 `status()` 模式**从个案提升为框架机制**。

## 五、不阻塞迁移的部分（明确说明）

不要让「迁移」听起来像重写。以下**原样保留**：

- **core/agent/run/stores 的绝大部分逻辑**（工具注册表、四张注册表、runner、loop、session/event 模型）与宿主无关，零改动。
- **插件契约**（PluginManifest / contributes）已经设计成与宿主解耦，零改动。
- **分层硬规矩**已实测合规：`plugins/**` 无一处 import `components/`/`views/`/`stores/`/`App.vue`。
- **测试 320 条**绝大部分是纯逻辑测试，走 `setHostBridge` 假实现，不依赖真酒馆。
