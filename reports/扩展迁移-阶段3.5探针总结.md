## 一、决定性结论：**迁得动，而且比预期好得多**

| 原本担心的风险 | 实测结论 |
|---|---|
| 「扩展里拿不到酒馆助手的 21 个接口，底座会废」 | ❌ **担心不成立**。酒馆助手本身就只是 ST 原生 API 的**薄封装**；底座需要的 17 个接口**全部**能在 `SillyTavern.getContext()` 找到原生对应 |
| 「要复刻酒馆助手的复杂逻辑」 | ❌ **不用**。JSR 的 `triggerSlash` 全文 9 行、`substitudeMacros` 3 行，就是原生调用的别名 |
| 「单文件约束会跟着迁移」 | ✅ **松绑**。动态 `import()` 分包实测三条路径全通 |
| 「宏注册端到端没验过」 | ✅ **打通并找到根因**（见下） |

**真正的工程量只有三块**（ext-prober B 层结论，与 Lead 静态结论一致）：
1. **脚本树**：`getScriptTrees`/`getScriptId`/`replaceScriptTrees` —— ST 没有「脚本」这个抽象，JSR 独有。**最大工程量**。
2. **变量作用域适配层**：JSR 是 message/chat/character/preset/global/script **六作用域**，ST 的 `variables` 是 local/global 两个。要自建映射。
3. **global 初始化协议**：JSR 自造的 `global_X_initialized` 事件协议，需基于 ST `eventSource` 自定。

其余 200+ 接口 = 改调用目标，不是重写。

## 三、历史遗留问题：**已找到根因并修复方向**

### 3.1 `registerMacroLike` 端到端失败 → 根因是**参数名写错**
ext-prober 实测打通，Lead 已用源码独立复核：
- **正确**：`macros.register('名', { unnamedArgs: 1, handler })`，调用 `{{名::arg}}`
- **错误**：传 `minArgs` / `maxArgs` / `unnamedArgDefs` → **注册「成功」但永不替换，且不报错**
- **源码钉死**：`MacroRegistry.js:63-75` 的 options 里**没有** `minArgs`；真名是 `unnamedArgs`(:66)。`minArgs` 是**产物字段**(:137)不是注册选项。默认 `strictArgs=true`(:68) → 带参调用不匹配 → **静默失败**。
- **澄清**：旧 API `registerMacro` **没坏**（实测可用）。之前的怀疑方向错了。

> **教训（写入插件开发文档）**：ST 宏注册是**静默失败**设计，参数名写错不报错。扩展版要加**注册后自检**（注册完立刻验证能否替换）。

### 3.2 宏 handler 必须**同步**
官方文档 :916「Handlers will run **synchronously**, so they can never return a Promise」。
好消息：我们的 `PluginMacro.render` 契约**本来就是同步返回 `string`**，天然兼容。
**要在扩展版固化**：类型保持同步 + 运行时守卫（返回 Promise 则拒绝注册）+ 测试断言。详见 `reports/扩展迁移-宏系统与设计约束.md`。

### 3.3 Lead 新发现的真缺陷：`rememberMacroValues` 无视插件开关
`plugins/host.ts:135-147` 调 `liveMacros({ plugin_state: undefined })`。
因 `registry.ts:41-45` 的 fallback 语义（没有就听 `manifest.defaultEnabled`），传 `undefined` ⇒ **完全无视用户的关闭开关**。

Lead 可执行证据（`node --experimental-strip-types` 实测）：
```
plugin_state UNDEFINED -> cangxuan enabled? true
plugin_state OFF      -> cangxuan enabled? false
enabledPlugins({plugin_state:undefined}) = cangxuan,worldbook   ← 关了还在
enabledPlugins(OFF)                      = worldbook           ← 正确
```

**与阶段 3 修掉的 F-A' 是同一类错误**（那次是 ToolRegistry 剥了一层外壳）。**同一模式第二次出现**，说明「传 plugin_state 的封装语义」是反复踩的坑。**扩展版应从类型上根治**（不可省的参数 / 不透明类型，不给「传 undefined」的机会）。

## 五、需要更新认知的两条

1. **「底座今天能跑」的真相**：完全因为玩家装了 JSR。`window.getVariables`/`generateRaw` **从来不在 window 上**，只在 `window.TavernHelper`，而该对象 100% 由 JSR 在 `src/function/index.ts:447` 组装。扩展形态**必须**改走 `getContext()`。
2. **`extensionSettings` 落盘告警**：实测落在 `data/default-user/settings.json`（该文件已 **50MB**，每次保存**全量重写**）。底座状态（多会话 + 事件日志）不宜全塞这里 → 需要**分片**或走 `accountStorage`。

## 六、对「打造最好的底座」的设计原则（回应用户诉求）

1. **单源宿主解析**：消灭 `hostFn` / `globalFunction` 两条平行链，改成**可注册的 provider chain**（注入假实现 → 原生适配器 → 兼容 JSR → 全局）。顺带删掉 `deps.substituteMacrosImpl` / `generateRawImpl` 两个「绕过积病」的后门。
2. **显式能力表**：每个宿主接口声明 `{name, provider, required, degrade, label}`；插件声明「需要哪些能力」；缺能力则**不注册并给可读原因**，而不是运行时炸在半路。把 image 插件已有的 `status()` 从个案提升为**框架机制**。
3. **分层已合规**：`plugins/**` 实测**零 import** `components/`/`views/`/`stores/`/`App.vue`——这条硬规矩保住了，扩展版继续执行。
4. **状态不可省**：把 `plugin_state` 做成**不透明类型**，从类型上杜绝「传 undefined」这类错误（`rememberMacroValues` 与 F-A' 是同一个坑的两次发作）。
5. **注册后自检**：宏/工具/页面注册后立刻验证一次，防静默失败（ST 宏注册就是静默失败的）。
6. **首次运行必须成功**：`activate` hook 有 5 秒超时且模块是**单例**（点「启用」不重跑顶层代码）→ 初始化逻辑必须写成**可重复调用的 `init()`**，不能依赖顶层副作用。
