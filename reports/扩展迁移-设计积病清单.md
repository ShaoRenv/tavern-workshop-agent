| # | 条目 | 类别 | 是否阻塞迁移 |

## 一、宿主解析链二义性（维度 1）——**真积病，阻塞**

### 1.1 现象

同一件「按名字取宿主接口」，代码里存在 **三条互不知情的解析链**，查找顺序与调用语义各不相同。

### 1.2 证据

**链 1 —— `hostFn()`（唯一的「官方」桥）**  `src/苍玄助手/core/storage.ts:76-91`

```
76: export function hostFn(name: string): HostFn | null {
77:   const injected = injectedBridge?.[name];          // (1) 注入的假实现
78:   if (typeof injected === 'function') return injected;
80:   const scope = typeof globalThis === 'undefined' ? null : (globalThis as Record<string, any>);
83:   const helper = scope.TavernHelper;                 // (2) globalThis.TavernHelper[name]
84:   if (helper && typeof helper[name] === 'function') {
85:     return (...args: any[]) => helper[name](...args);
86:   }
87:   if (typeof scope[name] === 'function') {           // (3) globalThis[name]
88:     return (...args: any[]) => scope[name](...args);
89:   }
90:   return null;
91: }
```

注意：返回的是**闭包包装**（`(...args) => helper[name](...args)`），**每次调用才重新解引用** `helper[name]`。

**链 2 —— `globalFunction()`（transport 私有的平行链）**  `src/苍玄助手/agent/transport.ts:166-183`

```
166: function globalFunction<T>(name: string): T | undefined {
167:   const host = globalThis as unknown as Record<string, unknown>;
169:     const helper = host.TavernHelper as Record<string, unknown> | undefined;
170:     if (helper && typeof helper[name] === 'function')
171:       return (helper[name] as (this: unknown) => unknown).bind(helper) as T;
175:   if (typeof host[name] === 'function') return (host[name] as ...).bind(globalThis) as T;
177:     const win = host.window as Record<string, unknown> | undefined;
178:     if (win && typeof win[name] === 'function') return (win[name] as ...).bind(win) as T;
182:   return undefined;
183: }
```

调用点共 3 处，全部绕过 `hostFn`：

| 接口 | 位置 | 用途 |
|---|---|---|
| `substitudeMacros` | `agent/transport.ts:450` | 宏替换 |
| `generateRaw` | `agent/transport.ts:626` | **文本通道主命脉** |
| `stopGenerationById` | `agent/transport.ts:652` | 中止生成 |

**链 3 —— 裸 `globalThis` 直取（连包装都没有）**

- `agent/transport.ts:494-495`：`fetchImpl()` 直接取 `globalThis.fetch`
- `core/macros.ts:55-58`：`applyStMacros()` 直接取 `globalThis.substitudeMacros`
- `plugins/builtin/image/nai.ts:328`：直接取 `globalThis.fetch`

> ⚠️ **链 3 是本次审计新发现的、任务书没点到的第三条链**。特别刺眼的是 `core/macros.ts:55-58` 与 `agent/transport.ts:450` —— **同一个 `substitudeMacros` 接口，同一个底座里走了两条不同的链**：core 走裸 `globalThis`，agent 走 `globalFunction`。这是二义性的最坏形态：**同一能力、同一进程、两种解析结果**。

### 1.3 三条链的语义差异（逐条判定，含「统一后是否等价」）

| 差异点 | `hostFn` | `globalFunction` | 统一后是否等价 |
|---|---|---|---|
| (1) 是否读注入假实现 | **读** `injectedBridge`（storage.ts:77） | **不读** | **不等价 —— 真实回归风险** |
| (2) `window[name]` 兜底 | 无 | 有（transport.ts:177-178） | 页面环境下 `globalThis === window`，**等价（死代码）** |
| (3) `this` 绑定方式 | 闭包 `(...args)=>helper[name](...args)` | `.bind(helper)` / `.bind(globalThis)` | 对 `helper[name]` **等价**；但见下「唯一实质差异」 |
| (4) 未命中返回值 | `null` | `undefined` | 需调用方统一 `??` 写法，**低风险** |

**关于 (3) 的精确判定（任务书点名要复核的 `.bind(helper)` vs 闭包）**：

- 对 `TavernHelper[name]` 这一支，`.bind(helper)` 与闭包 `helper[name](...args)` **语义等价** —— 两者都以 `helper` 为 `this` 调用。**结论：等价，不是回归点。**
- 但存在**一处细微不等价**：`hostFn` 的闭包**每次调用重新读取 `helper[name]`**（晚绑定）；`globalFunction` 的 `.bind` 在**解析那一刻就把函数引用固定下来**（早绑定）。
  → 宿主若在运行中**替换** `TavernHelper.substitudeMacros`（热重载 / 插件升级），`hostFn` 拿到新实现，`globalFunction` 仍调用旧函数。**扩展形态下这正好是最可能发生的场景**（扩展重载 = 宿主接口被换掉）。
  → 统一时**必须选 `hostFn` 的晚绑定语义**，不能迁就 `globalFunction`。

**关于 (1) 的精确判定（真正的回归点）**：

`globalFunction` 不查 `injectedBridge`，导致 transport 的 3 个接口在测试里**没法用 `setHostBridge` 假造**。这正是 `TransportDeps.substituteMacrosImpl`（`agent/transport.ts:40`）和 `generateRawImpl`（`agent/transport.ts:38`）这两个后门存在的原因 —— **它们是绕开二义性的补丁，不是设计意图**。

> **统一为单链后：只要新链保留第 (1) 层（注入假实现），并把 3 个接口纳入 `hostFn`，这两个 `deps.xxxImpl` 后门就可以删除，回归风险 = 把 `deps` 注入改写成 `setHostBridge` 注入，行为等价且覆盖率更高。**
> 但**若只做「把 transport 改成 import hostFn」而不动 `deps`**，则 `deps.xxxImpl ?? hostFn(name)` 的短路优先级仍在 —— 那时**不产生回归，但二义性只是从「两条链」变成「链 + 后门」，并未根除**。这是统一时必须做全的一步。

### 1.4 扩展形态下该怎样

按 `reports/扩展迁移-宿主桥设计.md` 已定的「多源 provider chain」落地，**并要求这次一步做全**：

```
resolve(name):
  1. 注入的假实现（测试 / 覆盖）        <- 保留 hostFn 第(1)层，这是可测性的根
  2. 注册进来的原生适配器（扩展自带）      <- 新增层：ST.getContext / STscript / 后端 API
  3. globalThis.TavernHelper[name]      <- 兼容老环境
  4. globalThis[name]                    <- 兼容旧行为
```

配套三条硬约束：

1. **晚绑定**：外部函数引用不 `.bind` 固定，保持每次调用重新解引用（对齐 `hostFn` 闭包语义）。
2. **删除 `globalFunction()`**（`agent/transport.ts:166-183`）与 `deps.substituteMacrosImpl` / `deps.generateRawImpl` 两个后门。
3. **`core/macros.ts:55-58` 的 `applyStMacros` 改走同一条链** —— 消除「同一接口两条链」的最坏情形。

### 1.5 是否阻塞迁移

**阻塞。** 这是唯一一处「同一能力在同一进程里有两种解析结果」的分歧，不统一就等于把二义性原样带进扩展版；且第 (1) 层的有无直接决定扩展版能不能单测。

## 二、桥把「酒馆助手」当唯一宿主（维度 1 延伸）——**真积病，阻塞**

### 2.1 现象

`hostFn` 的第 (2)(3) 层硬编码查 `globalThis.TavernHelper`。在扩展形态下，这等于**把底座绑死在 JS-Slash-Runner（第三方脚本加载器）上**，而不是 ST 官方能力。

### 2.2 证据

- `core/storage.ts:5`：「把 `window.TavernHelper` 的全局接口收在一处」
- `core/storage.ts:72`：「查找顺序：注入的假实现 → `window.TavernHelper[name]` → 全局同名函数」
- `core/storage.ts:83-86`：真正的 `TavernHelper` 解引用
- `plugins/builtin/cangxuan/assets.ts:14`：**反证** —— 「不依赖 TavernHelper：面板里 `window.TavernHelper` 是 `undefined`，纯 fetch 就够」
  → 说明代码里**已经知道**有「没有 TavernHelper」的环境，但只有 assets.ts 一个文件适配了
- `plugins/builtin/image/manifest.ts` / `cangxuan/manifest.ts` 的 `status()` 模式：能力可得性是**逐插件硬编码的个案**，不是框架机制

### 2.3 特别点名：`getScriptTrees` —— 不可替代的私有大接口

`core/portrait.ts:17-27` 走 `hostFn('getScriptTrees')`，用途是**读取「状态栏」脚本的内嵌 HTML 来抽取内置图库**：

```
17: function getScriptTreesViaHost(option: { type: string }): any[] {
18:   const fn = hostFn('getScriptTrees');
19:   if (!fn) return [];
1203:   const trees = getScriptTreesViaHost({ type });
1208:   if (script.name === STATUSBAR_SCRIPT_NAME && typeof script.content === 'string') {
```

配合 `core/portrait.ts:1101` 的 `STATUSBAR_SCRIPT_NAME = '状态栏'`。

**这是纯脚本形态的产物**：「脚本树」是酒馆助手独有的概念，ST 原生**根本没有这个 API**。扩展版里这条数据来源**整个消失**，图库采集能力要重新定义（改为扩展自带素材目录 / ST 原生 `/api/images/list`，后者 `assets.ts:80-83` 已经在用）。

### 2.4 扩展形态下该怎样

1. 把 `Capability` 描述符**从个案提升为框架机制**：每个宿主接口声明 `{ name, provider, required, degrade, label }`，启动时探一遍得出一张**能力表**；插件在 `contributes` 里声明所需能力，缺失时**该插件不注册并给出可读原因**，而不是运行时炸在半路。
2. 消掉所有「能力可得性靠 try/catch 兜底」的写法（如 `portrait.ts:19-26` 静默返回 `[]`、`storage.ts:495` 的 `console.warn` 降级）—— 降级要**显式登记进能力表**，让 UI 能说「立绘图库：不可用（缺 getScriptTrees）」，而不是无声地空着。
3. `getScriptTrees` 在扩展版**直接标为不可用能力**，图库来源改走 ST 原生资源接口。

### 2.5 是否阻塞迁移

**阻塞。** 扩展版的立身之本就是「不再依赖另一个第三方插件」；桥不改，底座换个壳还是酒馆助手的附庸。

## 三、模块级单例 / 全局可变状态（维度 3）——**真积病，选择性阻塞**

### 3.1 全量清点（grep `^(let|var)` + 注册表）

| # | 状态 | 位置 | 影响面 | 扩展形态下的风险 |
|---|---|---|---|---|
| 1 | `pluginMacroSource` | `core/macros.ts:123` | 全局宏渲染 | **高：多实例互相覆盖** |
| 2 | `pluginMacroNamesSource` | `core/macros.ts:140` | 全局宏名清单 | **高** |
| 3 | `registeredTavernMacros`（Map） | `plugins/host.ts:65` | 注册进**酒馆宏引擎**的全局副作用 | **高：卸载不干净会残留** |
| 4 | `lastMacroValues` | `plugins/host.ts:128` | 宏值回填 | **中：跨会话疑似串值** |
| 5 | `injectedBridge` | `core/storage.ts:57` | 测试注入 | **中** |
| 6 | `saveTimer` / `pendingData` | `core/storage.ts:599-600` | 防抖保存 | 低-中 |
| 7 | `csrfToken` | `plugins/builtin/cangxuan/assets.ts:20` | CSRF 缓存 | **低：见 3.4，良性** |
| 8 | `callSeq` | `agent/transport.ts:222` | tool_call id 计数 | 低：单调计数，串了也无害 |

### 3.2 重点 1：宏注册表 —— 多实例/热重载会串（**任务书点名，确认成立**）

```
core/macros.ts:123: let pluginMacroSource: PluginMacroRenderer | null = null;
core/macros.ts:130-132: registerPluginMacroSource(source) { pluginMacroSource = source; }   // 后注册覆盖前者
core/macros.ts:140: let pluginMacroNamesSource: string[] = [];
core/macros.ts:149-151: registerPluginMacroNames(names) { pluginMacroNamesSource = names.slice(); }
```

**「后注册覆盖前者」是明写在注释里的约定**（`core/macros.ts:128`：「同一个进程只该有一个来源，后注册的覆盖前者」）。在单脚本形态下成立 —— 一个页面只挂一份底座。**扩展到多实例后这条约定直接变成 bug**：

- 两个底座实例（如两个 ST 扩展页 / 面板重复挂载）→ 后者 `registerPluginMacroSource` 覆盖前者 → **实例 A 的渲染开始用实例 B 的插件集渲染**；
- 热重载：新模块实例注册进来，**旧实例从不注销**（`unwirePluginMacros` 只在 `plugins/host.ts:150-153` 定义，**测试里 0 处调用、src 里 0 处调用** —— 实测 grep 确认它是死代码）→ 旧 renderer 悬空持有旧 store 引用 = **内存泄漏 + 潜在地雷**。

叠加 `plugins/host.ts:65` 的 `registeredTavernMacros`：它是**往酒馆宏引擎注册全局副作用的登记簿**，`syncTavernMacros()` 靠它「先撤旧再注册新」实现幂等（`plugins/host.ts:77-108`）。**如果两次注册来自不同实例，`clear()` 会把对方注册的宏一起撤掉** —— 互相拆台。

### 3.3 重点 2：`lastMacroValues` 的跨会话串值

```
plugins/host.ts:128: let lastMacroValues: Record<string, string> = {};
plugins/host.ts:135-147: rememberMacroValues(data) { ... lastMacroValues = next; }
plugins/host.ts:130-132: macroValue(name) { return lastMacroValues[name] ?? ''; }
```
调用点唯一：`run/runner.ts:347`。

设计意图（`plugins/host.ts:124-127`）：酒馆宏引擎回调**无参**，拿不到底座上下文，所以取「最近一次渲染时的值」。

**问题**：`lastMacroValues` 是**跨会话、跨角色卡共享的进程级缓存**。用户切了会话/角色卡后，ST 渲染角色卡里的 `{{图片提示词}}` 时若尚未跑过新一轮，**会拿到上一个会话的值** —— 这是脚本形态下「一个页面只有一份状态」的直接后果。扩展形态多实例/多会话并行时更明显。

### 3.4 重点 3：`csrfToken` —— **这条不阻塞，是良性缓存**

```
plugins/builtin/cangxuan/assets.ts:20:  let csrfToken: string | null = null;
plugins/builtin/cangxuan/assets.ts:23-32: getCsrfToken(force) —— 缓存 + 403 重取
plugins/builtin/cangxuan/assets.ts:45-48: 403 -> getCsrfToken(true) 强制重取一次
plugins/builtin/cangxuan/assets.ts:104-106: resetAssetToken() —— 测试清缓存
```

**诚实判定：这是正确的缓存设计，不是积病。** 它是一个**进程级幂等的 CSRF 令牌缓存**，且带了失效自愈（403 → 强制重取）。多实例共享同一个 token **恰恰是对的**（token 本就是页面级的）。**唯一建议**是额外监听 ST 的 token 轮换（若原生提供事件）而不是只靠 403 兜底；但这属于优化，不影响迁移。

> 本条明确写「不阻塞」，避免把一切都说成风险。

### 3.5 扩展形态下该怎样

引入**可注入的实例容器**（`createApp(host, deps)` 形态），把这些状态从模块作用域收进实例：

```
createCangxuanCore({ host, storage, macros, pluginHost }) -> {
  macroRegistry,   // 取代 pluginMacroSource / pluginMacroNamesSource
  tavernMacroReg,  // 取代 registeredTavernMacros
  ...
}
```

并**给 `unwirePluginMacros` 找到真实调用点**（当前是死代码）：实例 `dispose()` 时必须 ① 注销模块宏源、② 对酒馆宏引擎逐个 `unregister`、③ 清 `lastMacroValues`。

**`lastMacroValues` 应按会话/角色卡分区**（key 带 `session_id` / `char_id`），或干脆放弃回填、改为要求渲染时显式传上下文。

### 3.6 是否阻塞迁移

- `pluginMacroSource` / `pluginMacroNamesSource` / `registeredTavernMacros` / `lastMacroValues`：**阻塞**（多实例 + 热重载会串，且注销路径是死代码）。
- `csrfToken` / `callSeq` / `saveTimer`：**不阻塞**，随容器化顺带收编即可。

## 四、脚本变量域耦合（维度 4）——**真积病，阻塞**

### 4.1 现象

持久化层把 `VariableScope{type:'script'}` 写死在类型、解析、读写四个层面。扩展形态里**没有「脚本变量」这个概念**，这层抽象整体失效。

### 4.2 证据

**类型层**（`core/storage.ts:105-110`）：

```
105: /** 酒馆助手的变量作用域参数；数据一律放脚本变量 */
106: export interface VariableScope {
107:   type: 'script';
108:   /** 省略 = 当前脚本（脚本内调用时可以直接省） */
109:   script_id?: string;
110: }
```

—— `type` 是**字面量类型 `'script'`**，连别的取值都编不出来。

**脚本 id 解析链**（`core/storage.ts:112-132`）：

```
118: export function resolveScriptId(): string | undefined {
119:   const injected = (globalThis as Record<string, unknown>).__CX_SCRIPT_ID__;
120:   if (typeof injected === 'string' && injected.trim() !== '') return injected.trim();
122:   const getScriptId = hostFn('getScriptId');
123:   if (getScriptId) { ... }
131:   return undefined;
132: }
```

—— 两级：**面板脚本注入的 `globalThis.__CX_SCRIPT_ID__`**（一个纯粹的脚本形态 hack）→ 酒馆助手 `getScriptId()`。

**作用域构造**（`core/storage.ts:134-138`）：

```

136:   const script_id = resolveScriptId();

```

**读写全绑定** —— 5 个出口全部拿 `scriptScope()`：

| 操作 | 位置 | 接口 |
|---|---|---|
| 读 | `storage.ts:499` | `getVariables(scriptScope())` |

### 4.3 迁移到 extensionSettings / ST 原生存储的成本

**好消息：数据层与存储层已经分离得很干净。** 整棵树是 `RootData`（`core/types.ts`，zod schema），`core/storage.ts` 只做「**序列化 + 迁移 + 校验**」，实际 I/O 收敛在极小面积：

- 读：`readStoredRootData()`（`storage.ts:492-506`）
- 写：`writeRawRootData()`（`storage.ts:538-570`）
- 防抖：`saveRootDataDebounced()`（`storage.ts:603-609`）

**结论：只需替换这 3 个函数 + 删掉 `VariableScope` 类型，`RootData` 与 `migrateRootData`（`storage.ts:208-308`，含 v1→v5 全部迁移逻辑）可 100% 复用。**

**成本清单**：

| 项 | 成本 | 说明 |
|---|---|---|
| 换后端 | **低** | 实现一个 `StoragePort{ read(), write(data) }`，扩展版给你 `extensionSettings` / `/api/settings` |
| 删 `VariableScope` / `resolveScriptId` / `__CX_SCRIPT_ID__` | **低** | 纯删除，无下游依赖 |
| 数据迁移 | **中** | 老用户数据在脚本变量里，扩展版要**一次性导入**：提供「从酒馆助手导出 → 扩展导入」。好在 `exportAll` / `importAll` 已存在（`App.vue:75` 已 import） |
| 语义反转（卸载即清空 → 常驻持久） | **中** | 需重新定义生命周期：数据归属「全局 / 角色卡 / 会话」哪一级？现在 `RootData` 是**单份全局**（`GLOBAL_KEY`），扩展版要考虑多用户（ST 有多用户模式） |
| 并发写 | **低-中** | 现在是内存防抖 + 单页写；多标签页/多客户端时要加冲突处理 |

### 4.4 扩展形态下该怎样

```

createStoragePort(backend: 'extensionSettings' | 'scriptVars' | 'memory') -> StoragePort
```

`RootData` schema + `migrateRootData` 原样搬；扩展版新增 **v6 迁移：脚本变量 → 扩展存储**（放在 `migrateRootData` 的既有版本链里，见 `storage.ts:199-201` 的 v4→v5 写法作为模板）。

### 4.5 是否阻塞迁移

**阻塞。** 但请注意：**阻塞的是「存储后端抽象」，不是「数据模型」**。`RootData` / zod schema / v1→v5 迁移函数**零改动**，这是底座里最值得庆幸的一处解耦。

## 六、独立复核：Lead 报的 `rememberMacroValues` 缺陷（维度 3 延伸）

> Lead 中途报来一条疑似缺陷，要求我**独立复核，不要照抄定性**。以下是复核结果 —— **结论：Lead 的现象与因果链成立，我独立复现成功；但对「严重性归属」我要提出一处修正。**

### 6.1 现象与代码

`src/苍玄助手/plugins/host.ts:135-147`：

```
135: export function rememberMacroValues(data: MacroData): void {
136:   const bag = data as unknown as Record<string, unknown>;
137:   const next: Record<string, string> = {};
138:   for (const macro of liveMacros({ plugin_state: undefined })) {   // <-- 传了 undefined
139:     try {
140:       const value = macro.render(bag);
141:       if (value) next[macro.name] = value;
142:     } catch { }
143:   }
144:   lastMacroValues = next;
145: }
```

`liveMacros(state)` 走 `enabledPlugins(state)`（`plugins/host.ts:32-38` → `plugins/registry.ts:48-50` → `pluginEnabled`）：

```
registry.ts:41: export function pluginEnabled(state: PluginStateHost, id: PluginId): boolean {
registry.ts:42:   const hit = state.plugin_state?.[id];
registry.ts:43:   if (hit && typeof hit.enabled === 'boolean') return hit.enabled;
registry.ts:44:   return pluginManifest(id).defaultEnabled;      // <-- 没有开关就退回默认值

```

传 `{ plugin_state: undefined }` ⇒ 第 42 行 `undefined?.[id]` 恒为 `undefined` ⇒ 第 44 行**恒取 `manifest.defaultEnabled`** ⇒ **用户的关闭开关被完全忽略**。

### 6.2 我的独立复现（自己跑出来的，非引用 Lead）

用 `node --experimental-strip-types` 直接 import 被测模块（临时脚本跑完即删，未改 src）：

```

A plugin_state UNDEFINED : cangxuan,worldbook

C cangxuan OFF           : worldbook            <- 传对了就排除
D ALL OFF                : (none)
E liveMacros-equivalent  : cangxuan,worldbook   <- host.ts:138 用的就是这个形状
```

**对照实验**（把 `rememberMacroValues` 的逻辑用「现状」与「传真 state」两个变体各跑一遍，隔离因果因子）：

```
用户状态 = 关闭 cangxuan 与 worldbook 时：
  AS-IS  (plugin_state: undefined) : {"图片提示词":"PORTRAIT-1","角色列表":"CHAR-1","图片元数据":"PORTRAIT-1"}
  FIXED  (传真 state)              : {}            <- 正确行为：关了就该是空
  用户状态 = 启用时：
  AS-IS                            : {"图片提示词":"PORTRAIT-1","角色列表":"CHAR-1","图片元数据":"PORTRAIT-1"}
  FIXED                            : {"图片提示词":"PORTRAIT-1","角色列表":"CHAR-1","图片元数据":"PORTRAIT-1"}
```

**因果因子被干净地隔离出来了：只有 `plugin_state: undefined` 这一个变量在起作用。传真 state 后关闭场景立刻变成 `{}`。**

### 6.3 端到端复现：陈旧值确实会流到酒馆宏回调

用假 `TavernHelper.registerMacroLike` 捕获回调，走完整链路：

```
cangxuan macros: 图片提示词[tavern/preset], 角色列表[preset], 图片元数据[preset]
用户关闭时 syncTavernMacros(OFF)     -> registered: 0        <- 注册侧正确
跑一轮 rememberMacroValues(bag)      -> 缓存被 OFF 插件的数据填满
用户开启后 syncTavernMacros(ON)      -> registered: 1  /{{\s*图片提示词\s*}}/g
  callback value                     -> "PORTRAIT-1"        <- 直接读到陈旧缓存
```

**这一条纠正了我对「可达性」的初始怀疑**：`lastMacroValues` 确实能通过 `syncTavernMacros` 注册的回调（`plugins/host.ts:101` 的 `register(regex, () => macroValue(macro.name))`）被角色卡读到。

### 6.4 我对 Lead 定性的一处修正（**我不同意的部分**）

Lead 说这是「真缺陷」，并暗示影响路径包含「陈旧值泄漏」。**我认可它是缺陷，但要把严重性从「用户可见的数据泄漏」下调为「状态污染 + 陈旧值」，理由如下（这是我独立查证后的分歧点）**：

1. **不是「关了还能用」的泄漏。** Lead 自己也注意到、我实测确认：注册侧 `syncTavernMacros` 走的是**真 state**（`plugins/host.ts:59` 由 `wirePluginMacros(state)` 传入），插件关闭时会把宏从酒馆引擎**注销掉**（实测 registered: 0）。所以用户关掉插件后，角色卡里那条宏**根本不会被注册**，无从渲染。
2. **真正的影响是「重新启用后的陈旧值」。** 由于 `lastMacroValues` 在关闭期间被持续填充、且**关闭时不清空**（`host.ts` 里没有任何一处清空它的代码；`unwirePluginMacros`（150-153）也只清宏源与宏名，**不碰 `lastMacroValues`**），重新启用后第一轮若尚未跑 `rememberMacroValues`，回调会读到**关闭期间或更早的值**。这是**时序依赖**，不是无条件错误。
3. **是否可触达取决于 ST 渲染时机**：ST 在面板外渲染角色卡时回调才会被调用；若用户开启插件后先跑了一轮 Agent，`rememberMacroValues` 会正确刷新缓存，问题窗口自行消失。

**修正后的定性：这是一个「真实存在、已复现、但影响面为『重新启用后的短暂陈旧窗口』的状态污染缺陷」，不是「关掉的插件仍在泄漏数据」。** 把它写成后者会高估严重性、也会误导扩展版的设计重点。

### 6.5 归类：结构性积病，还是必须立刻修的 bug？

**我的判定：两者都是，但主归类是「结构性积病」——而且这正是它最值得写进清单的理由。**

**理由**（这是本条最重要的结论）：

- 它**不是一处笔误**。`PluginStateHost` 这个类型（`plugins/types.ts:155-157`）把 `plugin_state` 声明成**可选**：
  ```
  156: export interface PluginStateHost {
  157:   plugin_state?: Record<string, { enabled?: boolean } | undefined>;
  ```
  于是 `{ plugin_state: undefined }` **类型检查完全通过**。`state` 参数本身也是必填的，但**「state 里没有 plugin_state」和「我根本没有 state」在类型上无法区分** —— 这正是 `rememberMacroValues` 传 `undefined` 却毫无编译阻力的原因。
- **同一个坑已经踩过第二次**。Lead 提到阶段 3 修掉的 **F-A'**（`agent/registry.ts:164` 还留着当时的注释：「manifest.defaultEnabled —— 表面『插件开着』，实际**所有开关都失效**（关掉的插件照样给工具）」）是**完全相同的错误模式**：调用方把 `plugin_state` 弄丢了一层，于是所有开关静默失效。**两次都栽在「plugin_state 的封装/传递语义」上，这不是巧合，是接口设计缺陷。**
- 扩展版要换 ST 新宏 API（`macros.register`，旧 `registerMacro` 已 deprecated），这段代码**本来就要重写** —— 但重写时若不改**类型**，第三次踩坑只是时间问题。

### 6.6 扩展版该怎么根治（从类型上，而非从这次调用上）

1. **让「有没有 state」在类型上不可混淆**：把 `PluginStateHost` 的 `plugin_state` 改为**必填**，并引入不透明的 `PluginState` 值对象（构造时就必须给出真实开关表）。这样 `{ plugin_state: undefined }` **编译不过**。
2. **`rememberMacroValues(data, state)` 补上 `state` 参数并设为必填** —— 当前它**根本没有 state 参数**（`host.ts:135` 只有一个 `data`），这才是允许调用方「随手编一个 undefined」的根因。
3. **`lastMacroValues` 关闭时必须清空**：在 `syncTavernMacros` 的行 91（`registeredTavernMacros.clear()`）旁边一并 `lastMacroValues = {}`，让「关掉即消失」在**缓存层**也成立（现在只在注册层成立）。
4. **补一条回归测试**：断言「插件关闭时 `rememberMacroValues` 不得让任何该插件的宏名进入缓存」。现在没有这条测试 —— 这也是它能潜伏至今的原因。
5. **加 lint 门禁**（与 §8.3 同一条建议）：禁止向 `PluginStateHost` 形参传字面量 `undefined`。

**是否阻塞迁移**：**不阻塞**（功能可正常用，只是存在陈旧窗口），但**必须在新架构里根治** —— 因为它属于「同一接口语义被误传」的高复发模式，扩展版重写宏系统时是唯一的低成本修复窗口。

**结论：全部落在 `core/` 与 `agent/` 内（+ 插件自身目录），与契约 `plugins/types.ts:6` 的「插件只拿得到底座给的 host，插件之间不许互相 import」完全一致。分层硬规矩实测 100% 合规。**

### 8.2 唯一可挑的一处（轻微，不阻塞）

`plugins/builtin/cangxuan/tools.ts` import 了 `../../../core/portrait.ts`，而 `core/portrait.ts` 是那个 48.6KB、混着 `getScriptTrees` 宿主调用与旧工程代码的巨型文件。
→ 不是在「方向」上违规，是在**耦合粒度**上不佳：插件依赖了一个内聚度差的 core 模块。扩展版把 `portrait.ts` 按 §7.2 拆开后，插件只 depend 到细粒度的图库子模块即可。

### 8.3 是否阻塞迁移

**不阻塞，且值得表扬。** 这是底座里**已经为扩展形态准备好的部分**：`plugins/types.ts:1-12` 的契约（四张注册表 + 不许互 import + 关掉即消失）**零改动可复用**。

> 建议扩展版**把这条规矩做成 lint 门禁**（`eslint.config.mjs` 里加 `no-restricted-imports`），而不是靠人工自觉 —— 现在合规是因为纪律好，不是因为工具在拦。**这条建议与 §6.6 第 5 点合并考虑：两者本质都是「把口头约定变成编译器能拦的约束」。**

## 九、运行时假设（维度 5）——**视扩展面板形态而定，多半不阻塞**

### 9.1 逐条清点

| # | 假设 | 证据 | 扩展形态下是否成立 |
|---|---|---|---|
| 1 | `pagehide` 时 `unmount` | `index.ts:25-27` | **多半不成立**：扩展面板是常驻 DOM。但**成本极低**，改成扩展的卸载钩子即可 |
| 2 | iframe「高度跟内容走」→ 不用 vh、不锁高、不做滚动容器 | `global.css:8`（原话：「前端界面是『自适应高度的 iframe』：不用 vh、不给整页锁高度、不做自己的滚动容器」）；`components/AppShell.vue:36-37`（「不要在这外面再套一层滚动容器」） | **取决于 ext-prober 的实测**（常驻 DOM vs iframe）。若常驻 DOM：**必须补滚动容器 + 高度约束**，否则 fixed 暗幕与长列表都会错位 |
| 3 | 弹窗用「文档流 + `scrollIntoView`」而非 fixed 居中 | `components/Sheet.vue:21-28`（原话：「前端界面是『高度跟着内容走』的 iframe，用 position:fixed 居中会在长页面里弹到屏幕外」）+ `Sheet.vue:33-35` 的 `scrollIntoView({block:'nearest'})` | 同 2。若常驻 DOM，fixed 居中**反而更正确**；现在的写法是为了迁就 iframe |
| 4 | `localStorage` 穿透到父窗口（**靠同源**） | `core/portrait.ts:1117-1139`：`hostStorage()` 依次尝试 `window.parent?.localStorage` → `window.top?.localStorage` → `localStorage` | **最脆弱的一条**。依赖「脚本与前端界面均与酒馆同源」（`portrait.ts:1117` 注释）。扩展若在不同 origin 或 iframe sandbox 下，**三级兜底全部返回 [] 且静默降级**（`portrait.ts:1144-1145`） |
| 5 | 全局 `errorCatched` / jQuery ready 引导 | `index.ts:14-18, 31-35, 38-44` | 扩展形态下换引导即可，**很薄** |
| 6 | `visibilitychange` 时刷新 | `App.vue:297, 301, 310` | 通用，**继续成立** |
| 7 | 同源 `fetch('/csrf-token')` 等 ST 原生 API | `plugins/builtin/cangxuan/assets.ts:8-14`（实测记录：`cx-pw-frame` 与酒馆同源 `about:srcdoc`，可直接 fetch） | **相反：这条会在扩展里变简单**。扩展本就跑在 ST 页面里，同源是**前提**而非假设 |

### 9.2 关键判定

**条目 2 / 3 / 4 是同一件事的三个面：整个 UI 层与数据采集层都建立在「我在一个自适应高度的同源 iframe 里」这个前提上。**

- 若扩展面板**仍是 iframe**（ST 扩展常用 `registerExtension` + 自建 iframe）：**基本不阻塞**，只需处理 `pagehide`。
- 若扩展面板是**常驻 DOM**：需要**一次集中修正**（`global.css:8` 的高度策略 + `AppShell.vue:36` 的滚动容器 + `Sheet.vue:24` 的弹窗定位 + `portrait.ts:1117` 的存储来源），但这四处**改动都很局部**，属于「适配」不属于「重写」。

### 9.3 是否阻塞迁移

**多半不阻塞**，但**依赖一个尚未落地的事实**：扩展面板是常驻 DOM 还是 iframe（这正是 ext-prober 在查的问题）。**在拿到答案前，本条不应被当作已解决。**
