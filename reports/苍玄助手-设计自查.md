# 苍玄助手 · 设计自查（底座 + 插件 这一版）

> 对象：reports/苍玄助手-底座与插件.md（理念/契约）、reports/苍玄助手-底座化实施计划.md（计划）、设计稿/苍玄助手-底座与插件设计稿.html（9 屏）。
> 原则：**简洁**（少一个概念、少一层界面）、**扩展性**（加插件/加来源不改编骨架）、**优雅**（同一件事只有一种说法、一个落点）。
> 自查方式：每条结论都对着**现有代码**核过（路径 + 行号级事实），不是凭印象。

## 0. 结论摘要

- 会真出问题或自相矛盾的：**12 条**（A1-A12）—— 其中最严重的是 **A1 懒加载在单文件脚本里根本不成立**。
- **第二轮（需求变更）**见 §6：立绘去页面 + 记录不占页面（进对话页 `⋯` 的 Sheet）+ 宏成为第四张注册表 + 插件改叫「苍玄助手」；复核时又抓到 1 个真 bug（传图结果不落盘）。
- **A12（动手前才发现）**：计划 §10 写「每个阶段一个 commit」，但这个工作区**根本不是 git 仓库** → 已改成文件快照到 backups/，并建议先 git init。
- 扩展性缺口：**8 条**（B1-B8）—— 最严重的是 **B1 MCP 工具是异步拉来的，静态工具清单撑不住**。
- 可以更简洁的：**5 条**（C1-C5）。
- 考虑过但**否决**的：3 条（附理由，免得下一轮再吵）。

## 1. 必须改（A：会咬人）

### A1 懒加载：单文件脚本里捏不出 chunk（最严重）

事实：webpack.config.ts 里 output.publicPath = **空串**、chunkFilename = <name>.[contenthash].chunk.js、optimization.splitChunks.chunks = **async**、asyncChunks: true。
而苍玄助手在酒馆里的形态是**一个脚本 JSON 里的一整段 JS**（src/酒馆助手脚本-苍玄助手.json），dist 里的 chunk 文件根本不会被酒馆加载。
后果：页面里一写 defineAsyncComponent / import()，webpack 就把代码拆成 chunk，运行时按**文档 URL** 相对解析去请求 -> 404 -> 插件页永远打不开（真酒馆里直接白页）。
决定：
1. 插件页的取法**统一走「运行时解析页面组件」**，阶段 1-3 全部静态 import（不写 import()），验收标准从「体积不膨胀」改成「**构建产物里不许出现任何 chunk 请求**」；
2. 阶段 3 顺手加 limitChunkCount = 1（或 splitChunks: false），把「一个脚本 = 一个文件」这条硬约束写进门禁；
3. 懒加载留到二期外部插件（那时才有独立 URL 可加载），并写明前提：得先有稳定的脚本 URL 或让用户填地址。
落点：计划 §5 验收、理念 §4.1 硬要求 1、设计稿屏 8「三条硬要求」。

### A2 「三张注册表」下面列了四行

设计稿屏 1 标题写「三张注册表：插件只往这里贡献」，下面却列了**四行**（工具 / 技能 / 页面 / **设置表单**）。设置字段是「插件声明、宿主渲染」的机制，不是一张聚合表，混进去会让「注册表」这个词失焦。
决定：统一成：**三张注册表（工具 / 技能 / 页面）+ 插件另外能声明设置字段（宿主渲染）**。四类贡献点仍然成立，但只有前三是「表」。

### A3 契约里没有「预设模板」这个贡献点，设计稿却在显示它

屏 6「它加了什么」里明写「预设模板：智绘姬」，理念 §11 原语表也写「预设｜底座｜用户（插件可提供模板）」，但 PluginManifest.contributes 里**没有对应字段**。
决定：加 presets?: PresetTemplate[]；并钉住语义 —— 模板是「**入口**」不是「活物」：点一下导入成用户自己的预设，导入后归用户，**关掉插件不回收**（否则用户数据会无声消失）。这条同时补上了 B5。

### A4 contributes.prompts 没有消费者

现状：全仓没有读 contributes.prompts 的代码，运行循环也不会拼「插件提示词块」。留一个没人用的贡献点 = 以后每个人都要猜它是什么。
决定：从阶段 1 / 阶段 2 的契约里**删掉**，进二期跟钩子总线一起做（那时才有消费者）。

### A5 设计稿数字与代码不符

屏 3 写「13 个 · 默认开 8」。代码事实：agent/registry.ts 里 DEFAULT_ON_TOOLS = 9（wb_list / wb_search / wb_read / entry_create / entry_edit / entry_delete / skill / read_skill_file / submit），工具总数 13（世界书 7 + 内核 5 + 生图 1）。
决定：改成「13 个 · 默认开 9」，并在旁边标一句「数字以 agent/registry.ts 为准」（设计稿不复制事实，只引用）。

### A6 「MCP 工具逐条停用」没有落点

现状：全局能力是常量拼的（App.vue: globalCaps = DEFAULT_ON_TOOLS + pluginTools），**没有工具级开关**；ToolOverrideSchema 里也只有 description / param_descriptions / param_defaults / timeout_ms / config，**没有 enabled**。设计稿屏 7 和理念 §9 都承诺了「逐条可停用」。
决定：定一条规则 —— **工具不能单独停用；停用永远在「来源」处**：
- 内置/外部插件的工具 -> 关插件（plugin_state）；
- MCP 工具 -> 关服务器，或在这个服务器页里逐条勾掉（存插件自己的设置 plugins.mcp.servers[].disabled_tools）；
- 「设置 · 能力 · 工具」段**只读**（只改说明），某条被来源停用时行上标「已停用」。
好处：底座一个字段不加、界面不加控件，而「谁能关掉它」永远只有一个答案。

### A7 「插件页」一词同时指两个东西

文档里「插件页」既指插件贡献的**内容页**（立绘那种，上顶栏），又指设置里的插件**管理页**（列表 › 详情）。
决定：定名 —— **插件内容页**（页面注册表注册的）与**插件管理页**（设置 · 能力 · 插件 › 详情）。计划、理念、设计稿、代码注释全部用这两个词。

### A8 屏 7 顶栏与容量规则冲突

屏 2 定的规则是「核心页常驻 + 插件页按 order 抢剩余格（药丸栏 5 格 = 3 核心 + 2 插件）」，屏 7 却画了「对话 MCP 立绘 世界书 设置」= 3 个插件页。
决定：屏 7 改成与其它屏一致（对话 立绘 世界书 记录 设置）；MCP 内容页默认 inTabbar: false（从设置 · 能力 · 插件 -> MCP -> 它加了什么 -> 页面 进），想在顶栏就把它的 order 提前。

### A9 TAB_IDS 留着 = 第二份事实来源

计划阶段 1 原写「core/types.ts：TAB_IDS 保留为 id 名单」，设计稿屏 8 也这么写；但页面一旦由注册表组装，TAB_IDS / TabId 联合类型就是**同一条事实的第二份定义**（改一处忘一处）。
决定：**删掉 TAB_IDS 与 TabId**。页面 id 只在页面注册表里定义（核心页也当成「底座贡献的页面」放进同一张表），active_tab 用 z.string() + 「当前页不存在就回落到第一个可用页」。TAB_LABELS 照计划删除。

### A10 顶栏顺序两份说法

计划阶段 1 验收写「界面上看不出任何变化（6 个页签、顺序不变）」，代码现顺序是 立绘/世界书/对话/能力/记录/设置；但设计稿 5 张手机图都画「对话」在第一位。
决定：写成时间线 —— 阶段 1 保持老顺序（6 格，纯等价改写）；**阶段 2 并掉「能力」时同时把「对话」提到第一位**（顶栏 5 格：对话 / 立绘 / 世界书 / 记录 / 设置），并把这一条写进阶段 2 验收（设计稿画的是阶段 2 之后的目标形态）。

### A11 插件 id 与页面 id 差一个字母

计划里插件 id 是 portrait，页面 id 是 portraits（零迁移必须保留的老 id）—— 一个 s 的差异是长期脚滑点。
决定：插件 id 直接用页面 id 的词：portraits / worldbook / image / mcp。数据键 plugins.portraits、plugin_state.portraits 与页面 id portraits 完全同名，少一层映射。

## 2. 应该做（B：扩展性）

- **B1 MCP 工具是异步来的，静态清单撑不住**：contributes.tools 是静态声明，而 MCP 要 initialize + tools/list 之后才知道有什么工具。注册表要区分两条通道：**静态贡献**（manifest.tools）与**运行时注册**（registerRuntimeTools(pluginId, ToolDef[])，拉取成功 upsert、失败只影响自己、断开即撤销）。底座因此**完全不需要知道 MCP 的存在** —— 这才是分层真的成立。落点：计划 §7 + 契约。
- **B2 插件状态谁算**：把现有 imagePluginStatus 泛化成契约里的 status?(config) => { label, kind }（插件自己知道自己缺什么），底座只负责画。定优先级：未启用 > 出错 > 缺配置 > 已启用（解决屏 5 里 MCP 行同时像「已启用」又标「缺配置」的歧义）。
- **B3 插件画面抛错会白屏**：加页面级错误边界（onErrorCaptured / errorHandler）——挂掉时页面内显示「这个插件挂了」+ 「停用」按钮，不许拖垮整个面板。落点：阶段 3 验收。
- **B4 插件页怎么拿自己的设置**：host 补一条明确的 host.config（只读写自己那段：get / set / subscribe），跟 host.storage 说清区别。写进理念 §3 host 表；否则阶段 3 一动手就会有人去 import store。
- **B5 贡献分两类**：**活的**（工具 / 页面 / 技能：关插件即消失）与**入口**（预设模板：导入即归用户，不回收）。写进判据，避免以后每个贡献点都要单独讨论一遍。
- **B6 插件自带的技能用户改不了**：技能行上「插件自带」是只读的，操作只有「复制成自己的」（复制后是普通技能，跟插件脱钩）。
- **B7 DATA_VERSION 什么时候涨**：定规矩 —— 只在**结构搬迁**（字段搬家/改名/换类型）时涨；插件新增设置字段靠 zod 默认值兜底，**不涨**。免得以后每加一个字段就动一次老数据。
- **B8 插件列表的排序与状态**：内置在前、外部随后、各自按 order / 名字；行状态标签按 B2 的优先级取一个。

## 3. 可以更简洁（C）

- **C1 「⋯ 更多页面」+ 容量抢占推迟到阶段 3**：阶段 1/2 里根本没有插件页，现在做这套容量逻辑是为假想需求写代码。阶段 3 真出现第 3 个插件页时再做，且 ⋯ 就是「**所有页面**」Sheet（复用现有 Sheet 组件，不新造下拉菜单）。
- **C2 plugin_state 里暂时不要 installed_at**：阶段 1 只留 { enabled }（installed_at 是外部装载才需要的，二期再加）。
- **C3 契约不写联合类型**：设计稿屏 8 写的 tools?: string[] | ToolDef[] 是文档简写，落到代码只会是**一种形状**（阶段 1 名字数组，阶段 3 换成 ToolDef，字段名不变）。
- **C4 两级药丸保留**：外层 4 格（接口/预设/能力/数据）+ 能力段内层 3 格（工具/技能/插件）。理由是操作数（三段都长，要跳），而且沿用现有 SegBar，不新造组件。
- **C5 插件行的快捷开关保留**（每天最常做的动作就是开关插件）：开关与 › 之间留 ≥8px、各自 ≥40px 点击区，避免误触。

## 4. 考虑过但否决的（附理由）

- **把阶段 1+2 合并**：否决。阶段 1「界面零变化」是一个**安全闸**：能证明注册表渲染与写死页签等价；合并会把这个性质弄丢（出问题分不清是注册表还是界面调整）。
- **给工具加全局 enabled 开关（tool_overrides.enabled）**：否决，见 A6。会让「能力」段多一个状态，而「在来源处停用」已经够用。
- **插件 id 与页面 id 分离**（portrait / portraits）：否决，见 A11。

## 6. 第二轮：需求变更后的复核（立绘去页面 / 记录进对话页 ⋯ / 宏 / 改叫苍玄助手）

### 6.1 用户新指令 → 落成了什么

| 指令 | 落成 |

### 6.2 复核时新抓到的问题

- **A13（真 bug，顺手修）**：现在的「传图」把解析出的元数据写进 App.vue 的**内存 ref**（`manualMeta`），**刷新就没了** → 阶段 3 搬进 `plugins.portraits.manual_meta` 才真的存下来。
- **A14（机制风险）**：宏是**全局副作用**（酒馆的 `registerMacroLike`）—— 插件自己注册就得自己记得 unregister，插件一多必然漏。→ 决定：**插件只给 `resolve`，注册 / 注销由底座在启用 / 停用时统一做**。
- **A2 修订**：上一轮定的是「三张注册表 + 一样声明」，宏进来之后是**四张注册表**（工具 / 技能 / 页面 / 宏）+ 一样声明。宏**不单独占管理段**（天天要管的开关仍然只有插件那一个），来源在插件管理页「它加了什么」里可见。
- **D1（设计冗余，已消除）**：原立绘页的工作台 = 「选预设 → 填需求 → 生成」，而对话页本身就是这件事 → 页面是重复的。这也解释了为什么去页面化是「更整洁」而不是「少个功能」。

### 6.3 用户已答复的两处（已按答复落进文档）

1. **记录**：用户口径「压根没人看的东西不要占页面」→ 放**对话页右上角 `⋯`** 里的一张 Sheet；核心页只剩 对话 / 设置。
2. **插件名**：就叫 **苍玄助手**（id `cangxuan`）—— 理由：底座是 agent 底座，苍玄助手只是其中一个功能。

### 6.4 命名撞车（记下来，别再纠结）

面板（脚本名 `酒馆助手脚本-苍玄助手.json` / 目录 `src/苍玄助手/`）和插件行都叫苍玄助手。处理办法：**面板名一律不动**（改脚本名 / 目录名要动构建与导入，不值得）；插件行的说明第一句写「苍玄界专用功能」，图标用「苍」。以后底座若要对外独立取名，改的是顶栏标题一处。
