## 1. 硬约束（这决定了「直接拿来改」能做到什么程度）

我实测了大小：

| 项 | 字符数 |
|---|---|
| `A3_世界书优化.md`（世界书手册） | **27,642** |
| `tavern-card-builder/SKILL.md` | 11,046 |
| `sillytavern-api-reference/references/core-facts.md` | 10,482 |
| **我们整个存储** `cx_assistant_v1` | **8,000** |
| 其中 skills 块 | 1,481 |

**结论：世界书手册一个文件就是整个存储的 3.5 倍。**

再叠加已经记在案的量级风险：

| 块 | 现在 | 加上 TavernWeave 素材后 |
|---|---|---|
| `presets` | 5,169 | 不变（5,169） |
| `skills` | 1,481 | **+27,642 → 直接爆** |
| 合计 | 8,000 | **≈35,000+** |

而 ST 的变量存在 `settings.json` 里 —— **那个文件已经 52 MB**。

**另外两个技术事实**：
- `tools_skill.ts` 有 **`BODY_LIMIT = 20000`**、`FILE_LIMIT = 12000` 的硬截断 → 27,642 字符的手册**读不全**
- 我们插件是扩展，**打包体积没有硬约束**（现在 index.js 只有 219 KB）→ 素材可以进 bundle

**所以真正的矛盾是**：素材能进 bundle，但**装不进「用户可编辑的技能」**（那是存在酒馆变量里的）。

## 2. 三条路线（请你选）

### 路线 A：内置 skill 进 bundle，不进变量 ⭐ 我推荐

```
素材（TavernWeave 适配版）
   ↓ 打包时嵌入
dist/extension/index.js  ← 无大小限制
   ↓ 首次运行
作为 builtin skill 出现，正文在代码里
   ↓
用户看不到 27,642 字符躺在自己的变量里
```

| | |
|---|---|
| ✅ | 不占用户存储，不受 8000 字符限制 |
| ✅ | 可以**完整**放手册，不截断 |
| ✅ | 符合 D7（删掉没价值的内置 skill，换成真材实料） |
| ⚠️ | 用户**不能编辑**内置 skill 正文（只能改工具提示词） |
| ⚠️ | 需要改 `createBuiltinSkills()` 的加载方式 |

**技术上可行**：现在 `builtin.ts` 是 18,816 字符的 TS 源文件，编译进 bundle。把手册作为 TS 字符串常量放进去即可。

### 路线 B：素材放 ST 真文件（`/api/files/`）

```
素材 → ST 服务器文件系统 /data/default-user/extensions/...
   ↓ 运行时按需 fetch
skill 正文只存「去哪读」
```

| | |
|---|---|
| ✅ | 不占变量，且**可更新**（改文件即更新） |
| ✅ | 阶段 7 已用过这条路，能力已验证 |
| ❌ | **依赖 ST 的 files API 权限**（部分部署会挡） |
| ❌ | 用户可能没开 files API → 技能读不到 |

### 路线 C：只搬「精华摘要」，正文自己压缩

```
27,642 字符 → 压到 3,000-5,000 字符
```

| | |
|---|---|
| ✅ | 能进变量，用户可编辑 |
| ❌ | **违反你的要求** —— 「AI 写的提示词很差」，压缩 = AI 重写 |
| ❌ | 27,642 → 4,000 会丢大量细节 |
