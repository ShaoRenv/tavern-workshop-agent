# 阶段 5 · 真机验收：世界书读写全坏（P5-7）—— 结论与更正

> 本文档记录 Lead 在真酒馆里的发现、**修复后的真机复验结果**，以及一处**我自己先说错、后来更正**的判断。

## 1. 原始缺陷（真实，已修）

| 动作 | 修复前 | 说明 |
|---|---|---|
| `readAll('Eldoria')`（真书、真 4 条） | **0 条** | `core/worldbook.ts:486` 要求 `Array.isArray(raw)`，而 ST 原生 `loadWorldInfo` 返回 `{ entries: {...} }` 对象 |
| `writeAll('Eldoria', 4 条)` | **书被清空成 0 条** | `writeAll` 传数组给 `saveWorldInfo`，而 ST 期望 `{ entries: {...} }` |

根因：`core/native.ts` 把这些名字映射到 ST 原生函数时，**名字对上了、形状没对上** ——
`getWorldbook`/`replaceWorldbook` 的契约是**酒馆助手形状**（数组进数组出），原生却是映射对象。

**实测三种形状（真酒馆探针）**：
```
ctx.loadWorldInfo('Eldoria')            → object，keys=['entries']，4 条
saveWorldInfo(name, [ ... ])            → 落盘后 0 条      ← 旧实现传的就是数组：写空
saveWorldInfo(name, { entries:{...} })  → 落盘后 1 条      ← ST 期望的形状
```

## 3. ⚠️ 更正：我先前说的「修复没生效 / 构建产物是旧的」是**错的**

我在排查中一度判断「部署的产物不含修复」，理由是：往 `native.ts` 加标记后重建，**chunk 的哈希和大小都没变**。
**这个判断错了，两个测量错误叠在一起**：

1. **查错了文件** —— `native.ts` 被 `src/extension/index.ts` **静态 import**，它的代码进的是 **`index.js`（入口）**，
   而我一直在 grep **async chunk**。chunk 里当然找不到我加的标记。
2. **字符串比对受控制台编码影响** —— 我用 `Contains('宿主能力已切到')` 去查，返回 False；
   但 `index.js` 里其实**有**这段代码（终端把它显示成乱码 `[鑻嶇巹鐣宂 瀹夸富鑳藉姏宸插垏鍒?ST ...]`）。
   同类的乱码在上一轮就出现过（PowerShell 把 UTF-8 当 GBK），我这次仍然踩了进去。

**验证构建产物是否更新，正确做法**（记下来，别再重复我这次的弯路）：
- 看 **`index.js`**（入口，静态 import 的东西在这）；chunk 只装动态 import / 拆分出去的部分；
- 别用中文 `Contains` —— 要么只比 **ASCII**（如 `loadWorldInfo`），要么用行级工具按字节比；
- 最可靠的是**行为验证**（在真机里读一次、看界面/日志），而不是在压缩产物里找字符串。
  **能改源码加一行临时诊断日志，就别去考古 bundle。**

⚠️ **我在验收里毁过一次真数据。** 教训：**在验证一条写入路径之前，不要假设它是无害的** ——
我原本以为「备份内容 = 真书当前内容，所以回滚是无副作用的」，但前提是写入路径正确；
在一个「写会清空」的 bug 面前，这个「安全」设计恰好变成了破坏性的。
**规则：写入类验证一律用自建的一次性世界书，绝不借真书。**

## 5. 写路径（write）的验证状态

| 层级 | 状态 |
|---|---|
| 代码层（独立探针，用真机捕获的真实形状） | ✅ 通过：数组 → `{ entries:{...} }`，uid 用条目 uid 当键，`extra` 往返不丢 |
| 单元测试（native-adapter 补的 7 条） | ✅ 通过 |
| **真机端到端写一次** | ⏳ **未完成**（见下） |

真机写验证我试了两次都没做成，原因是**注入竞态**：我在应用运行中直接往 `TavernHelper` 写 `wb_backups`，
应用的防抖 `save()`（2500ms）随后会用它的内存状态**覆盖**我的注入；
立刻 `location.reload()` 又会赶在 ST 落盘之前，导致注入根本没持久化。两个方向都失败。
**正确做法**：走应用**自己的**写入路径产生备份（即让模型真的调一次世界书工具 → 产生草稿 → 应用），
而不是从外部注入存储。这条留给下一步（见 task-31 / 验收清单）。

## 6. 为什么所有门禁都没拦住这类 bug

| 门禁 | 为什么没用 |
|---|---|
| `node --test` 543 条全绿 | 用的是**假端口**（手写 WorldbookPort），从不走真适配层 → 形状对不对测不到 |
| `tsc` 0 错 | `lateBind`/`resolvePath` 拿到的是宿主函数，类型在这里是断的 |
| 能力闸（P4-7） | 只检查「**有没有** getWorldbook」，**不检查形状对不对** |
| 之前的真机验证 | 只看「插件装没装、工具在不在、页签有没有」——**没有一次真的读或写一本世界书** |

**共同点：验证了「接上了」，没验证「真的能用」。**
下一段做外部插件装载时，同样的坑会以「别人的代码按文档形状写、真实宿主给的是另一种形状」再出现一次。

1. **每条适配映射都要有一次真实调用**（读一次、写一次），不只是「函数存在」；
